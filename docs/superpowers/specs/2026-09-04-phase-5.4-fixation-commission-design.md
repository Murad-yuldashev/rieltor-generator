# Phase 5.4 — Cross-CRM fixation (C6) + commission (C7/C8) Design

**Status:** Draft for review
**Date:** 2026-09-04
**Feature codes:** C6 (client fixation with uniqueness check), C7 (commission per unit, showcase filter), C8 (immediate commission payout)
**Depends on:** 4.1 (exclusive lead claim), 4.2 (realtor wallet), 4.3 (conversion outcome), 5.2 (booking + convert→SOLD), 5.3 (public ЖК inquiry → NEW_BUILD lead with complexId/unitId)

---

## 1. Goal

Close the loop's payment leg: let the realtor who brought a buyer **fixate** that buyer onto a developer's unit (attribution with a uniqueness check — C6), and when the unit's booking **converts to SOLD**, credit the fixated realtor a **commission immediately** to their wallet (C7/C8). This is the bridge that makes the developer's inventory pay realtors, joining Product A (lead pipeline) to Product B (developer CRM). Per the platform spec, fixation "settles whose client this is" and commission pays "immediately, without waiting for the developer."

## 2. Scope decisions (locked with product owner)

| Fork                | Decision                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fixation model**  | **Realtor-initiated from their claimed lead + phone-match at convert.** A realtor fixates their CLAIMED NEW_BUILD lead (which already carries unitId + the buyer) onto the unit; uniqueness = one ACTIVE fixation per (unit, buyer-phone). At convert→SOLD the booking's client phone is matched to an ACTIVE fixation → that realtor is credited. No new developer attribution UI required. |
| **Commission rate** | **Per-Complex default % + per-Unit override**, stored as basis points (bps). Realtor sees the per-unit value on their lead (C7 "per unit").                                                                                                                                                                                                                                                  |
| **Payout timing**   | **Immediate wallet credit at convert→SOLD** (platform-floats). New `WalletTxType.COMMISSION`. Developer-side billing/escrow/reconciliation deferred to Phase 6. Satisfies C8 "immediate, without waiting for the developer."                                                                                                                                                                 |
| **C7 showcase**     | **Minimal** — commission is visible to the realtor on their own claimed NEW_BUILD lead (apps/agent), never to the buyer. A full browsable commission-filtered developer-inventory showcase is deferred.                                                                                                                                                                                      |

## 3. Design rulings (load-bearing — confirm at review)

1. **Uniqueness is enforced in-code, not by a DB partial-unique index.** Prisma cannot express a partial (WHERE-filtered) unique index, and a plain `@@unique([unitId, buyerPhone])` would forbid re-fixation after a cancel. So "one ACTIVE fixation per (unitId, buyerPhone)" is enforced with the 4.1 exclusive-claim idiom — `await tx.$queryRaw\`SELECT 1 FROM "Unit" WHERE id = ${unitId} FOR UPDATE\`` inside a `$transaction`(mirroring`leads.service.ts:97`and`booking.service.book()`), then an in-tx check for a competing ACTIVE fixation → **409** for the loser (first-writer-wins).
2. **Commission fires only at `booking.act()` convert, and convert must be made atomic first.** Today the convert guard is a **pre-transaction status read** (`bookingOwnedOrThrow` at `booking.service.ts:92`, before the `$transaction` at :93) with **no row lock and no in-tx re-check** — harmless for the plain status flip (both racers just write CONVERTED) but it would **double-credit** a wallet under two concurrent `act(convert)` calls. So 5.4 changes convert to flip atomically — `tx.booking.updateMany({ where:{ id, status:'ACTIVE' }, data:{ status:'CONVERTED' } })` — and performs the fixation lookup + credit **only when `count === 1`** (a concurrent/re-fired convert gets `count === 0` → no credit). cancel/extend/expire never pay. Also `bookingOwnedOrThrow` selects only `status/unitId/orgId`, so the convert branch must **load `unit.priceSom` + `unit.commissionBps` (+ the complex's) inside the tx** before computing.
3. **Attribution is by phone match, not a hard Booking→User link.** The 5.2 booking client stays free-text; at convert we match a **canonicalized** `booking.clientPhone` to an ACTIVE fixation's `buyerPhone`. This satisfies C6's "whose client" attribution without unifying the two identities (a hard `Booking.userId` FK is deferred). `User.phone` is stored canonical (`/^998\d{9}$/`, E.164 without the `+`), but `booking.clientPhone` is **unvalidated free text** — so a shared `canonicalizePhone()` helper must normalize BOTH sides to `998XXXXXXXXX` (strip `+`/spaces/dashes, coerce a local leading `0` and bare 9-digit forms to the `998…` country form), not merely strip non-digits. `buyerPhone` is stored canonical on the Fixation. Phones that don't canonicalize to a match simply don't attribute (no credit); the CRM shows a "this unit has an active fixation" hint so the developer books with the matching phone.
4. **Commission amount is snapshotted at convert** from the authoritative SOLD unit price: `effectiveBps = unit.commissionBps ?? complex.commissionBps ?? 0`; `commissionSom = (unit.priceSom ?? 0n) * BigInt(effectiveBps) / 10000n` (BigInt division truncates toward zero — the documented rounding rule; no BigInt rounding helper exists). `unit.priceSom` is **nullable** — a null price yields `0` commission (fixation still CONVERTS, no credit). The realtor's lead shows an **estimated** commission (same formula on the current price) before convert; the Fixation stores the final `commissionSom` + `commissionBps` when it converts.
5. **The platform floats the payout.** There is no developer/org wallet today; building escrow/liability is Phase 6. 5.4 credits the realtor's wallet at convert and records it in the wallet ledger; developer-side settlement is out of scope. A zero effective rate → the fixation still CONVERTS but no wallet credit is written.
6. **Additive migration only** — new enum + new table + nullable columns + a new `WalletTxType` value (`ALTER TYPE … ADD VALUE`, the proven 5.1 idiom); no existing column altered.

## 4. Non-goals (deferred)

- **Full C7 browsable/commission-filtered realtor showcase** of developer inventory (a sizable new surface) — deferred; 5.4 surfaces commission only on the realtor's own claimed lead.
- **Developer/org wallet, escrow, billing, invoicing, reconciliation** — Phase 6 (finance). The platform floats commission.
- **Commission clawback** on booking cancel-after-convert, dispute, or refund (refund/dispute was already deferred in 4.3).
- **Fixation time-boxing / expiry cron** — a fixation stays ACTIVE until CONVERTED or CANCELLED (per (unit, buyer) scope, so it only blocks re-fixating the _same_ buyer on the _same_ unit).
- **Hard Booking→User/lead identity unification** — attribution is by phone match; a `Booking.userId` FK is deferred.
- **Two-sided fixation confirmation** (developer accepts/rejects) — realtor-initiated only.
- **Contract model** — Phase 6.

## 5. Architecture & data flow

```
Realtor (apps/agent)                        Developer (apps/crm)
────────────────────                        ────────────────────
1. claims a NEW_BUILD lead (4.1/4.2/5.3)    0. sets commission %: Complex.commissionBps
   → lead has claimedById + unitId + buyer      (+ optional Unit.commissionBps override)
2. FIXATE the lead onto its unit  ─────────►  (shaxmatka shows "unit has active fixation")
   POST /api/leads/:id/fixate
   in-tx: unit FOR UPDATE, uniqueness check
   → Fixation{realtorId,unitId,leadId,buyerPhone,ACTIVE, est. commission}
                                            3. books the unit for that buyer (5.2)
                                            4. convert → SOLD  (booking.act, in $transaction):
                                               match normalize(clientPhone) → ACTIVE Fixation on unitId
                                               ├─ compute commissionSom = priceSom * effBps / 10000
                                               ├─ ensureWallet(realtor) + COMMISSION credit  ◄── C8 immediate
                                               ├─ Fixation → CONVERTED (+ commissionSom)
                                               └─ Booking.fixationId set (audit)
5. sees commission credited in wallet + lead ◄──────────────────────────────────────────────┘
```

Reuse: the 4.1 exclusive-claim `FOR UPDATE` idiom (fixation uniqueness), the 4.2 wallet-credit-in-one-tx idiom (commission payout), the 5.2 convert `$transaction` (the trigger seam), the developer org-scoping chain (commission config authz).

## 6. Data model (Prisma — additive)

```prisma
enum FixationStatus {
  ACTIVE
  CONVERTED
  CANCELLED
}

model Fixation {
  id                String         @id @default(cuid())
  realtorId         String
  realtor           User           @relation("RealtorFixations", fields: [realtorId], references: [id], onDelete: Cascade)
  unitId            String
  unit              Unit           @relation(fields: [unitId], references: [id], onDelete: Cascade)
  propertyRequestId String         @unique          // one fixation per claimed lead
  propertyRequest   PropertyRequest @relation(fields: [propertyRequestId], references: [id], onDelete: Cascade)
  buyerPhone        String                          // digits-only normalized, denormalized for the convert match
  status            FixationStatus @default(ACTIVE)
  commissionBps     Int                             // effective rate snapshot at fixation
  commissionSom     BigInt?                         // final commission, set at convert
  createdAt         DateTime       @default(now())
  convertedAt       DateTime?
  cancelledAt       DateTime?
  bookings          Booking[]                        // set at convert (audit)

  @@index([unitId, status])       // the uniqueness lookup + "unit has active fixation"
  @@index([realtorId, status])    // the realtor's fixation list
}
```

Additive changes to existing models:

- `Complex.commissionBps Int?` — org default commission rate (basis points; null = 0).
- `Unit.commissionBps Int?` — per-unit override (null = inherit complex).
- `Booking.fixationId String?` + `fixation Fixation? @relation(fields:[fixationId], references:[id], onDelete: SetNull)` — set at convert for audit.
- `User.fixations Fixation[] @relation("RealtorFixations")` back-relation.
- `Unit.fixations Fixation[]` back-relation.
- `PropertyRequest.fixation Fixation?` back-relation.
- `enum WalletTxType += COMMISSION`.
- `WalletTransaction.fixationId String?` — a **new** nullable reference column for a COMMISSION row. `WalletTransaction` today has only a per-purpose `leadId String?` (for LEAD_CLAIM), **not** a generic reference, so do not overload `leadId` — add `fixationId`. (`WalletService` also has no tx-accepting credit path — `topup` opens its own `$transaction`; §8c adds a `credit(tx, …)` method mirroring `debitForClaim`.)

**Migration** `<ts>_phase_5_4_fixation_commission`: `CREATE TYPE FixationStatus`, `CREATE TABLE Fixation` (+ 2 indexes + 3 FKs), `ALTER TABLE Complex/Unit ADD COLUMN commissionBps`, `ALTER TABLE Booking ADD COLUMN fixationId` + FK, `ALTER TABLE WalletTransaction ADD COLUMN fixationId`, `ALTER TYPE WalletTxType ADD VALUE 'COMMISSION'`. No DROP, no existing column changed. (Postgres restriction: a newly-added enum value cannot be _used_ in the same migration that adds it — the migration only ADDs `COMMISSION`; no COMMISSION row is written until runtime, so this is fine.)

## 7. Shared DTOs (`packages/shared/src/schemas.ts`)

- `FixationStatusSchema = z.enum(['ACTIVE','CONVERTED','CANCELLED'])`.
- `FixationSchema` — `{ id, unitId, propertyRequestId, buyerPhone, status, commissionBps, commissionSom (string|null), createdAt, convertedAt(string|null) }`.
- `FixateInputSchema` — `{ unitId: z.string().optional() }` (required only when the lead has no unitId).
- **Extend `LeadSchema` + `toLead`** (the map's flagged gap): add `complexId (string|null)`, `unitId (string|null)`, a `unitInfo` object for NEW_BUILD leads (`{ number, complexName, priceSom (string|null), commissionSom (string|null) }` — the estimated commission), and `fixation: FixationSchema.nullable()` (the realtor's fixation on this lead, if any).
- Extend the CRM `ComplexSchema`/`ComplexDetailSchema` with `commissionBps (number|null)` and `UnitSchema` with `commissionBps (number|null)` + `hasActiveFixation (boolean)` (the shaxmatka indicator).
- `WalletTxTypeSchema += 'COMMISSION'`; the wallet-transaction DTO gains the nullable `fixationId`.
- Money stays BigInt-as-string (`commissionSom`).

## 8. API surface

### 8a. Realtor-side (`@Controller('leads')`, `JwtGuard + RealtorGuard`)

- `POST /api/leads/:id/fixate` — body `FixateInputSchema`. Asserts: lead `claimedById === caller`, `status === CLAIMED`, `type === NEW_BUILD`, has a `complexId`. Resolves `unitId` (from the lead, or the body — validated to belong to `lead.complexId`). Normalizes `buyerPhone` from `lead.author.phone`. In a `$transaction`: `SELECT … FOR UPDATE` the unit, reject (409 `"Bu xonadon uchun mijoz allaqachon fiksatsiya qilingan"`) if another ACTIVE fixation exists for `(unitId, buyerPhone)`; create the Fixation ACTIVE with `commissionBps` = effective rate and an estimated `commissionSom` snapshot. Returns the Fixation.
- `DELETE /api/leads/:id/fixate` — the realtor cancels their own ACTIVE fixation on that lead (→ CANCELLED). 404 if none; only the owning realtor.
- `GET /api/leads/mine` (existing) — now returns leads carrying `unitInfo` + `fixation` (via the extended `toLead`).

### 8b. Developer-side commission config (`@Controller('crm')`, `DeveloperGuard`, org-scoped)

- `PATCH /api/crm/complexes/:id` — extend to accept `commissionBps` (partial-update idiom, org-scoped, foreign → 404).
- `PATCH /api/crm/units/:id` — extend to accept `commissionBps` (override; null clears).
- The `UnitSchema` returned by the CRM reads now include `commissionBps` + `hasActiveFixation` (computed: an ACTIVE Fixation exists for the unit).

### 8c. Commission at convert (inside `booking.service.act()` convert)

No new endpoint — the existing `PATCH /api/crm/bookings/:id` `{action:'convert'}` gains the payout. The convert branch is rewritten to be atomic (ruling 2): inside the `$transaction`, `updateMany({ where:{ id, status:'ACTIVE' }, data:{ status:'CONVERTED' } })`; proceed only when `count === 1`; flip the Unit → SOLD; then load `unit.priceSom` + `unit.commissionBps` + the complex's `commissionBps`; find an ACTIVE Fixation where `unitId === booking.unitId` AND `buyerPhone === canonicalizePhone(booking.clientPhone)`. If found and the computed `commissionSom > 0`: `ensureWallet(fixation.realtorId)`, then credit via a **new tx-accepting** `WalletService.credit(tx, realtorId, commissionSom, { fixationId })` (mirrors `debitForClaim`'s `(tx, …)` signature but increments — `topup` opens its own tx and cannot be reused; the credit does an atomic `balanceSom: { increment }` + a `WalletTransaction{ type:'COMMISSION', amountSom, fixationId }`). Set Fixation → CONVERTED (`commissionSom`, `convertedAt`) and `Booking.fixationId`. All in the one tx (atomic with the SOLD flip). No `count===1` / no fixation / zero rate → convert proceeds, no credit.

## 9. Realtor cabinet (`apps/agent`)

- `features/leads/use-leads.ts` — add `useFixate(leadId)` (POST) + `useUnfixate(leadId)` (DELETE), invalidating the leads query.
- `pages/leads` `LeadCard` — for a CLAIMED NEW_BUILD lead: show the target unit (`unitInfo`: complex name + unit number + price), the **estimated commission** (`unitInfo.commissionSom`), and a **"Fiksatsiya qilish"** button when not yet fixated; when fixated, a status badge (`Fiksatsiya qilingan` / on convert `Komissiya olindi — <som>`). Commission is realtor-facing only.

## 10. Developer CRM (`apps/crm`)

- **Commission config:** on complex-detail, a commission-% input → `Complex.commissionBps` (shown/entered as a percent, stored as bps). On the building-detail / shaxmatka unit editor, an optional per-unit commission-% override → `Unit.commissionBps`.
- **Fixation indicator:** the shaxmatka cell / unit row shows a small badge when `hasActiveFixation` — so the developer knows a realtor has fixated a client on that unit and books with the matching phone. Read-only.
- `features/developer/use-developer.ts` — the existing update hooks carry `commissionBps`; no new endpoint.

## 11. Testing

- Browser smoke: realtor fixates a claimed lead; developer sets commission % + converts a matching booking; realtor sees the credit.

## 12. Open questions resolved → rulings map

| Map open question                           | Resolution                                                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Who initiates fixation?                     | Realtor-initiated from their claimed lead; phone-match at convert (scope decision 1).                         |
| What does fixation bind + uniqueness scope? | realtor + lead + unit; unique per (unit, buyer-phone), in-code (ruling 1).                                    |
| Buyer identity unification?                 | Phone match, no hard Booking→User link (ruling 3 / non-goal).                                                 |
| Commission model + storage?                 | Complex.commissionBps default + Unit.commissionBps override (bps) (scope decision 2).                         |
| C7 showcase in scope?                       | No — minimal realtor-lead visibility only (scope decision 4).                                                 |
| Payout timing + funding?                    | Immediate wallet credit at convert, platform-floats (scope decision 3 / ruling 4).                            |
| Conflict rules?                             | First-writer-wins on (unit, buyer-phone) via FOR UPDATE; no-fixation convert pays nothing; clawback deferred. |
| Gating/lifecycle?                           | Fixate = RealtorGuard; config = DeveloperGuard; convert = DeveloperGuard; no expiry cron.                     |

## 13. Rollout

Single additive migration; no env changes; no new dependency. Commission is invisible until a developer sets a rate and a realtor fixates, so existing flows are unaffected. `WalletTxType.COMMISSION` credits are platform-funded and recorded in the realtor wallet ledger; developer-side settlement lands in Phase 6.
