# Phase 4.1 — Lead foundation design

_Date: 2026-08-28 · Branch: `claude/phase-4.1-lead-foundation` · Base: master `aa600a7` · Part of: Phase 4 (Product C — Lead market) · Depends on: 2.2 (PropertyRequest / "Qidiryapman" board), 3.1 (RealtorGuard/Subscription)_

## 1. Goal

Turn the existing free "Qidiryapman" buyer-request board into the foundation of a **lead market**:
every buyer request becomes a **Lead** with an auto-computed **score** and a **score-tiered price**,
shown to realtors in a **lead feed**, and claimable **exclusively** — the first realtor to claim a
lead gets the buyer's contact and the lead closes to everyone else. This replaces today's
free-for-all reveal with an exclusive, scored, priced claim. **Payment** (a wallet that the claim
debits) is Phase **4.2**; **conversion tracking** is **4.3**; the full cross-CRM fixation (C6) is
Phase 5. This sub-phase closes the loop's shape without yet charging money.

## 2. Scope

1. **Evolve `PropertyRequest` into the Lead** (additive columns + status values): `score`,
   `priceSom`, `claimedById`, `claimedAt`, and `RequestStatus` gains `CLAIMED`/`EXPIRED`.
2. **Auto-scoring** (deterministic, server-side, 0–100) computed on create/update.
3. **Score-tiered pricing** — the score maps to one of three `priceSom` tiers (the price a realtor
   will pay in 4.2), stored on the lead and displayed in the feed.
4. **Richer buyer capture** — evolve the create form into a fuller intake (more complete → higher score).
5. **Realtor lead feed + exclusive claim** — `GET /api/leads` (OPEN, RealtorGuard) sorted by score;
   `POST /api/leads/:id/claim` (RealtorGuard) atomically claims a lead exclusively and returns the
   buyer's contact. A claimed lead leaves the feed.
6. **Shared `Lead` DTO** + the web/agent surfaces (the realtor feed + the buyer's "my leads" view).

### Non-goals

- **Wallet / balance / payment** — Phase 4.2. In 4.1 the claim is **free** (no balance check); the
  price is computed and displayed but not charged.
- **Conversion tracking / lead outcome** — Phase 4.3.
- **Full fixation with cross-CRM uniqueness (C6)** — Phase 5 (developer CRM). The exclusive claim is
  the 4.1-level uniqueness (one realtor per lead).
- **Renaming the Prisma model/table** — the model stays `PropertyRequest` internally (additive
  migration, no table rename); the concept is exposed as **`Lead`** in the DTO/API/UI. A later
  cosmetic `@@map` rename is out of scope.
- Marketplace listing display — untouched.

## 3. Data model (Prisma)

Additive changes to the existing `PropertyRequest` (2.2) — no rename, no other model changed:

```prisma
model PropertyRequest {
  // ... existing: id, authorId, author, deal, type?, district?, roomsMin?, priceMaxSom?, areaMinM2?, note?, status, createdAt
  score       Int       @default(0)     // 0..100, auto-computed
  priceSom    BigInt    @default(0)     // lead price (charged in 4.2), from the score tier
  claimedById String?                    // the realtor (User) who claimed it exclusively
  claimedBy   User?     @relation("ClaimedLeads", fields: [claimedById], references: [id], onDelete: SetNull)
  claimedAt   DateTime?
}

enum RequestStatus {
  OPEN
  CLOSED      // (existing)
  CLAIMED     // NEW — exclusively claimed by a realtor
  EXPIRED     // NEW — aged out (reserved; auto-expiry is a later concern)
}
```

`User` gains the back-relation `claimedLeads PropertyRequest[] @relation("ClaimedLeads")`. Migration
is additive (ADD COLUMN ×3 + 2 enum values + the FK). `score`/`priceSom` default 0 for existing
rows; they are recomputed the next time the lead is created/updated, and a one-time backfill in the
Lead service recomputes existing OPEN rows on first list (or a migration data step) — the few seed
requests are non-critical, so a lazy recompute-on-write is acceptable; the plan pins which.

## 4. Scoring + pricing

**Score `computeLeadScore(lead): number`** — deterministic, 0–100, server-side (a pure function so
it is unit-testable without the DB):

- **Completeness (0–50):** +10 for each present optional signal — `district`, `type`, `roomsMin`,
  `areaMinM2`, `note` (5 × 10). A bare request scores low; a fully-specified one scores 50 here.
- **Budget (0–30):** `priceMaxSom` scaled — `min(30, round(priceMaxSom / BUDGET_STEP))` where
  `BUDGET_STEP` makes a ~1.5 bln so'm budget hit the cap. Null budget → 0.
- **Recency (0–20):** `max(0, 20 - daysSinceCreated * RECENCY_DECAY)` — a fresh lead scores full,
  decaying to 0 over ~20 days. (Recency is computed at read/score time from `createdAt`.)
- Total clamped to `[0, 100]`.

The plan pins the exact constants (`BUDGET_STEP`, `RECENCY_DECAY`); the shape above is binding.

**Price `priceForScore(score): bigint`** — three tiers (round UZS figures, ~ the $2–4 range C16
cites):

| Score   | Tier | `priceSom` |
| ------- | ---- | ---------- |
| `< 40`  | LOW  | `20000`    |
| `40–70` | MID  | `35000`    |
| `> 70`  | HIGH | `50000`    |

Both are recomputed together whenever a lead is created or its fields change; `priceSom` is stored
(so the price a realtor sees is stable at claim time in 4.2). Recency affects the _score display_
and re-scoring on write, but a lead's stored `priceSom` is set at write time — a later re-score job
is a fast-follow, not 4.1.

## 5. Buyer capture

Evolve the existing create flow (`POST /api/requests` → the `/requests/new` form) into a fuller
**Lead intake**: the same fields (deal, type, district, roomsMin, priceMaxSom, areaMinM2, note) with
clearer prompts encouraging completeness (a short helper: "To'liqroq → ko'proq rieltor ko'radi").
On create, the server computes `score` + `priceSom` and stores them; `status = OPEN`. No new required
fields (completeness is rewarded, not forced). The buyer stays `author`.

## 6. Realtor lead feed + exclusive claim

- **`GET /api/leads`** (RealtorGuard — role REALTOR + active subscription): OPEN leads only, ordered
  by `score` desc then `createdAt` desc, returned as `Lead[]` (see §7). The buyer's contact is
  **masked** (like a listing) until claimed.
- **`POST /api/leads/:id/claim`** (RealtorGuard): **atomically** claim the lead. In a transaction
  with a row lock on the lead (`SELECT ... FOR UPDATE`), verify `status === 'OPEN'`; if already
  claimed → `409 Conflict` ("Bu lead allaqachon olingan"); else set `status = 'CLAIMED'`,
  `claimedById = realtorId`, `claimedAt = now`, and **return the buyer's contact**
  (`{ phone, name }` of the `author`). Also record a `ContactReveal` (requestId = leadId,
  userId = realtorId) for continuity with the existing reveal analytics. The claim is **free in 4.1**
  (no balance check — 4.2 adds the debit here). **Self-claim is blocked**: if `author.id === realtorId`
  → `400` ("O'z lead'ingizni ololmaysiz"), mirroring the 3.3b self-review guard.
- **`GET /api/leads/:id`** (RealtorGuard): a single lead's detail (masked contact if OPEN; full if
  claimed by the caller). Reuse for the claim-confirmation view.
- **`GET /api/leads/mine`** (RealtorGuard): the leads THIS realtor has claimed, contact revealed — a
  `Lead[]`, newest-claimed first. (The buyer's own posted leads stay under the existing
  `/api/my/requests`, extended to show claimed status.)

The exclusive claim (one `claimedById`, OPEN→CLAIMED under a row lock) IS the 4.1 fixation — no lead
is ever handed to two realtors.

## 7. DTOs (shared)

- **`LeadSchema`** (the realtor-facing lead) = `{ id, deal, type, district, roomsMin, priceMaxSom,
areaMinM2, note, score, priceSom, status, createdAt, contact: { name, phoneMasked } | { name, phone } }`
  — the contact is **masked** for an OPEN lead in the feed and **revealed** in a claim response / the
  claimer's view. Represent this as `phoneMasked: string` always, plus `phone: string | null` (null
  until claimed by the caller) — mirrors the listing seller pattern.
- **`LeadCreateSchema`** — the buyer intake body (the existing PropertyRequest create shape;
  server computes score/price, so they are NOT in the input).
- The buyer's "my leads" row (`MyLeadSchema`) = the lead + its `status` + (if CLAIMED) that a realtor
  has taken it (no realtor PII to the buyer beyond "olingan").

## 8. Modules & wiring

- `apps/api`: evolve `apps/api/src/requests/` into the lead module (or add a `leads` module reusing
  the same service) — a `LeadService` with `computeLeadScore`/`priceForScore` (pure helpers,
  unit-testable), `create` (compute+store), `feed` (OPEN, scored), `claim` (transactional exclusive),
  `mine`. Controllers: the realtor feed/claim (`@Controller('leads')`, RealtorGuard) + the buyer
  create/my-leads (JwtGuard). The existing `POST /api/requests/:id/contact` free reveal is **cut over**
  to the claim (no parallel alias) — the realtor path is the new claim; the buyer create/my-requests
  endpoints stay and gain the score/price/claimed-status fields.
- `apps/web`: the realtor **lead feed** — **evolve the existing `/requests` board in place** (add
  score + price, replace the reveal button with claim). The buyer's fuller create + a claimed-status
  badge on "my requests". Reuse the existing request UI; no cabinet feed in 4.1 (the board already
  lives in `apps/web` where realtors browse — moving it to `apps/agent` is out of scope).
- Shared Zod DTOs (`Lead`, `LeadCreate`, `MyLead`).

## 9. Constraints

- Uzbek user-facing copy; **English** identifiers/comments.
- **No new test files** unless the pure scoring/pricing helpers warrant a tiny data-driven check —
  default to the project rule (no new tests; verify via lint/typecheck/build/scratch/browser). The
  existing suite stays green.
- **Additive migration** (ADD COLUMN + enum values + FK); no table rename, no destructive op.
- **No new env var.**
- The lead feed + claim require **RealtorGuard** (role REALTOR + active subscription); the buyer
  create requires only auth (JwtGuard). The claim is **exclusive + transactional** (row-locked
  OPEN→CLAIMED) so a lead can never be double-claimed.
- **Do not break** the marketplace or any Phase 1–3 flow; the "Qidiryapman"→Lead change is confined
  to the requests/leads module + its UI.

## 10. Verification

- Automated: `yarn lint`/`typecheck`/`build` (4 workspaces); the existing suite green; additive migration.
- API (compiled-JS scratch): a buyer creates a lead with varying completeness/budget → `score`
  reflects the formula and `priceSom` the tier; a realtor `GET /api/leads` sees OPEN leads
  score-ordered with masked contact; `claim` on an OPEN lead → CLAIMED + returns the buyer contact +
  a ContactReveal row; a **second** realtor claiming the same lead → 409 (exclusive); the claimed
  lead no longer appears in the OPEN feed; a non-realtor (USER) hitting the feed/claim → 403.
- Web/agent (browser smoke): a buyer posts a fuller request → it shows a score + price in the realtor
  feed → a realtor claims it → the buyer contact reveals and the lead leaves the feed → a second
  realtor sees it gone / 409.

## 11. Risks

- **Double-claim race** — two realtors claiming simultaneously must not both succeed. The claim is a
  row-locked (`SELECT ... FOR UPDATE`) OPEN→CLAIMED transition (the same lock discipline 3.3b used
  for the rating aggregate). Highest-risk item; the scratch must prove concurrent claims yield exactly
  one winner + one 409.
- **Score/price backfill** — existing rows default to 0/0; decide (plan) lazy recompute-on-write vs a
  migration data step. Low stakes (few seed rows), but the feed ordering looks odd if legacy rows sit
  at score 0 — recompute existing OPEN rows once.
- **Behavior change** — the free reveal becomes an exclusive claim; the buyer now gets ONE realtor,
  not many. Intended (quality/closed-loop), but it is a visible change to the existing `/requests`
  flow — the plan must migrate the UI copy accordingly.
- **Contact masking** — the buyer's phone must be masked in the OPEN feed and revealed only to the
  claimer (mirror the listing `maskPhone` seam); a leak of an unclaimed buyer's number is a defect.
