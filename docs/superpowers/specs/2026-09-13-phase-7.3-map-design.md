# Phase 7.3 — Map (clustered price pins for listings + complexes) (design)

**Status:** approved design, ready for planning
**Branch:** `claude/phase-7.3-map` (off master `86582fc`, the Phase 7.2 completion / 7.2d merge)
**Roadmap:** Phase 7 (Growth layer, last roadmap phase) — 7.1 mortgage ✓ → 7.2 AI assistant ✓ → **7.3 map** → 7.4 journal.

---

## 1. Goal

Let a buyer browse the marketplace **on a map**: `/search` gains a list ↔ map toggle whose map shows
**clustered price pins** for both marketplace **listings** and published developer **complexes** (the A10
"map with clustered price pins" vision). A listing's detail page shows a **"Xaritada"** pin, and a
listing owner **drops a pin** on the create/edit wizard so their listing appears on the map. Coordinates
are optional everywhere — a row without a pin simply stays off the map (and in the list).

## 2. Scope

**In scope (7.3):**

- **Data:** add `latitude` / `longitude` (nullable) to the marketplace `Listing`; expose them on the
  listing summary + detail DTOs and add them to the public complex **summary** DTO (the model + detail
  already carry them from 5.3). Seed Tashkent coordinates for the demo listings and any coordinate-less
  demo complexes.
- **Owner capture:** a map **pin-picker** in the listing create/edit wizard (`apps/web`) writing
  `latitude`/`longitude` into the draft (WGS84-validated).
- **Map view:** a list ↔ map toggle on `/search`; the map renders **clustered price pins** from the same
  client-filtered listings the list shows, plus published complexes fetched alongside; a pin opens a mini
  card that links to the detail page.
- **Detail map:** a "Xaritada" section on the listing detail page showing that listing's single pin
  (when it has coordinates).
- **Map library:** Leaflet (+ marker clustering) with keyless OSM tiles, client-only.

**Deferred (named, not built):**

- A **server-side map/search endpoint** — 7.3 reuses the existing feeds (§3.2); a bbox/viewport-query
  endpoint is only needed once the dataset outgrows returning all published rows.
- Routing / directions, draw-a-polygon-to-search, heatmaps, offline/vector tiles, address geocoding,
  3D / traffic layers, saved map views, a "search this area on move" refetch.
- A pin on the developer CRM complex editor beyond the coordinates it already stores, and the map on the
  complex detail page (7.3 puts complexes on the marketplace map + keeps the existing complex pages).
- Phase 7.4 (journal) and the rest of Phase 7.

## 3. Design decisions (resolved)

1. **Both sources on one map, clustered price pins.** Listings and published complexes render as price
   pins on a single Leaflet map; nearby pins cluster into a count bubble (Uysot/Yandex style). A pin's
   label is the price (listings) / "from" price (complexes), grouped ICU-free.
2. **Reuse the existing feeds — NO new backend search endpoint.** `/search` already fetches every
   published listing via `GET /api/objects` and filters **client-side** (`filterListings(data, criteria)`);
   the map view renders pins from that same filtered array, guaranteeing **map ↔ list parity** for free.
   Complexes come from the existing `GET /api/jk` (all published, verified-org) list. The only backend
   work is carrying coordinates on those payloads. (A server-side viewport query is deferred, §2.)
3. **Coordinates are nullable and optional.** `Listing.latitude/longitude` are `Float?`; a listing/complex
   without both coordinates is simply absent from the map (never a `(0,0)` "null-island" pin, never a
   crash). The owner pin is optional; the listing still publishes without one.
4. **Owner drops a pin; demo rows seeded.** The create/edit wizard gets a map-picker step (click the map →
   set the draft's lat/lng, WGS84-validated); the ~18 demo listings and coordinate-less demo complexes are
   seeded with real Tashkent coordinates so the map is populated on a fresh DB.
5. **Leaflet + OSM, keyless, client-only.** Leaflet core + `leaflet.markercluster` + OpenStreetMap raster
   tiles (no API key, attribution shown) — matching the project's "works without a key" ethos. Wrapped in
   a small React component via `useEffect`/`useRef` (NOT `react-leaflet`, to avoid a React-19 peer-version
   coupling). The map is **client-only** (SSR-safe): Leaflet touches `window`, so it initializes after
   mount and the map route/chunk is dynamically imported (code-split) so the ~50 KB library never enters
   the initial bundle.

## 4. Data model

Additive migration `phase_7_3_map_coords`:

- `Listing += latitude Float?` , `longitude Float?` (nullable, mirroring `Complex`). No other change; no
  removal; no index (the dataset is returned whole and filtered client-side).

`Complex.latitude/longitude` already exist (5.3) — unchanged.

## 5. Backend

### 5.1 Shared DTOs (`packages/shared/src/schemas.ts`)

- `ListingSummarySchema += latitude: z.number().nullable()` , `longitude: z.number().nullable()` (map
  pins for the search list/map).
- `ListingDetailSchema += latitude/longitude` (nullable) — for the detail "Xaritada".
- `PublicComplexSummarySchema += latitude/longitude` (nullable) — the list payload the map needs (the
  detail schema already has them).
- `ListingDraftSchema += latitude/longitude` — optional, WGS84-bounded, mirroring the Complex CRM upsert:
  `z.number().min(-90).max(90).optional()` / `.min(-180).max(180).optional()`.

### 5.2 Listing feed + mapper (`apps/api/src/listings/`)

- The `ListingSummary` / `ListingDetail` mappers select and pass through `latitude`/`longitude` (the
  `GET /api/objects` list + `GET /api/objects/:id` detail now carry coordinates). No new route.
- `updateDraft` accepts `latitude`/`longitude` on the draft patch (whitelist them alongside the other
  draft fields so the picker's values persist), applied as-is to the `Float?` columns.

### 5.3 Complex feed (`apps/api/src/complexes-public/`)

- `complexes-public.service.toSummary` selects + returns `latitude`/`longitude` so `GET /api/jk` list
  cards carry the pin (the include already loads the columns; the detail already returns them).

### 5.4 Seed (`apps/api/prisma/seed-data.ts` + `seed.ts`)

- Add plausible Tashkent `latitude`/`longitude` to each demo listing row (spread across their seeded
  districts) and to any demo complex missing them, so a fresh DB shows a populated map.

## 6. Frontend (`apps/web`, FSD)

- **Map primitive** (`shared/ui/map/` — a leaf UI unit): a client-only Leaflet wrapper —
  `<PinMap pins={…} onSelect={…} />` — that initializes Leaflet in `useEffect` (guards `window`),
  renders OSM tiles with attribution, clusters markers (`leaflet.markercluster`), and draws each pin as a
  price **divIcon** (grouped ICU-free money, null-guarded). Exposes a single-pin mode for the detail
  page. The Leaflet CSS is imported in this module. Dynamically imported so it is code-split.
- **`/search` list ↔ map toggle** (`pages/search`): a toggle switches the results area between the
  existing list and `<PinMap>`; the map takes the **already-filtered** listings (`matches`) plus published
  complexes (a `useQuery` on `GET /api/jk`), maps them to pins (dropping coordinate-less rows), and on
  pin-select shows a mini card linking to `/obj/:id` (listing) or the complex page. The toggle state is a
  local UI concern (may persist via the 7.x localStorage pattern).
- **Listing detail "Xaritada"** (`pages/listing`): when the listing has coordinates, a map section renders
  a single pin (the `<PinMap>` single-pin mode); absent coordinates, the section is omitted.
- **Create/edit pin-picker** (`pages/listing-create`, a `features/*` unit): a wizard step with a
  `<PinMap>` in pick mode — clicking the map sets a draft pin (lat/lng), `patch({latitude, longitude})`;
  optional (the wizard proceeds without one). Reuses the existing draft `patch()` flow.
- **FSD:** the map primitive lives in `shared/ui` (imported by pages/features); the picker is a feature;
  pages compose. UI copy Uzbek; identifiers/routes/comments English.

## 7. Rulings & invariants (load-bearing)

- **R1 — coordinates nullable, no null-island, no crash.** Every pin source drops rows lacking both
  coordinates; a listing/complex without a pin is absent from the map and never rendered at `(0,0)`. All
  coordinate reads are null-guarded.
- **R2 — reuse feeds, map ↔ list parity.** No new backend search endpoint; the map renders from the same
  client-filtered `matches` the list uses (+ the published-complex list). Changing a filter changes both
  identically.
- **R3 — WGS84 validation on write.** The draft (and any coordinate write) validates lat ∈ [−90, 90],
  lng ∈ [−180, 180] (400 on out-of-range) so a bad pin cannot poison the map.
- **R4 — additive, optional.** One additive migration (two nullable `Float` columns on `Listing`);
  nothing removed; the owner pin is optional and a listing publishes without it.
- **R5 — Leaflet + OSM, keyless, client-only, code-split, SSR-safe.** No `react-leaflet`; Leaflet
  initializes after mount (guards `window`); the map chunk is dynamically imported; OSM tiles need no key
  and show attribution; if tiles fail to load the container still renders and pins still position (no
  crash).
- **R6 — money on pins ICU-free.** Price labels use the shared `formatPriceSom` / `groupDigits`
  (BigInt-as-string, no `toLocaleString`), null-guarded.
- **R7 — FSD.** Map primitive in `shared/ui`; the picker is a feature; pages compose. `yarn lint` (FSD
  boundary) passes.
