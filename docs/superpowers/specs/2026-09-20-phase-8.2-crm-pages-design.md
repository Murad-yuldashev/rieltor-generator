# Phase 8.2 — CRM Cabinet Pages: Desktop Layout + Widgets + Seed — Design

**Status:** design (spec) — awaiting review
**Date:** 2026-09-20
**Branch:** `claude/phase-8.2-crm-pages` (off master `e9cf49c`)
**Spec context:** follows Phase 8.1 (cabinet desktop foundation). Phase 8.3 (agent pages) is the sibling that follows this.

## Goal

Give every CRM cabinet page (`@rieltor/crm`, developer/застройщик) a proper **desktop internal layout** and **richer widgets**, and add the **seed data** that populates them — so the cabinet reads as a real product on wide screens instead of a stretched single column of sparse cards.

Phase 8.1 unlocked the width and added the shell/header; each page body is currently a **bare single column** that merely stretches on desktop. Phase 8.2 lays that content out for wide screens (grids, main+sidebar splits, stat rows) and fills it with content.

## Architecture

Client SPA (React 19 + Vite 6 + React Router 7 + TanStack Query 5, FSD), served at `/crm`. All pages already fetch from existing CRM endpoints (DeveloperService, BookingService, ContractService, PaymentScheduleService, OrgWalletService, FinanceService). The desktop redesign is **presentational**: regroup existing data into responsive layouts and derive richer stats **client-side** from data the pages already load. Mirror `apps/web`'s established desktop idioms (card-grid tiers, `lg:grid-cols-[1fr_sidebar]` main+sticky-aside, stat-card rows).

**Critical enabler — seed.** `apps/api/prisma/seed.ts` currently seeds ZERO CRM-domain rows (Organization, Membership, Complex, ComplexImage, Building, Unit, Booking, Contract, OrgContractCounter, OrgWallet, OrgWalletTransaction, Fixation, PaymentSchedule, PaymentInstallment, Payment = all empty); it only seeds an agent, a moderator, articles, mortgage programs, and marketplace listings. A freshly-seeded developer cabinet is entirely empty, so every new widget renders 0/empty. Phase 8.2 therefore adds an additive, idempotent developer-CRM seed block — the shared prerequisite for all nine pages.

## Tech Stack

React 19, React Router 7, Tailwind v4 (`@theme` tokens, already blue), TanStack Query 5, FSD. **No new runtime dependencies.** Charts/meters are pure CSS (progress/composition bars), not a charting library.

## Global Constraints

- Code/identifiers/comments **English**; UI copy Uzbek (keep existing Uzbek strings).
- **No new test files.** Verify with root turbo `yarn turbo run typecheck lint build --filter=@rieltor/crm --filter=@rieltor/api` (never `yarn workspace <pkg> lint` — exit 127). Editing existing fixtures allowed.
- **Phone (<768) layout stays visually intact** — only `md`/`lg`/`desk` tiers are added; the existing single-column order is preserved (use the `contents` wrapper trick, as `apps/web` complex-page does, so DOM/tab order stays flat on phone).
- **Colours unchanged** — CRM blue (`--color-accent:#2563eb`, `--color-accent-soft:#eef4ff`) is already set; status tones use the existing `brand-green`/`brand-amber`/`brand-rose` tokens (as finance-page already does). Any visual bar/meter uses the CRM blue accent, never the web chart's `#6d28d9`.
- **Seed is additive + idempotent**: a self-contained `seedDeveloperCrm()` guarded by `if ((await prisma.organization.count()) === 0)` with FIXED string ids (`seed-org-1`, `seed-cx-1`, …) so re-runs never duplicate. Money as BigInt literals (`900_000_000n`) → DTOs stringify (BigInt-as-string end to end). No schema/migration change (all these models already exist).
- **No backend endpoint changes** (see Non-Goals) — every widget in this phase is built from data the pages already fetch, or from the new seed.
- `apps/web`, `apps/agent`, and all other apps are **not touched**.

## Non-Goals (this phase — explicitly deferred)

- **New/changed API endpoints or DTO fields.** The exploration flagged three high-value-but-backend-requiring widgets — org-wide unit inventory tile (`GET /api/crm/units/summary`), per-complex unit/price aggregates on `ComplexSchema`/`ComplexDetail` (`unitsTotal`/`unitsAvailable`/`priceFromSom`), and a finance monthly **trend** chart (`GET /api/crm/finance/timeseries`). All are DEFERRED to a later phase. Where a widget would need them, use an existing-data proxy (e.g. sold ≈ contracts count, booked ≈ active bookings) or omit that specific tile rather than fake or add backend.
- **Charting library / Recharts sparklines.** Use pure-CSS progress and composition bars this phase; a real balance/collections trend chart is deferred with its endpoint.
- **Agent pages** (Phase 8.3), and the `become-developer` onboarding page (standalone centred form, outside the shell — leave as-is).
- **Page behaviour/logic, mutations, guards, routing** — unchanged; this is layout + derived widgets + seed only.

## Section 10 — Seed: `seedDeveloperCrm()` (the shared enabler)

New `apps/api/prisma/seed-crm.ts` (sibling of `seed-data.ts`), invoked from `seed.ts` `main()` after listings, guarded by `if ((await prisma.organization.count()) === 0)`; all rows use fixed string ids (idempotent). Money as BigInt literals. Chain (matching the services' create shapes):

- **Developer user**: `SEED_DEVELOPER_PHONE = '998900000001'` (mirrors `SEED_MODERATOR_PHONE`), upsert by phone, `role: 'DEVELOPER'` (MUST be set explicitly or `DeveloperGuard` 403s). Optional 2nd user (`998900000002`) for a 2-row members list. **Document the login phone** so a tester can OTP in (devCode) and land in the populated cabinet.
- **Organization** `seed-org-1` (`verified: true`, `verifiedAt`/`verificationRequestedAt` past) + **Membership** (OWNER for the developer user; optional MANAGER for the 2nd). Membership is what `DeveloperService.orgIdOf` resolves — without it the guard 403s.
- **Complexes** (4, `seed-cx-1..4`): mixed `status` (PLANNED / UNDER_CONSTRUCTION×2 / DONE), mixed `publishStatus` (2 PUBLISHED with slug+publishedAt, 2 DRAFT), varied districts (≥4, so facet chips have options), Tashkent lat/lng (reuse listing coords), `commissionBps` on two; each with ≥1 cover ComplexImage via the existing `processImage`/placeholder pipeline (≥1 complex with 3–6 gallery images).
- **Buildings** (per complex 1–3, e.g. "A blok", `floors` 9–16) + **Units** (~4–8 per floor): mixed status (~60% AVAILABLE / 25% BOOKED / 15% SOLD), varied rooms(1–4)/areaM2/`priceSom`, a few `commissionBps` overrides. **NOTE: `hasActiveFixation` is NOT a Unit column** (it is a DTO field the service derives from ACTIVE `Fixation` rows) — do not set it on `unit.create`; seeding a real Fixation needs an out-of-scope realtor→PropertyRequest→Fixation chain, so it is skipped this phase (the building-detail "Fiksatsiya" column renders empty). Ensure ≥1 complex fully satisfies the publish gate (verified org + ≥1 image + ≥1 priced available unit) and ≥1 DRAFT that does not (to demo the gate-hint).
- **Bookings** (~10–14 across all 4 statuses: several ACTIVE incl. 1–2 with `holdUntil` within 3 days, a couple EXPIRED, 1–2 CANCELLED with `cancelReason`, several CONVERTED); BOOKED units carry an ACTIVE Booking (clientName/clientPhone/holdUntil) so `activeBooking` populates.
- **Contracts** (~6–8 across ACTIVE + CANCELLED). **Each Contract wraps its OWN distinct CONVERTED Booking** — `bookingId` is a required `@unique` 1:1 FK, so create a dedicated CONVERTED Booking per contract (CONVERTED count ≥ contract count) and set the required snapshots `buyerName`/`buyerPhone` + `orgId` + `unitId` (SOLD unit) + `number` (via `OrgContractCounter`); every Booking also needs the required `createdById`. Some `agreedAmount`+`signedAt`, some null; CANCELLED with `cancelReason`+`cancelledAt`. ≥2 signed ACTIVE with a **PaymentSchedule** (down payment + installments) mixing PAID/PENDING incl. ≥1 PENDING **overdue** (past `dueDate`) so `debtorCount`/`overdueSom` populate; ≥1 ACTIVE unsigned with NO schedule (demo sign + create form).
- **OrgWallet** (`balanceSom` non-zero) + **OrgWalletTransactions** (a couple TOPUP 100k/300k/500k, several COMMISSION_DEBIT with `fixationId` across recent dates, ≥1 COMMISSION_REFUND); include a case that drives the balance negative to exercise the rose "Qarz" state.

Follow `seed-data.ts` `SEED_LISTINGS` as the fixture template (fixed ids, BigInt so'm, districts/geo). No new endpoints — every page reads from services that already exist.
