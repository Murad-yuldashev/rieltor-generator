# Phase 8.3 — Agent Cabinet Pages: Desktop Layout + Widgets + Seed — Design

**Status:** design (spec) — awaiting review
**Date:** 2026-09-21
**Branch:** `claude/phase-8.3-agent-pages` (off master `845a442`)
**Spec context:** the sibling that follows Phase 8.2 (CRM pages). Same treatment, applied to the `@rieltor/agent` (realtor/rieltor) cabinet. Phase 8.1 gave the shell/header + teal accent; 8.2 laid out and seeded the developer CRM. 8.3 finishes the roadmap by doing the same for the realtor cabinet.

## Goal

Give every agent cabinet page (`@rieltor/agent`, the realtor cabinet) a proper **desktop internal layout** and **richer widgets**, and add the **seed data** that populates them — so the realtor cabinet reads as a real product on wide screens instead of a stretched single column of sparse cards, matching what Phase 8.2 just delivered for the developer CRM.

Phase 8.1 unlocked the width and added the shell/header (teal accent); each page body is currently a **bare single column** that merely stretches on desktop. Phase 8.3 lays that content out for wide screens (card grids, main+sidebar splits, stat rows) and fills it with content.

## Architecture

Client SPA (React 19 + Vite 6 + React Router 7 + TanStack Query 5, FSD), served at `/agent`. All pages already fetch from existing agent endpoints (LeadsService, CollectionsService, PresentationsService, NotesService, ProfileService, WalletService, SubscriptionService, plus the public `GET /api/objects` marketplace + `GET /api/r/:slug` microsite). The desktop redesign is **presentational**: regroup existing data into responsive layouts and derive richer stats **client-side** from data the pages already load. Mirror the desktop idioms **just merged in Phase 8.2's `apps/crm/src/pages/*`** (card-grid tiers, `lg:grid-cols-[1fr_sidebar]` main+sticky-aside, `StatTile` rows) and `apps/web`'s originals.

**Critical enabler — seed.** `apps/api/prisma/seed.ts` currently seeds **zero realtor-domain rows**: no `REALTOR` User, no `Subscription`, no `PropertyRequest`/`Fixation`, no `Collection`/`CollectionItem`, no `Presentation`/`PresentationView`, no `Note`, no realtor `Wallet`/`WalletTransaction`, no `Review`. It seeds only a listing agent, a moderator, articles, mortgage programs, marketplace listings, and (from 8.2) the developer CRM. Worse, `CabinetGuard` (the agent client route guard) and `RealtorGuard` (`apps/api/src/agent/realtor.guard.ts`, server-side) both require `role === 'REALTOR'` **and** an active `Subscription` — so with today's seed **there is no way to even reach the agent cabinet**, and every new widget would render 0/empty. Phase 8.3 therefore adds an additive, idempotent `seedRealtorCabinet()` block — the shared prerequisite for all ten pages and for logging in at all.

## Tech Stack

React 19, React Router 7, Tailwind v4 (`@theme` tokens, agent teal already set), TanStack Query 5, FSD. **No new runtime dependencies.** Charts/meters are pure CSS (progress/funnel/composition bars), not a charting library.

## Global Constraints

- Code/identifiers/comments **English**; UI copy Uzbek (keep existing Uzbek strings).
- **No new test files.** Verify with root turbo `yarn turbo run typecheck lint build --filter=@rieltor/agent --filter=@rieltor/api` (never `yarn workspace <pkg> lint` — exit 127). Editing existing fixtures allowed.
- **Phone (<768) layout stays visually intact** — only `md`/`lg`/`desk` tiers are added; the existing single-column order is preserved (use the `contents` wrapper + `order-*` trick where main/aside reorder between phone and desktop, exactly as 8.2 did — `order-*` controls VISUAL order only, not DOM/tab order).
- **Colours unchanged** — agent teal (`--color-accent:#0d9488`, `--color-accent-soft`…) is already set from Phase 8.1; status tones use the existing `brand-green`/`brand-amber`/`brand-rose` tokens. Any visual bar/meter uses the agent teal accent, never the web chart's `#6d28d9` or the CRM blue.
- **Seed is additive + idempotent**: a self-contained `seedRealtorCabinet()` guarded by a count check (`if ((await prisma.subscription.count()) === 0)`) with FIXED string ids (`seed-realtor-*`, `seed-lead-*`, `seed-coll-*`, …) so re-runs never duplicate. Money as BigInt literals (`450_000_000n`) → DTOs stringify (BigInt-as-string end to end; `amountSom`/`commissionSom` are always POSITIVE — direction comes from the transaction `type`). No schema/migration change (all these models already exist).
- **No backend endpoint/DTO/schema changes** (see Non-Goals) — every widget in this phase is built from data the pages already fetch, or from the new seed.
- **The shared `StatTile` primitive lives in `apps/crm`** (`apps/crm/src/shared/ui/stat-tile`). FSD forbids a cross-app import, so agent gets its **own copy** at `apps/agent/src/shared/ui/stat-tile/` (mirror, do not import).
- `apps/web`, `apps/crm`, and all other apps are **not touched** (agent's own `StatTile` copy aside).

## Non-Goals (this phase — explicitly deferred)

- **New/changed API endpoints or DTO fields.** The exploration flagged widgets that would need backend (e.g. a per-presentation dwell-time series endpoint, an org-wide browse-facet aggregate, a wallet balance timeseries). All are DEFERRED. Where a widget would need them, use an existing-data proxy (client-side reductions over the arrays the page already loads) or omit that specific tile rather than fake data or add backend.
- **Charting library / sparklines.** Pure-CSS progress, funnel, and composition bars this phase; real trend charts are deferred with their endpoints.
- **CRM pages** (done in 8.2), and the two standalone onboarding pages **`become-realtor`** (route `/become-realtor`) and **`subscribe`** (route `/subscribe`) — both are centred forms _outside_ the cabinet shell (they run before the guard passes); leave them as-is. This phase only touches the ten _inside-the-cabinet_ pages.
- **Page behaviour/logic, mutations, guards, routing** — unchanged; this is layout + derived widgets + seed only. The AI **lead-assist** panel keeps its current per-lead behaviour (only its placement is considered).

## Section 11 — Seed: `seedRealtorCabinet()` (the shared enabler)

New `apps/api/prisma/seed-realtor.ts` (sibling of `seed-crm.ts`), invoked from `seed.ts` `main()` **last** (after `seedDeveloperCrm(prisma)`, because Fixation depends on the CRM units), guarded by `if ((await prisma.subscription.count()) === 0)`; all rows use fixed string ids (idempotent). Money as BigInt literals (positive; direction via `type`). Phone convention continues `9989000000xx` (00 moderator, 01 dev owner, 02 dev manager) → **realtor `SEED_REALTOR_PHONE = '998900000003'`**, buyer/lead authors `99890500000x`. Login works by phone via devCode (`NODE_ENV !== 'production'`). **Document the login phone** so a tester can OTP in and land in the populated cabinet.

Chain (matching the services' create shapes; every model already exists — no schema change):

- **Users**: 1 `REALTOR` User (`seed-realtor-1`, phone `998900000003`, `role: 'REALTOR'` — MUST be set explicitly or both guards 403) + a `RealtorProfile` (`userId`+`slug` both `@unique`; `agency`, `verified: true`, and `ratingSum`/`ratingCount` **kept equal to the sum/count of the seeded APPROVED Reviews**). Plus ~6 author Users (`createMany`, fixed ids) to satisfy `PropertyRequest.authorId` (required) and `Review.authorId` (each review needs a distinct author — `@@unique([realtorId, authorId])`).
- **Subscription** (`seed-sub-1`): `userId` `@unique` (1:1), `status: 'ACTIVE'`, `currentPeriodEnd` a **future** date (required, no default) — this is what unlocks the cabinet (both guards; `SubscriptionService.isActive`). (A second TRIAL row is _not_ seeded — one ACTIVE realtor is the target; the dashboard's TRIAL banner path stays reachable in code.)
- **PropertyRequest (claimed leads)** (~8–12 via `createMany`): each `claimedById = seed-realtor-1` (+ `claimedAt`), `authorId` from the seeded buyer users (required), and a non-null `outcomeStage` spread across all five (`NEW`/`CONTACTED`/`MEETING`/`WON`/`LOST`) with `lostReason` on the LOST ones — **seed ≥1 WON and ≥1 LOST** so `winRate` is non-null. Varied `score` (0–100) and `priceSom` (BigInt). 1–2 rows are `NEW_BUILD` carrying `complexId`+`unitId` from `seedDeveloperCrm`'s units (so the Fixation chain and the FixationPanel light up).
- **Fixation** (1–2): `propertyRequestId` `@unique` (one per lead), `realtorId = seed-realtor-1`, `unitId` from a `seedDeveloperCrm` unit whose `building.complexId` matches the lead's `complexId` (the fixate service validates this), `commissionBps` (Int, required); one **ACTIVE** (`commissionSom` null) + one **CONVERTED** with a `commissionSom` (BigInt). Bonus: this also lights the developer CRM "Fiksatsiya" column that 8.2 left empty. (If the CRM unit link is awkward, the leads page still fully renders without a Fixation — but seed it, since the units exist.)
- **Wallet + WalletTransaction**: 1 `Wallet` (`userId` `@unique`, `balanceSom` non-zero) + ~10 `WalletTransaction` rows across the four types (a couple `TOPUP`, several `LEAD_CLAIM` with `leadId`, several `COMMISSION` with `fixationId`, ≥1 `COMMISSION_CLAWBACK`); `amountSom` always POSITIVE. **Balance arithmetic must reconcile** with the ledger. Include a case that drives the balance negative to exercise the rose "Qarz" state. `view()` returns the latest 50 desc.
- **Collection + CollectionItem**: 3 `Collection` + ~9 `CollectionItem` (`createMany`; `@@unique([collectionId, listingId])`; `position` 1-based). Reuse existing `SEED_LISTINGS` ids (`bx-001…bx-018`) — no new listings. Include ≥1 empty collection (for the "Bo'sh" tile) and vary `updatedAt`.
- **Presentation + PresentationItem + PresentationView**: 2 `Presentation` (`token` `@unique`, fixed hex mirroring `randomBytes(16).toString('hex')` style) + ~6 `PresentationItem` + ~12 `PresentationView` (a mix of presentation-open events with `listingId` NULL — these are what `opensCount` counts — and per-listing view rows). Include ≥1 presentation with `opensCount === 0` (for the "Ochilmagan" tile).
- **Note**: ~5 `Note` rows (`createMany`; `@@unique([realtorId, listingId])`, one per listing) on distinct `SEED_LISTINGS` ids that carry an agent + images (so `toListingSummary` joins cleanly). Vary deal type across the joined listings so the notes "Sotuv/Ijara split" tile has both.
- **Review**: ~3 `Review` rows (`createMany`; `@@unique([realtorId, authorId])`, distinct authors; `status: 'APPROVED'` — only APPROVED are returned by `realtor-public.service`). Keep `RealtorProfile.ratingSum`/`ratingCount` consistent with these (`ratingAvg = ratingSum/ratingCount`).

Follow `seed-crm.ts` as the fixture template (fixed ids, BigInt so'm, guarded/idempotent, run ordering). No new endpoints — every page reads from services that already exist.

## Decomposition note

Phase 8.3, the final leg of the 8.1→8.2→8.3 roadmap.
