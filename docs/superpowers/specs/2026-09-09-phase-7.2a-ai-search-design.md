# Phase 7.2a — Buyer AI search (natural-language → filters) (design)

**Status:** approved design, ready for planning
**Branch:** `claude/phase-7.2a-ai-search` (off master `43e4ee3`, the Phase 7.1 merge)
**Roadmap:** Phase 7 (Growth layer, the last roadmap phase) — decomposed: 7.1 mortgage (done) → **7.2 AI assistant** → 7.3 map → 7.4 journal. Phase 7.2 is itself decomposed into four sequential slices: **7.2a buyer AI search** → 7.2b realtor lead assistant → 7.2c realtor AI content → 7.2d developer AI insights.

---

## 1. Goal

Give the buyer the marketplace's "AI-assistant pill" (platform spec §2 header): the buyer types a
natural-language query in Uzbek ("Yunusobodda 3 xonali, 100 mln gacha, metroga yaqin") and the
assistant turns it into **structured search criteria**, then runs the existing marketplace search.
The parsed criteria are shown as **editable filter chips** (the buyer sees what the AI understood and
can correct it), and the results come from the existing client-side filter — so there is no opaque
"AI ranking" and no way for the AI to hallucinate a listing.

This is the first slice of the Phase 7.2 AI-assistant subsystem; it establishes the reuse pattern
(a public AI endpoint over the existing `GeminiService`, with strict server-side validation of the
model output and graceful degradation) that the later slices follow.

## 2. Scope

**In scope (7.2a):**

- A public **`POST /api/ai/search-parse`** endpoint: `{ query }` → parsed `AiSearchCriteria` +
  a one-line Uzbek summary, or a `fallback` signal when AI is unavailable / the output is unusable.
- A shared DTO for the request + the parsed criteria (a partial of the existing client `Criteria`).
- A marketplace **natural-language search entry** (home hero) that calls the endpoint, then routes
  to the existing `/search` page with the parsed criteria applied and shown as editable chips.
- Graceful degradation end-to-end: no `GEMINI_API_KEY` / a bad model response → the buyer's raw
  text becomes the plain keyword search (the feature never blocks a search).

**Deferred (named, not built):**

- AI **ranking / recommendation** of listings (7.2a is parse-only; results come from the existing
  filter). Semantic similarity, "listings like this one", personalization.
- Server-side listing search / filtering (today `/api/objects` returns all listings and the client
  filters — 7.2a does not change that).
- Query logging / analytics, saved AI searches, multi-turn conversation, voice input.
- Rate-limiting infrastructure (7.2a caps input length + output tokens; a per-IP/user rate limiter
  for the public AI surface is a named fast-follow).
- The other Phase 7.2 slices (7.2b lead assistant, 7.2c AI content, 7.2d developer insights) and the
  rest of Phase 7.

## 3. Design decisions (resolved)

1. **NL → structured criteria, not AI ranking.** Gemini parses the query into the existing client
   `Criteria` shape; the existing `filterListings` produces the results. Transparent (editable
   chips), verifiable, hallucination-free.
2. **Reuse the existing search page + client filter.** The endpoint returns criteria; the web seeds
   the `/search` page's criteria (via the URL/query-string the page already reads) and lets the
   buyer edit them in the existing `FilterPanel`. No new results surface, no new filter logic.
3. **Public endpoint, strict output validation.** `POST /api/ai/search-parse` is unguarded
   (buyer-facing, like `@Controller('objects')`). The model returns free-form JSON text; the server
   `JSON.parse`-in-try/catch + Zod-validates + clamps it into `AiSearchCriteria`, dropping any
   invalid/unknown field. The LLM's shape is **never trusted** — an unparseable/invalid response is
   treated as a fallback, not a 500.
4. **Graceful degradation is a first-class path.** No API key, a provider outage, or an unusable
   parse all resolve to `{ fallback: true, criteria: { search: <raw query> }, summary: … }` so the
   client silently runs a plain keyword search.

## 4. Data model

**No change.** 7.2a is a stateless parse over existing data. No migration, no new table.

## 5. Backend

### 5.1 Shared DTOs (`packages/shared/src/schemas.ts`)

The parsed criteria are a **partial of the client `Criteria`** (only the fields the AI can fill; the
client merges into its `EMPTY_CRITERIA`). Every field optional so a sparse parse is valid.

```ts
/** The request body for the buyer AI search parser. */
export const AiSearchRequestSchema = z.object({
  query: z.string().trim().min(1).max(200), // cap: public + paid model call
});

/** What the AI parser is allowed to fill — a partial of the web client's Criteria.
 *  deal/type/sort are enums; rooms/price/area are clamped numbers; search is free text
 *  (district + landmark + anything unstructured, matched against title+district+landmark). */
export const AiSearchCriteriaSchema = z.object({
  deal: DealSchema.optional(), // SALE | RENT
  type: ListingTypeSchema.optional(), // NEW_BUILD | SECONDARY | HOUSE | COMMERCIAL (omit = ALL)
  rooms: z.number().int().min(0).max(20).nullable().optional(), // 5 = "5+"
  priceMin: z.number().int().min(0).max(1_000_000_000_000).nullable().optional(), // som
  priceMax: z.number().int().min(0).max(1_000_000_000_000).nullable().optional(), // som
  areaMin: z.number().int().min(0).max(100_000).nullable().optional(), // m²
  areaMax: z.number().int().min(0).max(100_000).nullable().optional(), // m²
  sort: z.enum(['NEW', 'CHEAP', 'EXPENSIVE']).optional(),
  search: z.string().max(200).optional(), // district/landmark/complex/free keywords
});

/** The parser response. fallback=true → AI unavailable/unusable; run a plain keyword search. */
export const AiSearchResponseSchema = z.object({
  fallback: z.boolean(),
  criteria: AiSearchCriteriaSchema,
  summary: z.string(), // one-line Uzbek "AI tushundi: …" (empty when fallback)
});
```

Plus the inferred types.

### 5.2 AiSearchController + parse (`apps/api/src/ai/`)

- Add a new **`AiSearchController`** to the existing `AiModule` (which already provides
  `GeminiService`): `@Controller('ai')`, **UNGUARDED** (public), `@Post('search-parse')`.
  (Two `@Controller('ai')` classes — the existing guarded `AiController` + this public one — do not
  collide: `/api/ai/description` vs `/api/ai/search-parse`, the established multi-controller pattern.)
- Handler: Zod-parse the body (400 on bad input via the schema); build an Uzbek prompt instructing
  Gemini to return **JSON only** with the `AiSearchCriteria` fields and the enum vocabularies; call
  `gemini.generate(prompt, { maxTokens: 256 })`.
- **Output handling (load-bearing):** if `generate` returns `null` → return
  `{ fallback: true, criteria: { search: query }, summary: '' }`. Otherwise strip any code fence,
  `JSON.parse` in a try/catch, then `AiSearchCriteriaSchema.safeParse` the result:
  - success → `{ fallback: false, criteria: <validated>, summary: <derived one-line Uzbek> }`
    (drop fields the model invented; `.safeParse` already strips unknown keys and rejects bad types).
  - failure (not JSON, or no valid field) → the same fallback as `null`.
- **Sanity clamps** after validation: if both `priceMin` and `priceMax` are set and `min > max`, swap
  them; likewise `areaMin`/`areaMax`. (Cheap guard against an inverted range.)
- Never throws for an AI/parse problem — the fallback path always yields a usable response (a 400 is
  only for a malformed request body, i.e. missing/oversized `query`).

### 5.3 The prompt

A single Uzbek instruction: role ("O'zbekistonda ko'chmas mulk qidiruv so'rovini JSON filtrlarga
aylantiruvchi yordamchi"), the exact allowed fields + enum values, the rules (money words:
`ming`=×1 000, `mln`/`million`=×1 000 000; prices are **in som**; `ijara`→RENT else SALE; put
district/landmark/complex names and anything unstructured into `search`; omit a field when unknown —
do not invent), and "Return JSON only, no prose." The server does not rely on the model obeying —
it validates (§5.2).

### Carrying the criteria to the search page

The `/search` page seeds its `criteria` on mount from the URL query-string, but that string encodes
**only `deal`/`type`/`search`** (`parseSearchQuery` — price/area/rooms/sort "live only in the
search page's panel" and are deliberately not URL-encoded, so a saved search can't capture them). The
AI's value is precisely `rooms`/`price`/`area`, so the URL cannot carry the full parse. 7.2a therefore
passes the full criteria via **React Router navigation state** (`navigate('/search', { state: … })`),
which the search page reads on mount **in addition to** the existing URL parse. This touches only the
search page's initial-state seed + the new feature — the query-string contract and saved-search
behavior are untouched.

## 6. Frontend (`apps/web`, FSD)

- **`features/ai-search/`** — a new feature:
  - `lib/to-criteria.ts` — merge an `AiSearchCriteria` into a full `Criteria` (start from
    `EMPTY_CRITERIA`, reused from `listing-filters`: `type` omitted → `'ALL'`, `deal` omitted →
    `'SALE'`, nulls preserved).
  - `model/use-ai-search.ts` — `useAiSearch()` (a mutation over
    `apiPost('/api/ai/search-parse', AiSearchResponseSchema, { query })` — note the client signature
    is `apiPost(path, schema, body)`; on network/HTTP error, resolve to a client-side
    `{ fallback: true, criteria: { search: query }, summary: '' }` so a failure never breaks the flow).
  - `ui/ai-search-bar.tsx` — a natural-language input ("AI bilan qidiring…") + submit; on submit call
    the parser, build the full criteria via `to-criteria`, then
    `navigate('/search', { state: { aiCriteria, aiSummary } })`.
- **Search page seed (`pages/search/ui/search-page.tsx`):** extend the existing `useState` initializer
  to prefer `location.state?.aiCriteria` (a full `Criteria`) when present — seeding all fields and
  setting `submitted = true` — else fall back to the current URL parse. When `location.state?.aiSummary`
  is present and non-empty, show a small "AI tushundi: <summary>" line above the filter panel. The
  buyer edits the seeded criteria in the existing `FilterPanel` (editable chips) exactly as a manual
  search.
- **Placement:** render `<AiSearchBar />` on the home hero (the marketplace entry). (The header
  "AI-assistant pill" can link to the same entry; the plan picks the exact spot — reuse, don't
  restructure the header.)
- **Graceful degradation:** `fallback:true` → the criteria are just `{ …EMPTY_CRITERIA, search: raw
query }` → the search page runs a plain keyword search; no error toast, the feature is invisible
  when AI is off beyond a plain search.

UI copy Uzbek; identifiers/routes/comments English.

## 7. Rulings & invariants (load-bearing)

- **R1 — never trust the model's shape.** The Gemini response is free text; the server JSON-parses in
  try/catch and Zod-validates into `AiSearchCriteria`, dropping invalid/unknown fields. A bad response
  is a fallback, never a 500 and never an unvalidated object reaching the client.
- **R2 — parse-only, results from the existing filter.** The AI fills criteria; `filterListings`
  produces results. No AI ranking, no AI-authored listing data. The buyer always sees + can edit the
  criteria (transparency).
- **R3 — graceful degradation.** No key / outage / unusable parse → `{fallback:true, criteria:{search:query}}` → the client runs a plain keyword search. The search entry works with AI off.
- **R4 — public-surface safety.** The endpoint is unguarded (buyer-facing) but caps input (`query` ≤
  200 chars, rejected by the schema) and output (`maxTokens` 256). A per-IP/user rate limiter is a
  named fast-follow (not built in 7.2a).
- **R5 — criteria fidelity.** The AI may only emit fields the client `Criteria` accepts, with the
  same enums/units (som for price, m² for area, `rooms` 5 = "5+"); the shared schema clamps ranges.
  The parsed criteria merge into `EMPTY_CRITERIA` exactly as a manual filter would, so AI search and
  manual search are indistinguishable downstream.
- **R6 — additive-only.** No schema change, no migration, no change to `/api/objects` or the existing
  guarded `/api/ai/description`; a new public controller in the existing `AiModule`.

## 8. Verification (no new test files — per project rule)

- `yarn typecheck` + `yarn lint` + `yarn build` green across api / shared / web.
- Compiled-JS scratch against a real `nest build` output (never `tsx`) OR a booted-Nest HTTP check of
  `POST /api/ai/search-parse` (no auth header → not 401/403): (a) with `GEMINI_API_KEY` unset →
  `fallback:true`, `criteria.search === query`, HTTP 200 (never 500); (b) a request with an oversized
  `query` (>200 chars) → 400; (c) the output-handling path is robust — simulate a non-JSON / invalid
  model string (e.g. via a scratch that feeds a bad string through the same parse+safeParse+clamp
  helper) → resolves to the fallback, and a valid JSON string → validated criteria with invented
  fields dropped and an inverted price range swapped.
- Browser smoke (AI on if a key is available, else the fallback path): the home AI search bar accepts
  a query, routes to `/search`, the criteria appear in the `FilterPanel` and the results match; with
  AI off, the raw query becomes the keyword search.
- Full suite green before merge (shared 18, web 34, api 37, e2e 22 → 111), zero new test files.
