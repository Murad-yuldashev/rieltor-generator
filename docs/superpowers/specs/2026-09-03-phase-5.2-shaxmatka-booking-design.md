# Phase 5.2 — Shaxmatka + booking design

_Date: 2026-09-03 · Branch: `claude/phase-5.2-shaxmatka-booking` · Base: master `cbe1edb` · Part of: Phase 5 (Product B — Developer CRM) · Depends on: 5.1 (Organization/Complex/Building/Unit + `apps/crm` + DeveloperGuard)_

## 1. Goal

Turn the developer CRM's flat unit list into a **shaxmatka** — the sales-core grid where a
construction company sees every unit of a building laid out by floor, colour-coded by status, and
manages sales at a glance: edit a single cell, bulk-change many at once, and **book** a unit (hold it
for a client for a configurable window). A booking flips the unit to `BOOKED`; cancelling or letting
the hold expire frees it back to `AVAILABLE`; converting it marks the unit `SOLD`. A scheduled job
auto-expires stale holds so a unit never stays reserved past its window. This is Phase 5, part 2 —
the developer's day-to-day sales tool on top of 5.1's inventory. It does **not** publish to the
marketplace (5.3), link a booking to a platform buyer or a lead/fixation (5.4), or add contracts /
payment schedules (Phase 6).

## 2. Scope

1. **`Booking` model** — a hold on a unit (free-text client, a `holdUntil` window, a lifecycle) +
   `BookingStatus`.
2. **Booking flow** — `POST /api/crm/units/:id/book` (create a hold, flip the unit to `BOOKED`) and
   `PATCH /api/crm/bookings/:id` (cancel / convert-to-sale / extend); a `GET /api/crm/bookings` list.
3. **Auto-expiry** — an hourly `@nestjs/schedule` cron that expires overdue `ACTIVE` bookings and
   frees their units.
4. **Bulk edit** — `PATCH /api/crm/units/bulk` to set status/price on many owned units at once.
5. **Shaxmatka UI** — a status-coloured grid on the building-detail page (floors × units), single-
   cell edit + multi-select bulk edit + the book/cancel/convert actions; a bookings list page.

### Non-goals (later)

- **Marketplace publishing / ЖК pages (A12)** — Phase 5.3.
- **Linking a booking to a platform buyer `User` or a lead; cross-CRM fixation (C6) / commission** —
  Phase 5.4. A 5.2 booking's client is **free text** (name + phone), not a linked entity.
- **Contracts, payment schedules, finance** — Phase 6.
- **A `line`/entrance (podъezd) dimension** — the grid is floor-rows × units-ordered-by-`number`; a
  second horizontal dimension for multi-entrance buildings is deferred (YAGNI). The 5.1 `Unit` gains
  no positional field.
- **Per-org configurable default hold duration** — the hold length is a per-booking `holdDays` input
  (with a default); an org-level setting is later.
- **Booking history/audit beyond the row's own status + timestamps**; **overlapping/queued holds** —
  a unit has at most one `ACTIVE` booking at a time.
- The marketplace, realtor cabinet, lead market, and the 5.1 inventory CRUD — unchanged except the
  additions below (the `Unit` view gains an optional active-booking summary; bulk edit).

## 3. Data model (Prisma)

Additive: one new model + one enum; `Unit` gains a `bookings` back-relation.

```prisma
enum BookingStatus {
  ACTIVE       // holding the unit now
  CANCELLED    // released by the developer (cancelReason set)
  EXPIRED      // holdUntil passed; freed by the cron
  CONVERTED    // turned into a sale (unit -> SOLD)
}

model Booking {
  id          String        @id @default(cuid())
  unitId      String
  unit        Unit          @relation(fields: [unitId], references: [id], onDelete: Cascade)
  clientName  String
  clientPhone String
  holdUntil   DateTime
  status      BookingStatus @default(ACTIVE)
  note        String?
  cancelReason String?                       // set when status = CANCELLED
  createdById String                          // the org member who booked (a User id)
  createdBy   User          @relation(fields: [createdById], references: [id], onDelete: Cascade)
  createdAt   DateTime      @default(now())
  updatedAt   DateTime      @updatedAt

  @@index([unitId])
  @@index([status, holdUntil])                // the expiry cron scans ACTIVE + overdue
}

// Unit gains: bookings Booking[]
// User gains:  bookings Booking[] (the createdBy back-relation)
```

`holdUntil` is the hold's expiry instant. **A unit has at most one `ACTIVE` booking** — enforced in
the service (an existing `ACTIVE` booking or a non-`AVAILABLE` unit rejects a new hold). The active
booking is found by `{ unitId, status: 'ACTIVE' }`. Money stays out of `Booking` (the sale price
lives on the `Unit`); `cancelReason`/`note` are free text.

## 4. Booking flow

All booking routes are `DeveloperGuard` + org-scoped through the unit's ownership chain
(`unit → building → complex → org`, the 5.1 `unitOwnedOrThrow` idiom; a foreign unit/booking → 404).

- **`POST /api/crm/units/:id/book`** body `{ clientName, clientPhone, holdDays?, note? }`: the unit
  must be **`AVAILABLE`** — else **409** ("Xonadon bo'sh emas"). In one `$transaction`: create a
  `Booking { status: ACTIVE, holdUntil: now + (holdDays ?? DEFAULT_HOLD_DAYS)*day, createdById }` and
  set `unit.status = 'BOOKED'`. `DEFAULT_HOLD_DAYS = 3`; `holdDays` bounded 1..90. Returns the booking.
- **`PATCH /api/crm/bookings/:id`** body `{ action: 'cancel' | 'convert' | 'extend', cancelReason?,
holdDays? }` (only on an `ACTIVE` booking — else 409):
  - **cancel** → `status: CANCELLED` (+ `cancelReason`), and if the unit is still `BOOKED`, `unit →
AVAILABLE` (one transaction).
  - **convert** → `status: CONVERTED`, `unit → SOLD` (the sale closed).
  - **extend** → `holdUntil = now + holdDays*day` (a fresh window; the unit stays `BOOKED`).
- **`GET /api/crm/bookings`** (org-scoped) → the org's bookings (newest first, a bounded window),
  each with the unit label (building + unit number) + client + `holdUntil` + status.
- The `Unit` view (`GET /api/crm/buildings/:id/units`, and the unit rows the grid reads) gains an
  optional **`activeBooking`** summary — `{ id, clientName, clientPhone, holdUntil }` when the unit's
  status is `BOOKED` and an `ACTIVE` booking exists; `null` otherwise. This is what colours a booked
  cell and shows who holds it.

## 5. Auto-expiry (cron)

An hourly `@nestjs/schedule` cron (mirroring `MonthlyValuationCron`) — `BookingExpiryCron` calling
`BookingService.expireOverdue()`: in one pass, every `ACTIVE` booking with `holdUntil < now` is set
`EXPIRED`, and any unit **still `BOOKED`** by such a booking is set `AVAILABLE` (a unit already moved
to `SOLD`/`AVAILABLE` by hand is left as-is). Runs on the single-instance deploy (the same caveat as
the monthly-valuation cron). Idempotent — a second run finds nothing overdue. `@Cron('0 * * * *')`
(top of every hour). No new env.

## 6. Bulk edit

**`PATCH /api/crm/units/bulk`** (DeveloperGuard) body `{ unitIds: string[] (1..500), status?:
UnitStatus, priceSom?: string }` — at least one of `status`/`priceSom` present. The service verifies
**every** `unitId` belongs to the caller's org (resolve `orgId` once, then a single query counts the
units whose `building.complex.orgId === orgId`; if the count ≠ `unitIds.length`, **404** — foreign or
missing ids, all-or-nothing on ownership, no write). Then:

- **`priceSom`** applies to **all** selected units (`updateMany`) — price never conflicts with a hold.
- **`status`** applies only to selected units that have **no `ACTIVE` booking**; a unit with an active
  hold is **skipped** for the status change (its status stays consistent with its live booking — bulk
  never silently strands a hold by flipping a `BOOKED` unit out from under its `ACTIVE` booking). The
  developer manages booked units through the booking flow (cancel/convert) instead.

Returns `{ updated: number, skippedBooked: number }` so the UI can tell the developer how many booked
units were left for individual hold management. (This keeps `Unit.status` and the active booking in
agreement without a hard failure.)

## 7. Shaxmatka UI (`apps/crm`)

On the **building-detail page** (5.1 already lists units there), add the shaxmatka grid as the
primary unit view:

- **Grid** — units grouped by `floor` (highest floor at top, like a real shaxmatka), each floor a row
  of cells ordered by `number`. Each cell shows the unit number + a **status colour**: `AVAILABLE`
  green, `BOOKED` amber, `SOLD` red (Uzbek legend: Bo'sh / Band / Sotilgan). A `BOOKED` cell shows the
  client name (from `activeBooking`). The grid scrolls inside an `overflow-x-auto` container.
- **Single-cell** — clicking a cell opens the unit panel: edit its fields (the 5.1 unit update) +,
  by status, **"Band qilish"** (AVAILABLE → a booking form: client name/phone, hold days) or, on a
  BOOKED unit, **"Bekor qilish"** (cancel + reason) / **"Sotildi"** (convert → SOLD).
- **Bulk** — a multi-select mode (cell checkboxes / a "tanlash" toggle) → a bulk bar to set status or
  price on the selection → `PATCH /api/crm/units/bulk`, then refresh.
- The existing add-unit form + the plain table remain reachable (the grid is the default; the table
  is a secondary list). Prices via `formatPriceSom(_, 'SALE')`.
- A **"Bandlar"** page (`GET /api/crm/bookings`) in the cabinet nav — the org's bookings (unit label,
  client, hold-until, status) with cancel/convert actions on the active ones.

## 8. Modules & wiring

- `apps/api`: the booking logic joins the existing **`DeveloperModule`** — `BookingService` (create/
  cancel/convert/extend/list/expireOverdue + the `activeBooking` enrichment) and the new controller
  routes on the `crm` controller (or a sibling `BookingController` in the same module), all
  `DeveloperGuard` + org-scoped; the bulk-edit route on the units surface; a `BookingExpiryCron`
  registered as a provider (ScheduleModule is already global). Reuses the 5.1 ownership-chain checks.
- Shared Zod DTOs: `BookingStatus`, `Booking`/`BookingRow` views, `BookingSummary` (the `activeBooking`
  shape on `Unit`), `BookingCreate` (`{ clientName, clientPhone, holdDays?, note? }`), `BookingAction`
  (`{ action, cancelReason?, holdDays? }`), `UnitBulkUpdate` (`{ unitIds, status?, priceSom? }`); the
  `Unit` view gains `activeBooking: BookingSummary | null`.
- `apps/crm`: the shaxmatka grid + booking controls on building-detail; the bookings list page + hook.

## 9. Constraints

- Uzbek user-facing copy; **English** identifiers/comments.
- **No new test files**; the existing suite stays green (api 37 + e2e 22, web 34, shared 18 = 111);
  `@rieltor/crm` ships no tests.
- **Additive migration**; **no new env var**.
- Booking + bulk endpoints are **DeveloperGuard** and **org-scoped** (the unit ownership chain →
  404 for a foreign unit/booking); bulk edit is **all-or-nothing** (any foreign id → 404, no partial
  write). BigInt money (`priceSom`) is a **string** end-to-end.
- A unit has **at most one `ACTIVE` booking**; a hold is only allowed on an `AVAILABLE` unit (else
  409); the booking↔unit-status writes are **transactional** (create/cancel/convert never leave the
  unit and the booking disagreeing).
- The expiry cron is **idempotent** and only frees a unit **still `BOOKED`** by the expiring hold.
- `apps/crm` imports only `@rieltor/shared` + its own `@/*`.

## 10. Verification

- Automated: `yarn lint`/`typecheck`/`build` (5 workspaces); the existing suite green; additive
  migration.
- API (compiled-JS scratch): book an `AVAILABLE` unit → a `Booking(ACTIVE)` + unit `BOOKED` + the
  `activeBooking` summary appears on the unit view; a second book on the now-`BOOKED` unit → **409**;
  **cancel** → booking `CANCELLED` + unit `AVAILABLE`; re-book → ok; **convert** → booking `CONVERTED`
  - unit `SOLD`; **extend** → `holdUntil` moves; a foreign org's user booking/cancelling this unit/
    booking → **404**. Bulk: set status/price on N owned units → all updated; a mix that includes a
    foreign id → **404**, nothing written. Expiry: an `ACTIVE` booking with `holdUntil` in the past +
    its unit `BOOKED` → `expireOverdue()` sets it `EXPIRED` + the unit `AVAILABLE`; a hand-`SOLD` unit's
    overdue booking → booking `EXPIRED` but the unit stays `SOLD`. Clean up.
- CRM (browser smoke): open a building's shaxmatka → the floor×unit grid with status colours; book a
  free cell (it turns amber, shows the client); bulk-select two cells → set price; cancel a booking
  (cell turns green); the bookings page lists the org's holds.

## 11. Risks

- **Booking ↔ unit-status desync** — a hold that flips the unit but crashes before writing the
  booking (or vice versa) would leave a `BOOKED` unit with no `ACTIVE` booking (uncancellable) or an
  `ACTIVE` booking on an `AVAILABLE` unit. Every create/cancel/convert wraps the booking write and the
  unit-status write in ONE `$transaction`; the scratch asserts they always agree.
- **Double-booking a unit** — two concurrent `book` calls on the same `AVAILABLE` unit must not both
  create an `ACTIVE` hold. The create re-reads the unit status inside the transaction and rejects a
  non-`AVAILABLE` unit (409); a row lock on the unit (`SELECT … FOR UPDATE`, the 4.x claim idiom)
  serialises the two so exactly one wins. The scratch fires two concurrent holds → one ACTIVE, one 409.
- **Bulk partial write / cross-tenant leak** — a bulk update spanning orgs, or a partial apply, would
  corrupt another org's inventory or leave a half-done change. The service counts the caller-owned
  units matching the ids and 404s the whole call unless the count equals the id count (ownership is
  all-or-nothing, no foreign id touched). The scratch asserts a foreign id in the set writes nothing.
- **Bulk status stranding a hold** — a bulk `status` change on a `BOOKED` unit would leave an
  `ACTIVE` booking on a non-`BOOKED` unit (an uncancellable desync). Bulk `status` **skips units with
  an active booking** (reported via `skippedBooked`); only `priceSom` touches them. The scratch
  asserts a booked unit in a bulk-status set keeps its `BOOKED` status + its live booking.
- **Cron freeing a manually-progressed unit** — an overdue booking whose unit was hand-sold must not
  be reset to `AVAILABLE`. `expireOverdue()` frees a unit only when it is **still `BOOKED`**; a `SOLD`
  unit is left alone. The scratch asserts this.
- **Single-instance cron** — like the monthly-valuation cron, `BookingExpiryCron` assumes one running
  instance; a multi-instance deploy would double-run it (idempotent, so harmless beyond wasted work).
  Documented, not solved here.
