# Phase 6.1 — Developer/Org wallet + funded commission Design

**Status:** Draft for review
**Date:** 2026-09-04
**Phase:** 6 (Contracts / Finance) — sub-phase 6.1 (the funding foundation)
**Depends on:** 4.2 (realtor wallet ledger), 5.4 (commission credit at convert — the "platform floats" seam this closes)

---

## 1. Goal

Stop the platform floating realtor commission. Give each `Organization` a **wallet** (an org-scoped ledger mirroring the realtor `Wallet`), let a developer **top it up** (a test-payment stub), and at booking **convert→SOLD** — in the same transaction that already credits the fixated realtor — **debit the owning org's wallet** by the same amount. The org wallet is the funding counterparty that later Phase-6 sub-phases (contracts, clawback, settlement) build on. If the org balance can't cover the commission, the sale still completes and the realtor is still paid immediately (C8); the org wallet simply goes **negative** — a recorded debt reconciled later.

## 2. Scope decisions (locked with product owner)

| Fork                      | Decision                                                                                                                                                                                     |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Phase-6 decomposition** | 6.1 org wallet + funded commission (this) → 6.2 Contracts → 6.3 clawback/reconciliation → 6.4 payment schedules + debtors + finance/KPI.                                                     |
| **Funding model**         | **Org wallet debited at convert** — the org debit and the realtor credit are two ledger movements in the ONE convert transaction. (Held escrow / pre-funding deferred to a later sub-phase.) |
| **Short balance**         | The sale proceeds and the realtor is paid; the org wallet goes **negative** (a recorded debt). No `402`, no block, no gate on the sale.                                                      |
| **Integrations**          | Top-up is a **stub** (immediate credit), mirroring the realtor top-up; real Click/Payme/Uzum + JSHSHIR come later.                                                                           |

## 3. Design rulings (load-bearing — confirm at review)

1. **A separate `OrgWallet` model, not a polymorphic `Wallet`.** The realtor `Wallet` is `userId @unique` (1:1 User); a new `OrgWallet` (`orgId @unique`) + `OrgWalletTransaction` mirrors its ledger machinery additively and leaves the realtor wallet untouched.
2. **Negative balance is allowed by design (a debt).** The commission debit at convert does NOT take a `FOR UPDATE` lock or a balance guard and NEVER throws `402` — over-spend is permitted so the sale and the realtor's C8 payout are never blocked by org funding. (Contrast the realtor `debitForClaim`, which 402s when short.) Because the debit is a plain atomic decrement with no read-modify-write guard, no row lock is needed.
3. **The org debit rides the existing convert transaction + exactly-once gate.** It is added right beside the realtor `wallet.credit(tx, …)` call, inside the `count===1` block and gated on `commissionSom > 0n`, so it commits atomically with the SOLD flip + realtor credit and inherits the same fire-at-most-once guarantee. No new idempotency key in 6.1 (the ledger-level idempotency key lands in 6.3 with clawback).
4. **`balanceSom` may serialize negative.** The realtor money convention is `z.string().regex(/^\d+$/)` (non-negative); `OrgWalletView.balanceSom` must allow a leading minus (`/^-?\d+$/`). `amountSom` stays non-negative (direction is carried by `type`, mirroring `WalletTransaction`).
5. **Top-up is a stub** (immediate credit, no gateway), mirroring the realtor `POST /wallet/topup`; reuse the shared `TOPUP_PACKAGES`. The org wallet is created lazily on first funding or first commission debit (P2002-safe upsert, like `ensureWallet`).
6. **Additive migration only** — new enum + two new tables + a back-relation; `Wallet`/`WalletTransaction` unchanged.

## 4. Non-goals (deferred)

- **Escrow / held (pending-vs-available) balance / pre-funding at booking** — a later 6.x sub-phase.
- **`Contract` model** — 6.2.
- **Commission clawback / reversal / reconciliation** (reversing a paid commission + refunding the org on an unwound sale, the ledger idempotency key) — 6.3.
- **Payment schedules, debtors, invoices, finance/KPI dashboards** — 6.4.
- **Real payment-provider integrations** (Click/Payme/Uzum/Apelsin/Paylov), QR, 1C export, JSHSHIR online signing — later (partner-dependent); 6.1 uses the stub.
- **Buyer payments / spending the org wallet on anything other than funding commission** — out of scope; the org wallet in 6.1 only has TOPUP (credit) + COMMISSION_DEBIT (debit).

## 5. Architecture & data flow

```
Developer (apps/crm)                         Booking convert (apps/api, existing 5.4 tx)
────────────────────                         ─────────────────────────────────────────
1. POST /api/crm/wallet/topup (stub)         booking.act('convert')  [$transaction, count===1]
   → OrgWallet balance += package             ├─ Unit → SOLD
   (GET /api/crm/wallet shows balance+ledger) ├─ Fixation → CONVERTED (commissionSom)
                                              ├─ wallet.credit(tx, realtorId, commissionSom)   ◄ existing (5.4)
                                              └─ orgWallet.debitForCommission(tx, orgId, commissionSom, {fixationId})  ◄ NEW (6.1)
                                                 (atomic decrement; balance may go negative; no 402)
```

The org whose unit sold funds the realtor's commission. `bookingOwnedOrThrow` already selects `unit.building.complex.orgId`, so the owning `orgId` is **captured in the `act()` closure** and usable inside the convert `$transaction` (org ownership is immutable, so a pre-tx read is safe); alternatively add `building.complex.orgId` to the in-tx unit `select` that today pulls only `priceSom`. Both money movements + the SOLD flip commit atomically; a concurrent/re-fired convert lands at `count===0` and moves no money (the exactly-once guarantee 5.4 already proved covers the new debit too).

Reuse: the realtor `WalletService` ledger idioms (lazy `ensureWallet` upsert, atomic increment/decrement + ledger row in the caller's tx, `balanceSom = sum(ledger)` invariant, BigInt-as-string DTO), the realtor `POST /wallet/topup` stub, `DeveloperGuard` + org-scoping, and the apps/agent wallet page (mirrored into apps/crm).

## 6. Data model (Prisma — additive)

```prisma
enum OrgWalletTxType {
  TOPUP           // developer funds the wallet (stub credit)
  COMMISSION_DEBIT // funds a realtor commission at convert
}

model OrgWallet {
  id           String                 @id @default(cuid())
  orgId        String                 @unique
  org          Organization           @relation(fields: [orgId], references: [id], onDelete: Cascade)
  balanceSom   BigInt                 @default(0)   // cached = sum(transactions); MAY be negative (debt)
  transactions OrgWalletTransaction[]
  createdAt    DateTime               @default(now())
  updatedAt    DateTime               @updatedAt
}

model OrgWalletTransaction {
  id          String          @id @default(cuid())
  orgWalletId String
  orgWallet   OrgWallet       @relation(fields: [orgWalletId], references: [id], onDelete: Cascade)
  type        OrgWalletTxType
  amountSom   BigInt          // always positive; direction implied by `type`
  fixationId  String?         // the funding event, for a COMMISSION_DEBIT row (nullable; audit link)
  createdAt   DateTime        @default(now())

  @@index([orgWalletId, createdAt])
}
```

- `Organization` gains `orgWallet OrgWallet?` (back-relation).
- **Migration** `<ts>_phase_6_1_org_wallet`: `CREATE TYPE OrgWalletTxType`, `CREATE TABLE OrgWallet` (+ unique on orgId + FK Cascade), `CREATE TABLE OrgWalletTransaction` (+ index + FK Cascade). No `DROP`, no change to `Wallet`/`WalletTransaction`.

## 7. Shared DTOs (`packages/shared/src/schemas.ts`)

- `OrgWalletTxTypeSchema = z.enum(['TOPUP','COMMISSION_DEBIT'])`.
- `OrgWalletTxRowSchema` — `{ id, type: OrgWalletTxTypeSchema, amountSom: z.string().regex(/^\d+$/), fixationId: z.string().nullable(), createdAt: z.string() }`.
- `OrgWalletViewSchema` — `{ balanceSom: z.string().regex(/^-?\d+$/)` (MAY be negative — a debt), `transactions: z.array(OrgWalletTxRowSchema) }`.
- Reuse the existing `TOPUP_PACKAGES` for the org top-up (or a sibling constant if the amounts should differ — default to reusing).

## 8. API surface (`@Controller('crm/wallet')` → served at `/api/crm/wallet`, `@UseGuards(JwtGuard, DeveloperGuard)`, org-scoped)

> Path note: the realtor wallet is `@Controller('wallet')` → `/api/wallet`; the new developer controller MUST declare `crm/wallet` so it lands at `/api/crm/wallet` (matching the sibling CRM controllers), not `/api/wallet`.

- `GET /api/crm/wallet` — the caller's org wallet view (`orgIdOf(userId)` → `OrgWalletService.view(orgId)`; lazy-creates an empty wallet if none).
- `POST /api/crm/wallet/topup` — body `{ packageId }` (mirror the realtor top-up body); stub-credits the org wallet by the package amount (atomic increment + a `TOPUP` ledger row). Returns the updated view.

`OrgWalletService`:

- `ensureOrgWallet(orgId)` — lazy P2002-safe upsert.
- `view(orgId): OrgWalletView` — balance + ledger (BigInt→string; balance may be negative).
- `topup(orgId, packageId)` — atomic increment + `TOPUP` row.
- `debitForCommission(tx, orgId, amountSom, { fixationId }): Promise<void>` — runs on the caller's tx (mirrors `WalletService.credit`'s tx-accepting shape but DEBITS): in-tx upsert-ensure the wallet, atomic `balanceSom: { decrement: amountSom }` (negative allowed, no guard/lock/402), create a `COMMISSION_DEBIT` row with `fixationId`. Injected into `BookingService` (via `WalletModule`-style DI on a new `OrgWalletModule`).

`booking.service.act()` convert: right after `wallet.credit(tx, fixation.realtorId, commissionSom, { fixationId })` (inside `count===1` + `commissionSom > 0n`), call `orgWallet.debitForCommission(tx, orgId, commissionSom, { fixationId })`. Resolve `orgId` from the unit ownership already loaded (or add `building.complex.orgId` to the in-tx unit select if not present).

## 10. Testing

Project rule: **no new test files**. Verify via `yarn lint`/`typecheck`/`build` (suite stays **111 green**; crm/agent build) + compiled-JS scratch (nest build → node; never tsx):

- convert with a matching fixation → the realtor `Wallet` is credited AND the owning org's `OrgWallet` is debited by the same `commissionSom` (org `balanceSom` decreases; goes NEGATIVE when it started at 0/short), both in one tx, `Unit` SOLD;
- **idempotent** — re-fire convert on the already-CONVERTED booking → NO second debit (count===0);
- `commissionSom === 0` (null price / zero rate) → NO org debit (mirrors no realtor credit);
- `POST /api/crm/wallet/topup` credits the org wallet (TOPUP row); `GET /api/crm/wallet` returns the balance (incl. a negative one) + ledger; a foreign/other-org caller only ever sees their own org's wallet;
- BigInt money is string end-to-end; the negative balance serializes (`-?\d+`).
- Browser smoke: the CRM wallet page shows balance/top-up/ledger, and a debt (negative) renders as "Qarz".

## 11. Rulings map

| Question                              | Resolution                                                                                     |
| ------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Where does the developer wallet live? | New `OrgWallet` model, org-scoped (ruling 1).                                                  |
| Who funds commission + when?          | The owning org, debited at convert in the same tx (scope decision 2).                          |
| Short balance?                        | Sale proceeds, realtor paid, org wallet goes negative — no block (scope decision 3, ruling 2). |
| Exactly-once for the new debit?       | Inherited from the convert `count===1` gate (ruling 3).                                        |
| Negative money serialization?         | `OrgWalletView.balanceSom` allows a leading minus (ruling 4).                                  |
| Top-up?                               | Stub, reuse TOPUP_PACKAGES, lazy wallet create (ruling 5).                                     |

## 12. Rollout

Single additive migration; no env changes; no new dependency. Until a developer tops up, a convert simply drives the org wallet negative (a visible debt) — the realtor is still paid, exactly as today, so nothing regresses; 6.1 only adds the counterparty ledger. Real funding/settlement (turning the debt into a real transfer) is the escrow/reconciliation work of later 6.x sub-phases.
