# Phase 5.1 — Developer organization + inventory foundation design

_Date: 2026-09-02 · Branch: `claude/phase-5.1-developer-inventory` · Base: master `a7e8cc2` · Part of: Phase 5 (Product B — Developer CRM) · Depends on: Phase 1 (auth, listings), Phase 3.1 (the `apps/agent` cabinet pattern this mirrors)_

## 1. Goal

Stand up the developer (застройщик) side of the platform: a **new `apps/crm` SPA** where a
construction company manages its real inventory — its complexes (ЖК), buildings, and units. This is
Phase 5, part 1 ("developers put real inventory in"), the prerequisite that every later developer
feature builds on: the shaxmatka grid + booking (5.2), marketplace publishing of ЖК pages (5.3), and
the **C6 cross-CRM fixation** (5.4) all need a developer organization with real complexes/units to
exist first. A developer is modeled as an **Organization** with **Memberships** (a company with
members), distinct from the single-user realtor model. Onboarding is **free** in 5.1 (monetization is
a later concern); the gate is an active org membership. No money moves, nothing publishes to the
marketplace yet, and there is no shaxmatka/booking/fixation — just the org + inventory foundation and
the CRM shell.

## 2. Scope

1. **Data model** — `Organization` + `Membership` (+ `OrgRole`), the `Complex → Building → Unit`
   hierarchy (+ `ComplexStatus`, `UnitStatus`), and a new `DEVELOPER` value on `UserRole`.
2. **Access** — `POST /api/crm/become-developer` (creates the org + an OWNER membership + flips the
   role, in one transaction), a DB-fresh `DeveloperGuard` (role DEVELOPER + an active membership),
   and org-scoped ownership on every inventory query.
3. **API** — a `DeveloperModule` serving `/api/crm/*`: the org view + full CRUD for complexes,
   buildings, and units, all `DeveloperGuard`-gated and scoped to the caller's org.
4. **`apps/crm` SPA** — a new Vite/React workspace (`@rieltor/crm`) served at `/crm`, mirroring
   `apps/agent`: shared JWT auth, a login gate, a client-side developer guard + a become-developer
   page, and the inventory-management cabinet.
5. **Deploy wiring** — serve `apps/crm/dist` at `/crm` from the API (Express-level, like `/agent`);
   the Docker build path is updated; a Netlify-parity follow-up is noted (out of 5.1's runtime scope).

### Non-goals (later sub-phases / phases)

- **Shaxmatka grid + booking** — Phase 5.2. 5.1 renders units as a plain list/table, not the
  interactive status grid; there is no unit hold/booking.
- **Marketplace publishing + verified-developer badge (A12)** — Phase 5.3. 5.1 inventory is
  CRM-internal only; nothing appears on `apps/web`.
- **C6 cross-CRM fixation, commission (C7/C8)** — Phase 5.4.
- **Contracts, payment schedules, debtors, finance, KPI/reporting** — Phase 6 (§4.2/§4.3 of the
  platform spec).
- **Member invitations / multi-member management / branches / granular permissions** — a later
  sub-phase. 5.1 creates the org with a single OWNER; **one user belongs to one org**
  (`Membership.userId` is unique) — multi-org membership is deferred.
- **Developer monetization (pricing tiers, §4.7)** — later. Onboarding is free in 5.1.
- **A separate `Floor` model** — a `floor Int` on `Unit` is sufficient for 5.1 (the shaxmatka groups
  by floor in 5.2). YAGNI.
- The marketplace, realtor cabinet, and lead market — unchanged.

## 3. Data model (Prisma)

All additive. New models + two enum additions; no existing model changed except `User` gains a
`memberships` back-relation and `UserRole` gains `DEVELOPER`.

```prisma
enum UserRole { USER  REALTOR  DEVELOPER  MODERATOR  ADMIN }  // + DEVELOPER

enum OrgRole { OWNER  MANAGER }
enum ComplexStatus { PLANNED  UNDER_CONSTRUCTION  DONE }
enum UnitStatus { AVAILABLE  BOOKED  SOLD }

model Organization {
  id        String       @id @default(cuid())
  name      String
  district  String?                         // Tashkent district (marketplace list); optional at 5.1
  createdAt DateTime     @default(now())
  updatedAt DateTime     @updatedAt
  members   Membership[]
  complexes Complex[]
}

model Membership {
  id        String   @id @default(cuid())
  orgId     String
  org       Organization @relation(fields: [orgId], references: [id], onDelete: Cascade)
  userId    String   @unique                 // 5.1: one org per user
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  role      OrgRole  @default(OWNER)
  createdAt DateTime @default(now())
  @@unique([orgId, userId])
  @@index([orgId])
}

model Complex {
  id          String        @id @default(cuid())
  orgId       String
  org         Organization  @relation(fields: [orgId], references: [id], onDelete: Cascade)
  name        String
  district    String
  address     String?
  description String?
  status      ComplexStatus @default(UNDER_CONSTRUCTION)
  createdAt   DateTime      @default(now())
  updatedAt   DateTime      @updatedAt
  buildings   Building[]
  @@index([orgId])
}

model Building {
  id        String   @id @default(cuid())
  complexId String
  complex   Complex  @relation(fields: [complexId], references: [id], onDelete: Cascade)
  name      String
  floors    Int?                              // total floor count (helps the 5.2 shaxmatka)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  units     Unit[]
  @@index([complexId])
}

model Unit {
  id         String     @id @default(cuid())
  buildingId String
  building   Building   @relation(fields: [buildingId], references: [id], onDelete: Cascade)
  number     String                            // unit number/label, e.g. "42"
  floor      Int
  rooms      Int?
  areaM2     Float?
  priceSom   BigInt?                           // BigInt money, string end-to-end
  status     UnitStatus @default(AVAILABLE)
  createdAt  DateTime   @default(now())
  updatedAt  DateTime   @updatedAt
  @@index([buildingId])
}

// User gains: memberships Membership[]
```

`Organization → Complex → Building → Unit` cascade on delete (removing an org cleans its whole
inventory tree). `priceSom` is `BigInt` (serialized as a string, like every other money field). One
user maps to one org via `Membership.userId @unique` — the guard resolves the caller's org from that
single membership.

## 4. Access model

- **`POST /api/crm/become-developer`** (JwtGuard only — right after the upgrade the caller's JWT still
  says USER, exactly like `become-realtor`) body `{ name, district? }`: in ONE `$transaction`, set
  `user.role = 'DEVELOPER'`, create the `Organization`, and create a `Membership { role: OWNER }`
  linking the user. Idempotent — if the user already has a membership, return the existing org view
  (do not create a second). A crash between the writes must not strand a DEVELOPER with no org, so all
  three happen in the transaction (the `becomeRealtor` discipline).
- **`DeveloperGuard`** (mirrors `RealtorGuard`, DB-fresh — never trusts `req.user.role`): loads the
  user's `role` + whether a `Membership` exists; `role !== 'DEVELOPER'` → 403 ("Quruvchi emassiz");
  no membership → 403. **No subscription check** — membership is the entitlement. The guard only
  gates; it does not mutate the request.
- **Org scoping** — the `DeveloperService` takes the caller's `userId` as its **first argument**
  (from `@CurrentUser()`, never a client value) and resolves the `orgId` from that user's single
  `Membership` (the `Membership.userId @unique` makes this a one-row lookup). Every complex/building/
  unit query is then scoped to that `orgId`. Per-id routes use an `ownedOrThrow`-style check that
  walks the chain (unit → building → complex → org) and returns **404** (not 403) when the row
  belongs to another org — the `collections.service` idiom (foreign == missing), so a client can
  never read or mutate another org's inventory.

## 5. API (`DeveloperModule`, `/api/crm/*`)

All routes under `@UseGuards(JwtGuard, DeveloperGuard)` except `become-developer` (JwtGuard only).
The global `api` prefix makes the real URLs `/api/crm/*`; a `@Controller('crm')` does not collide with
the `/crm` SPA static route (which is served at the Express level, not under `/api`).

- **Org:** `POST /api/crm/become-developer` (JwtGuard); `GET /api/crm/org` → the caller's org +
  members (name, district, members `[{ userId, role, name?, phone }]`).
- **Complexes:** `GET /api/crm/complexes` (the org's complexes, newest first);
  `POST /api/crm/complexes` (`{ name, district, address?, description?, status? }`);
  `GET /api/crm/complexes/:id` (a complex + its buildings); `PATCH /api/crm/complexes/:id`;
  `DELETE /api/crm/complexes/:id`.
- **Buildings:** `POST /api/crm/complexes/:id/buildings` (`{ name, floors? }`);
  `PATCH /api/crm/buildings/:id`; `DELETE /api/crm/buildings/:id`.
- **Units:** `GET /api/crm/buildings/:id/units`; `POST /api/crm/buildings/:id/units`
  (`{ number, floor, rooms?, areaM2?, priceSom?, status? }`); `PATCH /api/crm/units/:id`;
  `DELETE /api/crm/units/:id`.

Shared Zod DTOs (in `packages/shared`): `OrgRole`/`ComplexStatus`/`UnitStatus` enums; `Organization`,
`Membership`/`OrgMember`, `Complex`, `ComplexDetail` (+ buildings), `Building`, `Unit` views; the
create/update inputs (`BecomeDeveloper`, `ComplexCreate`/`ComplexUpdate`, `BuildingCreate`/
`BuildingUpdate`, `UnitCreate`/`UnitUpdate`). `priceSom` is a string in every DTO.

## 6. `apps/crm` SPA (new workspace `@rieltor/crm`)

Mirrors `apps/agent` file-for-file where possible (the realtor cabinet is the reference build):

- **Workspace:** `apps/crm/package.json` (name `@rieltor/crm`, the same deps as `@rieltor/agent`),
  `vite.config.ts` with **`base: '/crm/'`** and a **unique dev port (5175)** + the `/api` + `/images`
  proxies, the three `tsconfig*.json`, `eslint.config.js` (the FSD `boundaries` flat config, its
  root path set to the crm package), `index.html` (`lang="uz"`), `src/main.tsx`. Auto-registered by
  the root `workspaces: ["apps/*"]` — no root edit; turbo fans out `build`/`typecheck`/`lint`/`test`.
- **`src/app`:** `providers.tsx` (QueryClient + RouterProvider, the same 403-handling defaults),
  `router.tsx` (`basename: '/crm'`; `RootLayout → DeveloperGuard → cabinet pages`, with the
  become-developer page reachable when the role is not yet DEVELOPER), `root-layout.tsx` (the shared
  login gate — reused verbatim), `developer-guard.tsx` (the client gate: `useSession` role check →
  `role === 'DEVELOPER'` else the become-developer page; no subscription/paywall), `index.css`
  (Tailwind 4 + tokens).
- **`src/shared/api/`:** `client.ts` + `auth-storage.ts` copied verbatim (same `rieltor.auth`
  localStorage key → one login serves web/agent/crm on the shared origin). `src/entities/session/`
  copied (the `useSession` → `/api/auth/me` hook).
- **Serving (API `bootstrap.ts`):** add a `/crm` block mirroring the `/agent` block —
  `crmDist = process.env.CRM_DIST ?? resolve(apiRoot, '..', 'crm', 'dist')`, `useStaticAssets(crmDist,
{ prefix: '/crm', index: false, redirect: false, maxAge: '1y', immutable: true })`, and an
  `index.html` SPA-fallback matching `req.path === '/crm' || startsWith('/crm/')`. `CRM_DIST` is read
  via `process.env` directly (no `envSchema` change, exactly like `AGENT_DIST`).

## 7. UI (`apps/crm`)

- **Become-developer** page (shown by the guard when `role !== 'DEVELOPER'`): a form to create the
  organization (`name`, `district`) → `POST /api/crm/become-developer` → on success seed/invalidate
  `['session']` (role now DEVELOPER) so the guard flips to the cabinet.
- **Cabinet:**
  - **Organization** — the org profile (name/district) + the members list (read-only in 5.1).
  - **Complexes** — a list of the org's complexes + a create form; each links to a complex detail.
  - **Complex detail** — the complex fields (editable) + its **buildings** list + a create form;
    each building links to its units.
  - **Building detail (units)** — a **units table** (number, floor, rooms, area, price, status) with
    add/edit/delete rows. Prices via the shared som formatter (`formatPriceSom(_, 'SALE')`).
  - Uzbek copy; English identifiers. Standard CRUD forms — the rich interactive shaxmatka is 5.2.

## 8. Modules & wiring

- `apps/api`: a `DeveloperModule` (`DeveloperController` for `/api/crm/*` + a `DeveloperService`
  holding the org-onboarding + inventory logic + `DeveloperGuard`); imports `AuthModule` (JwtGuard);
  exports `DeveloperGuard` (later sub-phases reuse it). Registered in `app.module.ts`. The `/crm`
  static serving lives in `bootstrap.ts` (not a controller).
- `packages/shared`: the DTOs in §5; `UserRole` mirror gains `DEVELOPER`.
- `apps/crm`: the new SPA (§6/§7).
- Deploy: `Dockerfile` gains `yarn workspace @rieltor/crm build` + the `apps/crm/dist` COPY (+ its
  `package.json` in the deps stage). **Netlify parity** (`netlify-build.sh` + `netlify.toml` +
  `netlify/functions/api.js` `CRM_DIST`) is a documented follow-up, not required for the 5.1
  server (Docker/Railway) runtime.

## 9. Constraints

- Uzbek user-facing copy; **English** identifiers/comments.
- **No new test files**; the existing suite (api 37 + e2e 22, web 34, shared 18 = 111) stays green,
  plus whatever the new `@rieltor/crm` workspace contributes (it ships no tests of its own).
- **Additive migration**; the only new env is `CRM_DIST` (read via `process.env`, no schema change,
  like `AGENT_DIST`).
- Inventory endpoints are **DeveloperGuard** (role DEVELOPER + active membership); every query is
  **org-scoped** (foreign rows → 404). `become-developer` is JwtGuard-only.
- BigInt money (`priceSom`) is serialized as a string end-to-end.
- `apps/crm` imports only `@rieltor/shared` + its own `@/*`; it never imports `apps/web`/`apps/agent`/
  `apps/api`. The FSD `boundaries` eslint config is enforced per package.
- The `/crm` SPA is served at the Express level (never a Nest controller), so it cannot collide with
  the `/api/crm/*` API — the same discipline the `/agent` SPA follows.

## 10. Verification

- Automated: `yarn lint`/`typecheck`/`build` (now 5 workspaces incl. `@rieltor/crm`); the existing
  suite green; additive migration.
- API (compiled-JS scratch): a USER calls `become-developer` → role DEVELOPER + an Organization + an
  OWNER Membership all exist (and a second call is idempotent — no duplicate org); `GET /api/crm/org`
  returns the org + the OWNER member; a non-developer USER hitting any `/api/crm/*` data route → 403;
  create a complex → building → unit and read them back (org-scoped); a second org's user cannot read/
  mutate the first org's complex/building/unit → 404; `priceSom` round-trips as a string; deleting a
  complex cascades its buildings + units.
- Web/CRM (browser smoke): build `apps/crm`, serve at `/crm`, log in (shared token), land on the
  become-developer page, create an org, then create a complex → building → units and see them listed;
  a realtor/plain user visiting `/crm` sees the become-developer gate (not the cabinet).

## 11. Risks

- **A whole new SPA is a large surface** — but it is a near-verbatim copy of `apps/agent` (auth,
  client, session, layout, guard, FSD). The risk is drift/omission, not novelty; the plan copies the
  agent files and changes only `base`/`basename`/port/guard.
- **Deploy parity** — the `/crm` serving works on the long-running server (Docker/Railway) but not on
  the current Netlify config (which never wired `/agent` either). This is a known, documented gap; the
  5.1 deliverable targets the server runtime. Do not silently assume Netlify serves `/crm`.
- **Org scoping is the security boundary** — a missing org filter would let one developer read/edit
  another's inventory. Every query filters by the caller's `orgId`, and per-id routes verify the
  ownership chain (unit→building→complex→org) returning 404 for a foreign row. The scratch must prove
  the cross-org 404s.
- **One-org-per-user simplification** — `Membership.userId @unique` keeps 5.1's guard trivial. If a
  real user must belong to multiple orgs later, this becomes a migration + a guard change; it is
  called out as a deliberate 5.1 boundary, not an oversight.
- **`DEVELOPER` role addition** — adding an enum value is additive and safe; the client `UserRole`
  mirror in `@rieltor/shared` must gain `DEVELOPER` in lockstep or `/api/auth/me` parsing breaks for a
  developer. The plan updates both together.
