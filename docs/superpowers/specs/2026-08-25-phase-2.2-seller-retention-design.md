# Phase 2.2 — Seller retention design

_Date: 2026-08-25 · Branch: `claude/phase-2.2-seller-retention` · Depends on: Phase 2.1 (valuation, merged to master `01931d6`)_

## 1. Goal

Turn the one-shot valuation from Phase 2.1 into a durable relationship: let an owner
**track a home's value over time**, get a **monthly update**, and let buyers post
**"Qidiryapman"** (reverse) requests that realtors and owners can answer. This closes the
seller side of the loop — a seller who valued their home once has a reason to come back
every month — and opens a demand-side board that feeds the marketplace.

## 2. Scope (all four features)

1. **"Mening uyim" cabinet** — a logged-in owner tracks one or more homes (from the
   valuation params), sees the current estimate and monthly delta.
2. **Price history** — a per-property chart. We have no historical price data, so the
   chart is seeded with a **modeled trailing curve** (clearly labelled) that real monthly
   snapshots replace over time.
3. **Monthly price notification** — an in-app inbox; a scheduled job recomputes each
   tracked property monthly and writes a `PRICE_UPDATE` notification with the % delta.
4. **"Qidiryapman" board** — buyers post what they want; realtors/owners browse, filter,
   and reveal the requester's contact (same masked-phone + lead-log pattern as listings).
   **Browsable board only — no auto-matching.**

### Non-goals (this phase)

- No auto-match notifications when a new listing fits an open request (deferred).
- No Telegram/SMS push for notifications — in-app inbox only (Telegram push waits for the
  Phase 2.3 bot; SMS waits for the Phase 1.1 provider).
- No manual "re-value now" button — the monthly cron is the only recompute trigger.
- The existing `/my/listings` cabinet and the `<1440px` mobile layouts are untouched.

## 3. Data model (Prisma)

Four new models, three new enums. All money is `BigInt` (som), mirrored as strings across
the wire like `priceSom`. FKs cascade from `User`.

```prisma
model TrackedProperty {
  id         String          @id @default(cuid())
  ownerId    String
  owner      User            @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  label      String?         // user nickname, e.g. "Mening kvartiram"
  type       ListingType
  district   String
  rooms      Int?            // null for COMMERCIAL, mirrors valuation
  areaM2     Float
  floor      String?
  createdAt  DateTime        @default(now())
  snapshots  PriceSnapshot[]
  @@index([ownerId])
}

enum SnapshotSource { MODELED  ACTUAL }

model PriceSnapshot {
  id                String          @id @default(cuid())
  trackedPropertyId String
  trackedProperty   TrackedProperty @relation(fields: [trackedPropertyId], references: [id], onDelete: Cascade)
  estimateSom       BigInt
  capturedAt        DateTime        @db.Date
  source            SnapshotSource
  @@index([trackedPropertyId, capturedAt])
}

enum NotificationType { PRICE_UPDATE }

model Notification {
  id        String           @id @default(cuid())
  userId    String
  user      User             @relation(fields: [userId], references: [id], onDelete: Cascade)
  type      NotificationType
  title     String
  body      String
  targetId  String?          // deep-link target, e.g. a trackedPropertyId
  readAt    DateTime?
  createdAt DateTime         @default(now())
  @@index([userId, createdAt])
}

enum RequestStatus { OPEN  CLOSED }

model PropertyRequest {
  id          String        @id @default(cuid())
  authorId    String
  author      User          @relation(fields: [authorId], references: [id], onDelete: Cascade)
  deal        Deal
  type        ListingType?  // null = any
  district    String?       // null = any
  roomsMin    Int?
  priceMaxSom BigInt?
  areaMinM2   Float?
  note        String?
  status      RequestStatus @default(OPEN)
  createdAt   DateTime      @default(now())
  @@index([status, createdAt])
}
```

`User` gains back-relations: `trackedProperties TrackedProperty[]`, `notifications
Notification[]`, `propertyRequests PropertyRequest[]`.

**Contact reveal for requests:** reuse the existing lead pattern. `ContactReveal` currently
requires `listingId`; make it `listingId String?` and add `requestId String?` (exactly one
set), so a request reveal is logged the same way a listing reveal is. Add
`@@index([requestId, createdAt])`.

## 4. Price-history modeling

A `TrackedProperty` is born with a full chart so day-one isn't a single dot:

- On create, call `ValuationService.estimate()` with the property params → today's
  `estimateSom` (an `ACTUAL` snapshot dated today).
- Generate **12 monthly `MODELED` snapshots** walking backwards from today:
  `value(monthsAgo) = round(today / (1 + g) ** monthsAgo)` where `g` is a documented
  constant monthly growth assumption (`MODELED_MONTHLY_GROWTH = 0.008`, ~10%/yr), living in
  `@rieltor/shared` config.
- Add a small **deterministic** per-property jitter (hash of `id` → ±0.4% per point) so the
  curve isn't a perfect exponential. Deterministic → the same property always renders the
  same history (no `Math.random`).
- The chart draws `MODELED` points as a dashed/lighter line with a "modellashtirilgan"
  legend; `ACTUAL` points (today's, plus everything the cron adds) as a solid line.
- Over the following months the cron appends `ACTUAL` snapshots; the solid line grows and
  the modeled tail ages out of the visible window.

## 5. Backend API (NestJS, global `api` prefix)

**Tracked properties** (JWT-guarded, owner-scoped):

- `POST /my/properties` — body = valuation params (+ optional `label`); creates the property,
  runs the valuation, writes the ACTUAL + 12 MODELED snapshots; returns the property with
  its latest estimate.
- `GET /my/properties` — the owner's properties, each with latest `estimateSom` and monthly
  delta (latest vs. one-month-prior snapshot) for the cabinet cards + sparkline points.
- `GET /my/properties/:id` — one property with its full snapshot series (chart data).
  404/403 if not the owner's.
- `DELETE /my/properties/:id` — stop tracking (cascades snapshots).

**Notifications** (JWT-guarded):

- `GET /my/notifications` — list newest-first + `unreadCount`.
- `POST /my/notifications/read-all` — mark all read (also `POST /my/notifications/:id/read`
  for a single item).

**Property requests ("Qidiryapman"):**

- `POST /requests` — create (JWT-guarded).
- `GET /requests` — public, filterable (`deal`, `type`, `district`, `roomsMin`,
  `priceMaxSom`); only `OPEN`; masked author phone in the payload.
- `GET /requests/:id` — public detail (masked phone).
- `POST /requests/:id/contact` — JWT-guarded; returns the author's real phone and logs a
  `ContactReveal(requestId=…)`.
- `PATCH /requests/:id` (close) and `DELETE /requests/:id` — author-only.
- `GET /my/requests` — the author's own requests (JWT-guarded).

New Nest modules: `PropertiesModule`, `NotificationsModule`, `RequestsModule` — each imports
`AuthModule` (for `JwtGuard`) and `PrismaModule`; `PropertiesModule` also depends on
`ValuationModule` (exporting `ValuationService`).

## 6. Monthly cron job

`@nestjs/schedule` (new dependency), `ScheduleModule.forRoot()` registered once.

`@Cron('0 3 1 * *')` (1st of month, 03:00) → for each `TrackedProperty`:

1. Recompute via `ValuationService.estimate()`.
2. Append an `ACTUAL` `PriceSnapshot` dated today.
3. If the estimate changed vs. the previous snapshot, write a `PRICE_UPDATE`
   `Notification` (`targetId = trackedPropertyId`, body carries the % delta).

Notes / risks:

- Single Docker instance → in-process cron is fine. Multiple instances would double-run;
  documented as a scale-time concern (needs a lock or external scheduler).
- With static seed data the monthly median barely moves (delta ≈ 0) — expected; real
  movement arrives with real listings, and the modeled tail carries the day-one visual.
- The job must be resilient: one property's valuation failing must not abort the batch.

## 7. Frontend (web — mobile-first, `desk:` for desktop)

**Pages** (`pages/*`, FSD):

- `my-properties` — `/my/properties` (cabinet: cards with label, district+type, estimate,
  monthly delta ▲/▼, mini-sparkline; empty state → `/valuation` CTA) and
  `/my/properties/:id` (big estimate + delta, full price chart, "E'lon joylash" →
  wizard prefilled, "Kuzatuvni to'xtatish").
- `notifications` — `/notifications` (list, read/unread, "Hammasini o'qilgan deb belgilash";
  row click → deep-link via `targetId`).
- `requests` — `/requests` (filter bar + request cards + reveal), `/requests/new` (form),
  `/my/requests` (own, with close/delete).

**Chart component:** `shared/ui/price-chart` — **dependency-free SVG** line chart matching
the project's library-free ethos (like the scroll-snap gallery). Renders a modeled
(dashed/lighter) segment + an actual (solid) segment, a light area fill, min/max labels, a
responsive `viewBox`. Reused as the cabinet mini-sparkline (compact, axis-less variant).

**Retention loop (2.1 → 2.2):** the valuation result screen gains a **"Uyni kuzatishga
qo'shish"** CTA — logged-in → `POST /my/properties` from the just-computed params → navigate
to `/my/properties/:id`; anonymous → open the login modal, then continue.

**FSD placement:**

- `entities`: `tracked-property`, `notification`, `property-request` (types, queries, card
  pieces).
- `features`: `track-property` (save action + button), `notification-bell` (badge),
  `request-contact-reveal` (reveal).
- `shared/ui`: `price-chart`.

**Navigation (existing `<1440px` untouched):** the 4-tab bottom nav is unchanged. Entry
points are additive — desktop header (`desk:`) gets a "Qidiryapman" link, a notification
bell with unread badge, and a "Mening uyim" account-menu item; mobile reaches the cabinet
from the valuation result and the account area, notifications from a bell in page headers,
and "Qidiryapman" from a home-page link.

## 8. Shared schemas (`@rieltor/shared`)

Single source of truth for both apps:
`TrackedPropertyCreateSchema`, `TrackedPropertySchema` (+ latest estimate + delta),
`PriceSnapshotSchema`, `TrackedPropertyDetailSchema` (with snapshot array),
`NotificationSchema` + `NotificationListSchema` (with `unreadCount`),
`PropertyRequestCreateSchema`, `PropertyRequestSummarySchema` (masked phone),
`PropertyRequestFilterSchema`, and the `MODELED_MONTHLY_GROWTH` constant.

## 9. Graceful degradation & edge cases

- Valuation already degrades without a Gemini key (Phase 2.1); tracked-property creation and
  the cron reuse `ValuationService`, so they inherit that — numbers always come back.
- A property in a zero-comparable market (valuation returns estimate `0`) must not create a
  misleading chart — treat estimate `0` as "not enough data" and surface it the same honest
  way the valuation page does, rather than plotting a flat-zero line.
- Empty states everywhere: no tracked properties, no notifications, no requests.
- Requests: masked phone for anonymous/unauthed; real phone only via the guarded reveal.

## 10. Verification approach

Same as Phase 2.1: subagent-driven development (implementer → reviewer → fix-loop), a
ledger as the source of truth. Per the project convention ([[no-tests-unless-asked]]) **no
new test files** — verify with `yarn lint`, `yarn typecheck`, the existing web/shared/API
unit + e2e suites staying green (currently 111 tests), plus `curl` and browser walks. When a
schema change ripples into demo fixtures, update them in the same task (Phase 1 lesson).

## 11. Deferred / future

- Auto-match notifications (new listing ↔ open request) — natural next use of the
  `Notification` model.
- Telegram/SMS delivery of notifications (Phase 2.3 bot / Phase 1.1 SMS).
- Multi-instance-safe scheduling (lock or external cron) at scale.
- Backlog memory (unchanged): title insurance, trade-in, insurance, contractor services.
