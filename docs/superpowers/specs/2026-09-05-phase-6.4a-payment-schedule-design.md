# Phase 6.4a — Payment schedule + payment recording (design)

**Status:** approved design, ready for planning
**Branch:** `claude/phase-6.4a-payment-schedule` (off master `25b5889`, the Phase 6.3 merge)
**Depends on:** 6.2 (Contract + agreedAmount), 6.3 (Contract status ACTIVE/CANCELLED)
**Roadmap:** Phase 6 — 6.1 org wallet → 6.2 Contracts → 6.3 clawback → **6.4 payment schedules + debtors + finance/KPI**, itself split: **6.4a payment schedule + payment recording** → 6.4b debtors + finance/KPI dashboard + reconciliation.

---

## 1. Goal

Give a Contract an **installment plan** and a way to **record collection against it**. A sale
(6.2 Contract) currently records only the agreed price; there is no way to track how the buyer
pays it off over time. 6.4a adds a `PaymentSchedule` (down payment + N equal monthly installments)
that a developer optionally attaches to an ACTIVE contract, plus a stub "mark installment paid"
that records a `Payment`. This is the collection foundation the 6.4b debtor register + finance/KPI
dashboard build on.

Real payment-provider integrations (Click, Payme, Uzum, Apelsin, Paylov), QR payment, and SMS are
partner-dependent and **deferred** (spec §4.2). Payments in 6.4a are recorded manually by the
developer — the same test-payment-stub posture as the wallet top-ups.

## 2. Scope

**In scope (6.4a):**

- `PaymentSchedule` (1:1 with a Contract) + generated `PaymentInstallment` items (down payment +
  N equal monthly installments; the items sum exactly to `agreedAmount`).
- A stub `Payment` recorded when the developer marks an installment paid.
- CRM: create/view/delete a schedule on a contract; mark an installment paid; a paid/total summary.

**Deferred (named, not built):**

- OVERDUE detection (cron) + **debtor register** → **6.4b**.
- **Finance/KPI dashboard** + commission reconciliation (net after clawbacks; `contractId` on the
  wallet ledger) → **6.4b**.
- Real payment providers / QR / bulk SMS / IP telephony (partner-dependent).
- Late-payment penalties + penalty waiver; partial payments (6.4a records one full-amount `Payment`
  per installment); schedule editing after creation (only delete-when-unpaid); multi-payment /
  payment-type / branch attribution.
- Buyer-facing payment view; automatic refund of collected installments when a sale is unwound (6.3
  cancel) — a business/6.4b concern (a cancelled contract's schedule simply becomes inert).

## 3. Design decisions (the four forks, resolved)

1. **6.4a foundation, then 6.4b reporting.** 6.4a = payment schedule + payment recording; 6.4b =
   debtors + finance/KPI dashboard + reconciliation. Each is a clean, mergeable unit.
2. **Down payment + N equal monthly installments**, auto-generated. The developer supplies the down
   payment, the installment count, and the start date; the last installment absorbs the rounding
   remainder so the items sum exactly to `agreedAmount`.
3. **Stub payment recording** — the developer marks an installment paid (`method = STUB`); a
   `Payment` row is written. Real providers deferred.
4. **Optional, developer-created on an ACTIVE contract.** Many sales are full-payment and need no
   schedule; the developer creates one when installments apply.

## 4. Data model (additive migration)

All changes are additive: three new enums, three new tables, two virtual back-relations. No change to
any existing table's columns.

```prisma
/// Installment payment frequency (6.4a). Monthly only for now; extensible.
enum PaymentFrequency {
  MONTHLY
}

/// Installment lifecycle (6.4a). PENDING until paid; OVERDUE is added in 6.4b.
enum InstallmentStatus {
  PENDING
  PAID
}

/// How a payment was recorded (6.4a). STUB = the developer marked it paid (no real provider);
/// real providers (Click/Payme/Uzum) are deferred.
enum PaymentMethod {
  STUB
}

/// A Contract's installment plan (6.4a): down payment + N equal monthly installments. One per
/// Contract. Generated PaymentInstallment items sum EXACTLY to the contract's agreedAmount
/// (down payment is item seq 0 when > 0; the last monthly installment absorbs the rounding remainder).
model PaymentSchedule {
  id               String               @id @default(cuid())
  contractId       String               @unique
  contract         Contract             @relation(fields: [contractId], references: [id], onDelete: Cascade)
  currency         Currency             @default(SOM)
  downPaymentSom   BigInt               @default(0)
  installmentCount Int                  // monthly installments (seq 1..N); >= 1
  installmentSom   BigInt               // the regular monthly amount (the last item may differ by the remainder)
  startDate        DateTime             // down-payment due date; first monthly installment = startDate + 1 month
  frequency        PaymentFrequency     @default(MONTHLY)
  installments     PaymentInstallment[]
  createdAt        DateTime             @default(now())
}

/// One due line. seq 0 = down payment (present only when downPaymentSom > 0); seq 1..N = monthly.
model PaymentInstallment {
  id         String            @id @default(cuid())
  scheduleId String
  schedule   PaymentSchedule   @relation(fields: [scheduleId], references: [id], onDelete: Cascade)
  seq        Int
  dueDate    DateTime
  amountSom  BigInt
  status     InstallmentStatus @default(PENDING)
  paidAt     DateTime?
  payment    Payment?
  createdAt  DateTime          @default(now())

  @@unique([scheduleId, seq])
  @@index([scheduleId])
}

/// A recorded payment against one installment (6.4a stub). Marking an installment PAID writes this.
model Payment {
  id            String             @id @default(cuid())
  installmentId String             @unique
  installment   PaymentInstallment @relation(fields: [installmentId], references: [id], onDelete: Cascade)
  amountSom     BigInt
  method        PaymentMethod      @default(STUB)
  note          String?
  createdById   String
  createdBy     User               @relation("RecordedPayments", fields: [createdById], references: [id], onDelete: Cascade)
  paidAt        DateTime           @default(now())
}
```

Back-relations to add (virtual): `Contract.paymentSchedule PaymentSchedule?`;
`User.recordedPayments Payment[] @relation("RecordedPayments")`.

Migration name: `phase_6_4a_payment_schedule`. `CREATE TYPE` ×3, `CREATE TABLE` ×3 (+ their
unique/index/FKs). No `ALTER`/`DROP` of any existing table. No data write.

### 4.1 Installment generation (the money math)

Given `agreedAmount = A` (must be non-null), `downPaymentSom = D` (0 ≤ D ≤ A), `installmentCount = N`
(1 ≤ N ≤ 600), `startDate = S`:

- `remaining = A − D`; `base = remaining / N` (BigInt floor division) → stored as `installmentSom`.
- Monthly items seq `1..N`: `amountSom = base`, except the **last** (seq N) `= remaining − base·(N−1)`
  (absorbs the remainder). `dueDate = S` plus `seq` whole months (UTC-safe month add).
- When `D > 0`: a seq-0 item, `amountSom = D`, `dueDate = S`.
- **Invariant:** `D + base·(N−1) + (remaining − base·(N−1)) = A` — the items sum EXACTLY to `A`.

All arithmetic is `BigInt`; money is serialized as string end-to-end.

## 5. Backend

### 5.1 Shared DTOs (`packages/shared/src/schemas.ts`)

```ts
export const PaymentFrequencySchema = z.enum(['MONTHLY']);
export const InstallmentStatusSchema = z.enum(['PENDING', 'PAID']);
export const PaymentMethodSchema = z.enum(['STUB']);

export const PaymentInstallmentSchema = z.object({
  id: z.string(),
  seq: z.number().int(),
  dueDate: z.string(),
  amountSom: z.string().regex(/^\d+$/),
  status: InstallmentStatusSchema,
  paidAt: z.string().nullable(),
});

/** A contract's schedule with its items + a paid/total summary. Named `…View` (like
 *  `OrgWalletView`) to avoid colliding with the Prisma `PaymentSchedule` model in the service. */
export const PaymentScheduleViewSchema = z.object({
  id: z.string(),
  contractId: z.string(),
  currency: CurrencySchema,
  downPaymentSom: z.string().regex(/^\d+$/),
  installmentCount: z.number().int(),
  installmentSom: z.string().regex(/^\d+$/),
  startDate: z.string(),
  frequency: PaymentFrequencySchema,
  installments: z.array(PaymentInstallmentSchema),
  totalSom: z.string().regex(/^\d+$/), // == agreedAmount
  paidSom: z.string().regex(/^\d+$/), // sum of PAID installments
  remainingSom: z.string().regex(/^\d+$/), // totalSom − paidSom
});

export const PaymentScheduleCreateSchema = z.object({
  downPaymentSom: z.string().regex(/^\d+$/),
  installmentCount: z.number().int().min(1).max(600),
  startDate: z.string(), // ISO date
});
export const PaymentRecordSchema = z.object({ note: z.string().max(500).optional() });
```

Plus the inferred types. `GET .../schedule` returns `PaymentScheduleViewSchema | null` (null when none).

### 5.2 PaymentScheduleService (`apps/api/src/developer/payment-schedule.service.ts`)

A new service, provider in `DeveloperModule`, injecting `PrismaService` + `DeveloperService`
(for `orgIdOf`). Org-scoping: a contract by `{ id, orgId }`; an installment by
`{ id, schedule: { contract: { orgId } } }` — a foreign/missing id → 404.

- `create(orgId, contractId, input): Promise<PaymentScheduleView>` — in one `$transaction`: load the
  contract `{ id, orgId }` (404), require `status === 'ACTIVE'` (409 on CANCELLED) and
  `agreedAmount != null` (400 `Kelishilgan summa yo'q`) and no existing schedule (409); validate
  `0 ≤ downPaymentSom ≤ agreedAmount`; create the `PaymentSchedule` + generate the
  `PaymentInstallment` items per §4.1 (`createMany`); return the view. `PaymentSchedule.contractId
@unique` is the backstop against a concurrent double-create.
- `getForContract(orgId, contractId): Promise<PaymentScheduleView | null>` — org-scoped; null if none.
- `remove(orgId, contractId): Promise<void>` — org-scoped; only when NO installment is PAID (else 409
  `To'lov qayd etilgan jadvalni o'chirib bo'lmaydi`); cascade-deletes the items.
- `pay(orgId, installmentId, note?): Promise<PaymentScheduleView>` — in one `$transaction`: load the
  installment org-scoped (404), require its schedule's contract `status === 'ACTIVE'` (409) and the
  installment `status === 'PENDING'` (409 `Ulush allaqachon to'langan`); create a `Payment`
  (`amountSom = installment.amountSom`, `method = STUB`, `createdById = caller`) and flip the
  installment to `PAID` + `paidAt`. `Payment.installmentId @unique` is the idempotency backstop.
  Returns the fresh schedule view.

the `PaymentScheduleView` DTO is mapped with money as `String(bigint)`, dates as ISO; `totalSom` = sum of all
items (== agreedAmount), `paidSom` = sum of PAID items, `remainingSom` = total − paid.

### 5.3 Controller (`apps/api/src/developer/payment-schedule.controller.ts`)

`@Controller('crm')` + `@UseGuards(JwtGuard, DeveloperGuard)`, resolving `orgIdOf(u.id)`:

- `POST   /api/crm/contracts/:id/schedule` → `create(orgId, id, PaymentScheduleCreateSchema.parse(body))`
- `GET    /api/crm/contracts/:id/schedule` → `getForContract(orgId, id)`
- `DELETE /api/crm/contracts/:id/schedule` → `remove(orgId, id)`
- `POST   /api/crm/installments/:id/pay` → `pay(orgId, id, PaymentRecordSchema.parse(body).note)`

Registered in `DeveloperModule.controllers` + the service in `providers`.

## 7. Rulings & invariants (load-bearing)

- **R1 — items sum EXACTLY to agreedAmount.** Down payment (seq 0 when > 0) + N monthly installments,
  the last absorbing the BigInt-division remainder → `Σ items = agreedAmount`. No money is created or
  lost by rounding.
- **R2 — one schedule per contract.** `PaymentSchedule.contractId @unique`; create only on an ACTIVE
  contract with `agreedAmount != null` and no existing schedule.
- **R3 — pay is idempotent + gated.** `Payment.installmentId @unique`; `pay` requires the installment
  `PENDING` and the contract `ACTIVE` (a re-fired/duplicate pay → 409, no second Payment). The
  recorded `amountSom` equals the installment amount (full-amount stub; no partials in 6.4a).
- **R4 — org-scoping.** Every schedule/installment op is gated by `orgId = orgIdOf(caller)` (contract
  by `{id, orgId}`; installment by `{id, schedule:{contract:{orgId}}}`); a foreign/missing id → 404.
- **R5 — delete only when unpaid.** `remove` refuses (409) once any installment is PAID (a recorded
  Payment is real money collected).
- **R6 — additive-only + money-as-string.** Three enums + three tables + two virtual back-relations;
  no existing-table column change; all amounts `String(bigint)` / `z.string().regex(/^\d+$/)`.
- **R7 — a cancelled contract's schedule is inert.** Schedule/pay ops require the contract ACTIVE, so
  a 6.3-cancelled contract's schedule can no longer take payments; no 6.3-cancel change is made in 6.4a
  (installment refunds on unwind are a 6.4b/business concern).
