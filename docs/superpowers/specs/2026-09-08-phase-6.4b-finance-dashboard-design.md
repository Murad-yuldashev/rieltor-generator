# Phase 6.4b — Debtors + finance/KPI dashboard (design)

**Status:** approved design, ready for planning
**Branch:** `claude/phase-6.4b-finance-dashboard` (off master `535a196`, the Phase 6.4a merge)
**Depends on:** 6.4a (PaymentSchedule/Installment/Payment), 6.1/6.3 (org wallet ledger: COMMISSION_DEBIT/REFUND)
**Roadmap:** Phase 6 — 6.1 org wallet → 6.2 Contracts → 6.3 clawback → 6.4 (6.4a payment schedule → **6.4b debtors + finance/KPI dashboard**). This is the last Phase-6 sub-phase.

---

## 1. Goal

Give the developer an org-level **finance snapshot** and a **debtor register** over the payment
schedules built in 6.4a. Today the installment data exists per-contract but there is no aggregate
view: how much is contracted, collected, outstanding, overdue; who is behind on payments; and what
the net commission cost is after clawbacks. 6.4b adds a read-only finance dashboard + debtor list.

This is a **pure read-only reporting layer**: NO schema change, NO migration, NO money-path change
(convert/cancel untouched), NO cron. Overdue is computed at read time; net commission is derived
from the existing org wallet ledger.

## 2. Scope

**In scope (6.4b):**

- An org **finance summary** (`GET /api/crm/finance`): contracted / collected / outstanding /
  overdue totals over the org's schedules + net commission (from the org wallet ledger) + org balance.
- A **debtor register** (`GET /api/crm/debtors`): the org's contracts with ≥1 overdue installment.
- A CRM **"Moliya"** page (summary cards + debtor table) + a nav tab.

**Deferred (named, not built):**

- Stored `OVERDUE` installment status + a marking cron (6.4b computes overdue on read).
- Debtor **bulk SMS + task assignment** (§4.2 — partner-dependent / heavy).
- **Plan-vs-fact reporting, sales targets, employee KPI** (§4.2 — needs a targets model; heavier).
- **`contractId` on the wallet ledger** for per-contract commission attribution (org-level net
  commission is derivable from the existing ledger without it).
- A platform-wide (moderation) finance view; unscheduled full-payment sales in the collection metrics
  (out of the installment domain); real payment providers.

## 3. Design decisions (the four forks, resolved)

1. **Overdue computed on read** — `installment.status === 'PENDING' && dueDate < now` (server request
   time). No `OVERDUE` enum, no cron, no touch to the 6.4a `pay` gate (an overdue-but-unpaid
   installment stays `PENDING`).
2. **Debtor register = a CRM read-only list.** Bulk SMS / task assignment deferred.
3. **Dashboard = an org-level aggregate summary.** Plan-vs-fact / targets / employee KPI deferred.
4. **No `contractId` on the ledger.** Net commission = `Σ COMMISSION_DEBIT − Σ COMMISSION_REFUND`
   from the existing org wallet ledger; the money-path code (convert/cancel) is not touched.

## 4. Data model

**No change.** 6.4b is pure aggregation over existing tables (PaymentSchedule / PaymentInstallment /
Payment / Contract / OrgWallet / OrgWalletTransaction). No migration.

## 5. Backend

### 5.1 Shared DTOs (`packages/shared/src/schemas.ts`)

```ts
/** Org finance snapshot over the payment schedules + the org wallet ledger. */
export const FinanceSummarySchema = z.object({
  contractedSom: z.string().regex(/^\d+$/), // Σ all installment amounts (== Σ scheduled agreedAmount)
  collectedSom: z.string().regex(/^\d+$/), // Σ PAID installments
  outstandingSom: z.string().regex(/^\d+$/), // contracted − collected
  overdueSom: z.string().regex(/^\d+$/), // Σ PENDING installments with dueDate < now
  scheduleCount: z.number().int(), // schedules in the org
  debtorCount: z.number().int(), // contracts with ≥1 overdue installment
  commissionPaidSom: z.string().regex(/^\d+$/), // net: Σ COMMISSION_DEBIT − Σ COMMISSION_REFUND (≥ 0)
  orgBalanceSom: z.string().regex(/^-?\d+$/), // cached org wallet balance (MAY be negative = debt)
});

/** One debtor row: a contract with overdue installments. */
export const DebtorRowSchema = z.object({
  contractId: z.string(),
  contractNumber: z.string(),
  buyerName: z.string(),
  buyerPhone: z.string(),
  overdueSom: z.string().regex(/^\d+$/), // Σ overdue installments for this contract
  oldestDueDate: z.string(), // earliest overdue dueDate (ISO)
  remainingSom: z.string().regex(/^\d+$/), // Σ non-PAID installments for this contract
});
```

Plus the inferred types `FinanceSummary`, `DebtorRow`.

### 5.2 FinanceService (`apps/api/src/developer/finance.service.ts`)

A new service, provider in `DeveloperModule`, injecting `PrismaService`. All queries are org-scoped
(installments via `schedule.contract.orgId`; ledger via `orgWallet.orgId`). `now = new Date()` at the
start of the call so every metric uses one consistent instant.

- `summary(orgId): Promise<FinanceSummary>`:
  - `contracted` = `installment.aggregate({ where: { schedule: { contract: { orgId, status: 'ACTIVE' } } }, _sum: { amountSom } })`. **All collection/debtor queries filter `contract.status === 'ACTIVE'`** (a cancelled sale is not a live obligation — see R4); the ledger/commission queries do NOT (net commission already reflects a cancellation via its REFUND).
  - `collected` = same with `status: 'PAID'`.
  - `overdue` = same with `status: 'PENDING', dueDate: { lt: now }`.
  - `outstanding = contracted − collected`.
  - `scheduleCount` = `paymentSchedule.count({ where: { contract: { orgId } } })`.
  - `debtorCount` = count of DISTINCT contracts with an overdue installment (a `paymentSchedule.count`
    with `where: { contract: { orgId }, installments: { some: { status: 'PENDING', dueDate: { lt: now } } } }`
    — one schedule per contract, so a schedule count == a contract count).
  - `commissionPaid` = `orgWalletTransaction.aggregate({ where: { orgWallet: { orgId }, type: 'COMMISSION_DEBIT' }, _sum })` − the same for `COMMISSION_REFUND` (net ≥ 0 by construction — every refund reverses a prior debit), **clamped to ≥ 0** so a ledger anomaly can't emit a negative string that would fail the non-negative DTO.
  - `orgBalance` = `orgWallet.findUnique({ where: { orgId } })?.balanceSom ?? 0n` (no wallet yet → 0).
  - Each `_sum.amountSom` is `bigint | null` → coalesce to `0n`; serialize all as `String(bigint)`.
- `debtors(orgId): Promise<DebtorRow[]>`:
  - `paymentSchedule.findMany({ where: { contract: { orgId }, installments: { some: { status: 'PENDING', dueDate: { lt: now } } } }, include: { contract: { select: { id, number, buyerName, buyerPhone } }, installments: { select: { amountSom: true, status: true, dueDate: true } } } })`.
  - Per schedule: `overdue` = installments where `status==='PENDING' && dueDate < now` → `overdueSom = Σ`, `oldestDueDate = min(dueDate)`; `remainingSom = Σ (status !== 'PAID')`. Map to `DebtorRow`. Sort by `oldestDueDate` ascending (most overdue first).

### 5.3 Controller (`apps/api/src/developer/finance.controller.ts`)

`@Controller('crm')` + `@UseGuards(JwtGuard, DeveloperGuard)`, resolving `orgIdOf(u.id)`:

- `GET /api/crm/finance` → `summary(orgId)`
- `GET /api/crm/debtors` → `debtors(orgId)`

Registered in `DeveloperModule` (provider + controller). `@Controller('crm')` + `finance`/`debtors`
paths do not collide with the existing crm routes (established multi-`@Controller('crm')` pattern).

## 7. Rulings & invariants (load-bearing)

- **R1 — read-only.** No schema change, no migration, no money-path change, no cron. Every endpoint is a
  pure aggregation of existing rows.
- **R2 — overdue computed at request time.** `PENDING && dueDate < now`; `now` captured once per call so
  summary + debtors agree.
- **R3 — org-scoping.** Every aggregate filters by the caller's org (installments via
  `schedule.contract.orgId`, ledger via `orgWallet.orgId`); a foreign org's data is never counted or listed.
- **R4 — collection totals over the installment domain, ACTIVE contracts only.** `contractedSom == Σ installments of the org's ACTIVE scheduled contracts`
  (by the 6.4a sum invariant). The collection + debtor queries filter `contract.status === 'ACTIVE'`, so a
  6.3-CANCELLED sale (unwound, unit re-sellable, commission already reversed via COMMISSION_REFUND) does
  NOT inflate contracted/overdue or surface a phantom debtor — keeping the collection side consistent with
  the commission side. Full-payment (unscheduled) contracts are out of scope.
- **R5 — net commission from the existing ledger.** `commissionPaidSom = Σ COMMISSION_DEBIT −
Σ COMMISSION_REFUND` (≥ 0); the money-path is not touched.
- **R6 — money as string.** BigInt `_sum` coalesced (`?? 0n`) and serialized `String(bigint)`;
  `orgBalanceSom` allows a leading `-` (debt).

## 8. Verification (no new test files — per project rule)

- `yarn typecheck` + `yarn lint` green across api / shared / crm.
- Compiled-JS scratch against a real `nest build` (never `tsx`): seed an org with a few contracts +
  schedules; mark some installments PAID; set some installment dueDates in the past (PENDING) →
  (a) `summary` returns contracted = Σ all installments, collected = Σ PAID, outstanding = contracted −
  collected, overdue = Σ past-due PENDING, scheduleCount + debtorCount correct; (b) net commission =
  Σ COMMISSION_DEBIT − Σ COMMISSION_REFUND — a convert-only org (net == debit total, hitting the
  refund-null branch) AND a convert+cancel org (net == debit − refund); orgBalance = the cached
  balance (incl. a negative debt case); (c) `debtors` lists only contracts with overdue installments,
  each row's overdueSom/oldestDueDate/remainingSom correct, sorted oldest-first — include a debtor with
  a PENDING FUTURE-due installment and assert `remainingSom > overdueSom` (remaining counts it, overdue
  does not);
  (d) a SECOND org's contracts/installments/ledger are NEVER counted or listed (org isolation);
  (e) an org with no schedules → all-zero summary, empty debtors, no crash.
- Browser smoke: the CRM "Moliya" page renders the cards + debtor table for a seeded org.
- Full suite green before merge (shared 18, web 34, api 37, e2e 22 → 111), zero new test files.
