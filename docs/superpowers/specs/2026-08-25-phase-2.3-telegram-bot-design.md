# Phase 2.3 — Telegram bot design

_Date: 2026-08-25 · Branch: `claude/phase-2.3-telegram-bot` · Base: master `344b78c` · Depends on: Phase 2.1 (valuation), Phase 2.2 (notifications)_

## 1. Goal

A Telegram bot that is a **new delivery channel over existing services** — users get a
free valuation, create a listing (with photos) through a chat wizard, and receive their
monthly price notifications as Telegram DMs. No new business logic: the bot reuses
`ValuationService`, `ListingsService`, `processImage`, and the notification path.

## 2. Scope (full bot)

1. **Valuation in chat** — reuses `ValuationService.estimate`.
2. **Listing creation in chat** — a conversational wizard mirroring the 6-step web wizard,
   including photo upload, that creates a DRAFT and submits it to moderation
   (`ListingsService`).
3. **"Mening e'lonlarim"** — list the user's listings (`ListingsService.listMine`).
4. **Notification DM delivery** — the Phase 2.2 monthly cron's `PRICE_UPDATE` notifications
   are also sent as Telegram DMs to users who have a `telegramId` (the deferred
   "Telegram push" from Phase 2.2).

### Non-goals

- No webhook mode (long-polling only; webhook is a scale-time swap).
- No AI description in the bot wizard (manual text; the web wizard keeps the AI button).
- No payments, no inline-mode search, no group-chat features.
- Session state is in-memory (single instance); Redis-backed sessions are a scale-time item.

## 3. Library & connection

- **`nestjs-telegraf`** (Telegraf integrated with NestJS DI) — `@Update()` classes,
  `@Command`/`@Action`/`@On` handlers, `@Ctx()` injection. Long-polling.
- The plan verifies `nestjs-telegraf` installs and works on NestJS 11; **fallback**: if it
  is incompatible, wrap raw `telegraf` in a plain Nest `@Injectable()` service that owns the
  `Telegraf` instance and registers handlers in `onModuleInit`. The rest of this design
  (scenes, reuse, degradation) is identical either way.

## 4. Graceful degradation (no bot crash without a real token)

The bot must never stop the API from booting when `TELEGRAM_BOT_TOKEN` is a placeholder
(dev, CI, or a not-yet-created bot):

- Register the bot with **auto-launch disabled** (`launchOptions: false` in nestjs-telegraf,
  or simply do not call `bot.launch()` unconditionally).
- A `BotService.onModuleInit()` calls `bot.launch()` inside **try/catch**; a failure (invalid
  token → Telegram 401, or a network error) is logged at `warn` and swallowed, so the app
  boots and every HTTP endpoint keeps working. The bot is simply dormant.
- The DM hook checks the bot is live (e.g. `bot.botInfo != null` after a successful launch, or
  a `botReady` boolean the service sets) before calling `sendMessage`; when dormant, only the
  in-app notification is written (today's behaviour). This mirrors the Gemini degradation.

## 5. Identity — auto-provision a User from the Telegram sender

Every bot interaction has `ctx.from.id` (the Telegram numeric id). The bot ensures a platform
`User` exists for it, mirroring the existing Telegram-Login flow in `auth.service.ts`
(find by `telegramId`, else create `{ telegramId, name: from.first_name, phone: 'tg:'+id }`).
Extract that "ensure user from telegram id" logic into a shared `AuthService` method the bot
calls, so login and bot cannot drift. The resolved `userId` owns the drafts the bot creates
and is the key for `listMine` — no separate bot-auth.

## 6. Conversation model

`session` middleware holds per-user wizard state (in-memory). `/start` shows the main menu
(inline keyboard): **🏡 Uyni baholash · ➕ E'lon joylash · 📋 Mening e'lonlarim**.

### 6.1 Valuation scene (reuses `ValuationService`)

Steps as inline-button / text prompts: `type` (NEW_BUILD/SECONDARY/HOUSE/COMMERCIAL) →
`district` (from `@rieltor/shared` `TASHKENT_DISTRICTS`) → `rooms` (skipped for COMMERCIAL) →
`areaM2` (numeric text). Then `ValuationService.estimate({ type, district, rooms, areaM2 })`
and reply with the estimate, low–high range, and the Uzbek explanation — identical output to
the web page. Follow-up buttons: "E'lon joylash" (enter the listing scene), "Qayta hisoblash".

### 6.2 Listing wizard scene (reuses `ListingsService`)

Auto-provision the user, `createDraft(userId)` → `draftId`, then walk the same fields the web
wizard collects, PATCHing as it goes and submitting at the end:

`deal` → `type` → `address` (text) → `landmark` (text) → `rooms`/`areaM2`/`floor` →
**photos** → `title` (text) → `description` (text) → `priceSom` (numeric text) →
`ListingsService.submitForModeration(draftId, userId)` → "E'loningiz moderatsiyaga yuborildi".

**Photos** are the one genuinely new mechanic: when the user sends a photo, take the largest
`file_id`, `ctx.telegram.getFileLink(file_id)`, fetch it into a `Buffer`, adapt it to the
`Express.Multer.File` shape `addImage` already accepts (`{ buffer, originalname, mimetype:
'image/jpeg', size, fieldname: 'file' }`), and call `ListingsService.addImage(draftId, userId,
file)` — which runs the same `processImage` sharp pipeline as the web upload. Cap at 10 (the
web limit); "Tayyor" ends the photo step. If `addImage` cannot accept a hand-built Multer file,
add a thin `addImageBuffer(draftId, userId, buffer)` beside it that calls `processImage`
directly — the plan decides after reading the method.

### 6.3 "Mening e'lonlarim"

`ListingsService.listMine(userId)` → a text list with status labels and a link to each
listing's public page (`${PUBLIC_BASE_URL}/obj/:id`).

## 7. Notification DM hook (Phase 2.2 completion)

Introduce `NotificationsService.notify(userId, { type, title, body, targetId })` that (1)
writes the `Notification` row (today's behaviour), and (2) if the user has a `telegramId` **and
the bot is live**, sends `bot.telegram.sendMessage(telegramId, body)`. The Phase 2.2 monthly
cron (`PropertiesService.runMonthlyValuation`) calls `notify()` instead of
`prisma.notification.create` directly. The bot capability is injected behind a small interface
so `NotificationsModule`/`PropertiesModule` don't hard-depend on Telegraf and the DM is
skipped cleanly when the bot is dormant.

## 8. Modules & wiring

- New `apps/api/src/bot/` — `bot.module.ts` (TelegrafModule.forRootAsync + providers),
  `bot.service.ts` (launch guard + `sendMessage` capability + user-provision helper use),
  `bot.update.ts` (`/start`, menu actions), `valuation.scene.ts`, `listing.scene.ts`,
  `telegram-photo.ts` (file_id → Buffer → Multer.File adapter).
- `BotModule` imports `AuthModule` (user provision), `ValuationModule`, `ListingsModule`,
  `NotificationsModule`; `app.module.ts` registers `BotModule`.
- New env: `TELEGRAM_BOT_TOKEN` already exists (reused for both Login HMAC and the bot).
  Optional `TELEGRAM_BOT_ENABLED` is **not** added — the try/catch launch is the switch.

## 9. Constraints

- Uzbek user-facing copy; English identifiers/comments.
- Money as strings on the wire is irrelevant here (the bot talks to services directly), but the
  bot must format som with the shared `formatPriceSom`.
- **No new test files** ([[no-tests-unless-asked]]); the existing 111-test suite stays green.
  Verify with `yarn lint`, `yarn typecheck`, `yarn build`, API unit + e2e, and a `nest build`
  scratch that boots the app context with a placeholder token and confirms: the app starts, the
  bot logs a dormant/launch-failed warning without throwing, and existing endpoints still
  respond. **CI note:** the Docker image and the `check`/`e2e` jobs already set a placeholder
  `TELEGRAM_BOT_TOKEN`; the bot must stay dormant there so CI stays green ([[ci-gotchas]]).
- FSD/Nest module boundaries: the bot depends on services, not the reverse (except the DM
  capability injected behind an interface).

## 10. Verification & live test

- Automated: app boots with the bot dormant (placeholder token), suite green, no endpoint
  regressions.
- Live (manual, by the user): create a bot via **@BotFather**, put its token in
  `TELEGRAM_BOT_TOKEN`, restart the API; then in Telegram: `/start` → valuation → estimate;
  `/start` → listing wizard → send photos → submit → confirm the DRAFT appears in the web
  moderation queue; run the monthly cron and confirm a linked user gets the DM.

## 11. Risks

- **`nestjs-telegraf` on NestJS 11** — may lag the Nest major; the raw-Telegraf-in-a-service
  fallback removes the risk at the cost of a little boilerplate.
- **Photo pipeline** — Telegram file download + hand-built Multer file feeding `processImage`
  is the most likely place for a mismatch; verify the `addImage` input shape early.
- **In-memory sessions** — a restart drops in-progress wizards; acceptable for v1, Redis at scale.
- **Long-polling in one container** — the poller runs beside the HTTP server; a launch that
  succeeds then loses connectivity should not crash the process (Telegraf handles reconnms; the
  launch guard covers startup).
- **Cannot be E2E-tested in CI** (no real bot) — logic is exercised via the app-boot scratch and
  the reused services' existing tests; live validation is the user's manual pass.
