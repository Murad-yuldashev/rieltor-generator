# Phase 5.3 — Marketplace publishing (A12 ЖК pages + verified developer) Design

**Status:** Draft for review
**Date:** 2026-09-03
**Feature code:** A12 (platform-spec L152) — Residential-complex (ЖК) pages + verified-developer badge
**Depends on:** Phase 5.1 (Organization/Membership + Complex→Building→Unit inventory), Phase 5.2 (shaxmatka + Booking), Phase 4.2/4.3 (lead purchase/wallet + scoring/conversion)

---

## 1. Goal

Cross the CRM→marketplace boundary for the first time: let a developer (застройщик) **publish** a Complex from the `/crm` cabinet so it appears on the public web marketplace as a **ЖК page** buyers can browse, showing live per-unit availability (shaxmatka), a **verified-developer** trust badge, cover + gallery imagery, and a map pin. A buyer's inquiry on a ЖК becomes a scored **lead** (`PropertyRequest`, type `NEW_BUILD`) that flows into the existing realtor claim/purchase pipeline — closing the loop from developer inventory to realtor monetization.

Phase-5 deliverable framing (platform-spec L349): _"developers put real inventory in."_ 5.3 is the publish/expose layer on top of the 5.1/5.2 inventory the developer already manages — **no new inventory concept**, only visibility + a public read surface + buyer inquiry.

## 2. Scope decisions (locked with product owner)

| Fork               | Decision                                                                                                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Public depth**   | ЖК page **+ live availability** — the public detail page shows a read-only shaxmatka (per-unit AVAILABLE/BOOKED/SOLD, floor, rooms, area, price).                                               |
| **Verified badge** | **Moderator approval flow** — developer requests verification; a MODERATOR/ADMIN grants it (mirrors the existing realtor-verification flow). Badge lives on **Organization** (whole developer). |
| **Inquiry → lead** | Buyer inquiry **creates a `PropertyRequest` lead** (type `NEW_BUILD`, linked to the complex) that enters the realtor claim/purchase pipeline (closed loop).                                     |
| **Media / geo**    | Add **cover + gallery + geo** — a `ComplexImage` relation (reusing the existing webp image pipeline) + `latitude`/`longitude` on Complex.                                                       |

## 3. Design rulings (load-bearing — please confirm at review)

These resolve the map's open questions. Each is a deliberate choice to keep 5.3 shippable and consistent with existing patterns.

1. **Publish is a developer self-service toggle, gated on verification** — not a per-complex moderation queue. A Complex flips `DRAFT ↔ PUBLISHED` from the CRM. Publishing is **allowed only when** (a) the owning Organization is `verified === true`, **and** (b) a data-completeness gate passes (≥1 cover image, ≥1 `AVAILABLE` unit with `priceSom`, `district` present). This gives moderators exactly **one** control point (verify the developer); after that the developer manages their own ЖК visibility. Rejected/incomplete → `409` with a specific Uzbek message. Unpublish is always allowed.
2. **Verified is Organization-level**, granted by a moderator (mirrors realtor `verified`). The ЖК page renders a green _"Tasdiqlangan quruvchi"_ badge when `complex.org.verified`.
3. **The public ЖК is its own read surface, NOT projected into the `/api/objects` search feed.** Units surface only _within_ the ЖК page + the `/jk` browse. Auto-listing individual units into the general object search is **deferred**. This bounds scope and avoids reshaping the listing/seller model.
4. **Buyer inquiry requires the buyer to be signed in** (JwtGuard), because a `PropertyRequest` has a required `author` (User) and a claimable lead must reference a real person. The signed-in buyer _is_ the seeker. Anonymous "reveal developer contact" is a possible future lighter path (not in 5.3).
5. **Images reuse the existing webp pipeline** via a new `ComplexImage` model (mirrors `Image`); a dedicated developer upload endpoint mirrors the listing image upload. (A new model rather than extending `Image` because `Image.listingId` is non-null — adding a Complex image there would require a destructive column change.) **Reuse is at the `apps/api/src/listings/process-image.ts::processImage` level only** — that function is model-agnostic (its `listingId` arg is used solely as a `/images/<id>/<nn>` path segment, so passing `"complex/<cuid>"` yields the `/images/complex/<cuid>/01` base). `ListingsService.addImage/addImageBuffer` are Listing-coupled (owner/status/count checks over `prisma.image`) and are **not** reused; the Complex image service re-implements that thin add-logic around `processImage`, writing `ComplexImage` rows.
6. **Slug** is auto-generated from the complex name at first publish (kebab, uniqueness-suffixed), validated by the existing realtor-slug regex shape. Developer-chosen slugs are deferred.
7. **Additive migration only** — new enum + new fields + new model + nullable FKs; no existing column altered/dropped (the project's one-migration-per-phase additive cadence).

## 4. Non-goals (explicitly deferred)

- **Rich A12 content** — documents, construction-progress timeline, installment/ipoteka terms (A12 lists these; construction timeline is Product-B §4.5, installments are Finance §4.2 / Phase 6). 5.3 ships the **badge + ЖК page + unit availability + inquiry + cover/gallery/geo**; the rich content blocks come later.
- **Individual units as searchable `Listing` rows** in `/api/objects` (ruling 3).
- **A national viloyat/region taxonomy** — `Complex.district` stays free-text with the existing `TASHKENT_DISTRICTS` facet; a country-wide region enum is a later cross-cutting change.
- **A public developer-profile page** (`/developer/:slug`) — the developer is shown _on_ the ЖК page (name + verified badge) only; a standalone microsite like `/r/:slug` is deferred.
- **Server-side pagination/filtering** for the public list — follows the existing `/api/objects` fetch-all + client-filter convention (revisit when catalog size demands it).
- **C6 cross-CRM fixation / commission** — Phase 5.4.
- **MANAGER invites / multi-user orgs** — still one-user-one-org (5.1 baseline).

## 5. Architecture & data flow

```
Developer (CRM /crm)                Moderator (web /moderation)         Buyer (web /jk)
──────────────────                  ───────────────────────────         ───────────────
1. build inventory (5.1/5.2)
2. upload cover+gallery ─┐
3. request verification ─┼──────►   4. review queue → verify org
                         │              (Organization.verified=true)
5. Publish complex ◄─────┘  (gated: org.verified && completeness)
      │
      ▼  Complex.publishStatus = PUBLISHED, slug set, publishedAt
   GET /api/jk  ────────────────────────────────────────────────────►  6. browse ЖК list
   GET /api/jk/:slug ─────────────────────────────────────────────►     7. ЖК detail
                                                                             (gallery, verified
                                                                              badge, price-from,
                                                                              availability grid)
                                                                         8. POST /api/jk/:slug/inquiry
                                                                             (JwtGuard)
                                                                                │
                                                                                ▼
                                            PropertyRequest {type:NEW_BUILD, complexId, ...}
                                            scored (computeLeadScore + conversionAdjustment)
                                                                                │
                                                                                ▼
                                            realtor claim/purchase pipeline (4.2/4.3) — loop closed
```

Two existing blueprints are copied almost verbatim:

- **Public read surface** ← `apps/api/src/realtor-public/*` (`@ApiExcludeController`, unguarded, slug-gated, curated DTO leaking no internal ids).
- **Moderator verification** ← `apps/api/src/listings/realtor-moderation.controller.ts` (`RolesGuard @Roles('MODERATOR','ADMIN')`, PATCH flips a `verified` boolean, `P2025→404`).

## 6. Data model (Prisma — additive)

New enum:

```prisma
enum ComplexPublishStatus {
  DRAFT
  PUBLISHED
}
```

`Organization` — add verification surface:

```prisma
  verified               Boolean   @default(false)
  verificationRequestedAt DateTime?
  verifiedAt             DateTime?
  verificationNote       String?    // moderator rejection/approval note
```

`Complex` — add publish + slug + geo + images relation:

```prisma
  slug          String?              @unique
  publishStatus ComplexPublishStatus @default(DRAFT)
  publishedAt   DateTime?
  latitude      Float?
  longitude     Float?
  images        ComplexImage[]
  inquiries     PropertyRequest[]    @relation("ComplexInquiries")
```

New `ComplexImage` (mirrors `Image`, cascades from Complex):

```prisma
model ComplexImage {
  id        String   @id @default(cuid())
  complexId String
  complex   Complex  @relation(fields: [complexId], references: [id], onDelete: Cascade)
  base      String   // '/images/complex/<cuid>/01' — same base-path convention as Image
  ogUrl     String?
  width     Int
  height    Int
  position  Int      @default(0)
  createdAt DateTime @default(now())

  @@index([complexId])
}
```

`PropertyRequest` — add ЖК/unit provenance (nullable, SetNull so lead survives inventory deletion):

```prisma
  complexId String?
  complex   Complex? @relation("ComplexInquiries", fields: [complexId], references: [id], onDelete: SetNull)
  unitId    String?
  unit      Unit?    @relation("UnitInquiries", fields: [unitId], references: [id], onDelete: SetNull)
```

`Unit` — add back-relation: `inquiries PropertyRequest[] @relation("UnitInquiries")`.

**Migration:** one additive folder `<ts>_phase_5_3_marketplace_publishing`: `CREATE TYPE ComplexPublishStatus`, `ALTER TABLE Organization ADD COLUMN` ×4, `ALTER TABLE Complex ADD COLUMN` ×5 (+ unique index on slug), `CREATE TABLE ComplexImage` + index + FK, `ALTER TABLE PropertyRequest ADD COLUMN complexId/unitId` + 2 FKs. No `DROP`, no existing column changed.

## 7. Shared DTOs (`packages/shared/src/schemas.ts`)

Public (buyer-facing, PII-stripped) — new:

- `ComplexPublishStatusSchema = z.enum(['DRAFT','PUBLISHED'])`.
- `PublicUnitSchema` — `{ id, number, floor, rooms(nullable), areaM2(nullable), priceSom(string nullable), status: UnitStatusSchema }` — **no booking object** (PII stripped; only `status`).
- `PublicBuildingSchema` — `{ id, name, floors(nullable), units: PublicUnitSchema[] }`.
- `PublicComplexSummarySchema` — the browse card: `{ slug, name, district, coverImage: ImageSchema.nullable(), buildStatus: ComplexStatusSchema, priceFromSom: string|null, unitsAvailable: number, developerName: string, developerVerified: boolean }`.
- `PublicComplexDetailSchema` — `PublicComplexSummarySchema` minus card-only aggregates, plus `{ description(nullable), address(nullable), latitude(nullable), longitude(nullable), gallery: ImageSchema[], buildings: PublicBuildingSchema[], priceFromSom, unitsAvailable, unitsTotal }`.
- Reuse the existing `Image`/responsive-image shape for `coverImage`/`gallery` (base + webp variants).

Inputs / CRM / moderation — new:

- `ComplexInquirySchema` — `{ note: z.string().trim().max(1000).optional(), unitId: z.string().optional() }` (buyer identity comes from the JWT).
- **Extend `PropertyRequestCreateSchema`** with optional `complexId: z.string().optional()` + `unitId: z.string().optional()` — the inquiry lead needs these persisted, and today `create()` writes a fixed field set and the DTO (a non-`.strict()` `z.object`) silently **strips** unknown fields, so they must be first-class inputs (see §8c).
- `DeveloperVerifySchema` — `{ verified: z.boolean(), note: z.string().trim().max(500).optional() }` (moderator).
- `ModeratorDeveloperRowSchema` — the moderation queue row: `{ orgId, name, district(nullable), verified, verificationRequestedAt(nullable), complexCount, memberPhone }`.
- Extend `OrganizationSchema` (CRM self-view) with `{ verified, verificationRequestedAt(nullable), verifiedAt(nullable) }` so the developer sees their status.
- Extend `ComplexSchema`/`ComplexDetailSchema` (CRM) with `{ slug(nullable), publishStatus, publishedAt(nullable), latitude(nullable), longitude(nullable), imageCount }` and a `coverImage`/`images` field so the CRM shows publish state + media.
- Money stays **BigInt-as-string** (`priceSom`, `priceFromSom`) end-to-end.

## 8. API surface

### 8a. Developer-side (`@Controller('crm')`, `DeveloperGuard`, org-scoped)

- `POST /api/crm/complexes/:id/images` — multipart (`FileInterceptor('file')`, 10 MB limit, jpeg/png/webp allowlist — same as `listing-image.controller.ts`); calls `processImage("complex/<complexId>", buffer)` (the model-agnostic core from `process-image.ts`), writes a `ComplexImage` row (position = current max + 1), returns the updated complex media. The owner/status/count logic in `ListingsService.addImageBuffer` is **re-implemented thin** for Complex (a per-complex image cap + the 5.1 ownership chain → 404 for a foreign complex).
- `DELETE /api/crm/complexes/:id/images/:imageId` — remove one image.
- `PATCH /api/crm/complexes/:id/publish` — body `{ publish: boolean }`. On `true`: assert `org.verified` (else `409` _"Avval tashkilotni tasdiqdan o'tkazing"_) + completeness gate (else `409` with the missing-item message); generate `slug` if absent; set `publishStatus=PUBLISHED`, `publishedAt=now`. On `false`: `publishStatus=DRAFT` (slug retained).
- `PATCH /api/crm/complexes/:id` — extend the existing update to accept `latitude`/`longitude` (partial-update idiom).
- `POST /api/crm/organization/verification-request` — sets `verificationRequestedAt=now` (idempotent; no-op if already verified). Returns the org self-view.

### 8b. Moderator-side (`@Controller('moderation/developers')`, `JwtGuard + RolesGuard @Roles('MODERATOR','ADMIN')`)

- `GET /api/moderation/developers` — queue: organizations with `verificationRequestedAt` set (pending first), returning `ModeratorDeveloperRow[]`.
- `PATCH /api/moderation/developers/:orgId` — body `DeveloperVerifySchema`; sets `verified` + `verifiedAt`/`verificationNote`; `P2025→404`. (Mirrors `realtor-moderation` exactly.)

### 8c. Public (`@Controller('jk')`, `@ApiExcludeController`, **unguarded** except the inquiry write)

- `GET /api/jk` — all `PUBLISHED` complexes as `PublicComplexSummary[]` (fetch-all; client filters by district). Hard-filters `publishStatus=PUBLISHED`.
- `GET /api/jk/:slug` — one `PublicComplexDetail`; `404` on unknown/unpublished slug. Curated: no `orgId`/internal ids, **no booking rows**. `priceFromSom` = min `priceSom` over `AVAILABLE` units; `unitsAvailable`/`unitsTotal` computed.
- `POST /api/jk/:slug/inquiry` — **`JwtGuard`** (method-level; class stays guard-less). Body `ComplexInquirySchema`. Calls the **extended** `RequestsService.create(callerId, { deal: 'SALE', type: 'NEW_BUILD', district: complex.district, note, complexId: complex.id, unitId? })` — `authorId` is the `userId` param (not the body), and `create()` + `PropertyRequestCreateSchema` are extended (§7) to **persist** `complexId/unitId` (today they would be silently stripped and never written). Scoring/pricing (`computeLeadScore` + `conversionAdjustment` + `priceForScore`) stay inside `create()`, so the inquiry lead is scored + priced like any other and enters the OPEN pool. Returns `201`. `404` if slug not published.

## 9. Public web UI (`apps/web`, FSD)

- **Route** `/jk` (browse) + `/jk/:slug` (detail), registered in `app/router.tsx` **outside** `TabLayout` (own chrome), mirroring `/r/:slug`.
- **entities/complex/api.ts** — `complexesQuery()` (`['complexes']`, `GET /api/jk`, `z.array(PublicComplexSummarySchema)`) + `complexQuery(slug)` (`['complex', slug]`, `GET /api/jk/:slug`, `PublicComplexDetailSchema`, `staleTime 5min`). Copy the `realtorQuery` idiom exactly.
- **pages/complexes** — browse: `useQuery(complexesQuery())`, client-side district filter + infinite scroll (reuse `useInfiniteScroll`), a **ЖК card** (cover, name, district, _"narx — X so'mdan"_, `unitsAvailable`, verified pill) cloning `ListingCard`.
- **pages/complex** — detail: mobile-first column → lg 2-col grid; hero `Gallery`; developer name + green _"Tasdiqlangan quruvchi"_ badge (reuse the `Icon name="check"` pill from `listing-result-row`/`agent-card`); price-from + unit-mix; **availability grid** (buildings → floors → unit chips coloured AVAILABLE=green / BOOKED=amber _"band"_ / SOLD=red _"sotilgan"_, reusing the CRM shaxmatka colour language but read-only, PII-free); map pin from `latitude`/`longitude`; a sticky **"So'rov yuborish"** inquiry CTA. 404 → `NotFoundView`.
- **features/complex-inquiry** — `useComplexInquiry(slug)` mutation → `POST /api/jk/:slug/inquiry`; if `readTokens()===null`, the CTA routes to login first (FSD slot-injected into the entity card/detail, never imported upward).
- **Nav** — add a _"Novostroykalar"_ entry to `shared/config/nav.ts` (drawn by both header + bottom nav) pointing at `/jk`; optionally a home _"Ommabop turar-joy majmualari"_ carousel band (platform-spec §2.4) reusing the ЖК card.
- **Moderation** — `pages/moderation-developers/{api.ts, ui/*.tsx}` cloning `moderation-realtors`: in-page `MODERATOR/ADMIN` gate, `useQuery` + `useMutation(apiPatch)` on `/api/moderation/developers`, shared-key invalidation; add a cross-link in the sibling moderation Shells.

- **complexes page** — a published/draft badge on each complex card (new `PUBLISH_STATE_LABELS/BADGE` following `complex-status.ts`).
- **organization page** — a _"Tasdiqlanish so'rovi"_ button (→ `verification-request`) + the org's verification status (Kutilmoqda / Tasdiqlangan), reading the extended `OrganizationSchema`.
- **use-developer.ts** — `usePublishComplex`, `useComplexImages` (upload/delete), `useRequestVerification` hooks; invalidate `complexQueryKey(id)` + `COMPLEXES_QUERY_KEY` + `ORG_QUERY_KEY`.
- **shared/api/client.ts** — the CRM client today exposes only `apiGet/apiPost/apiPut/apiPatch/apiDelete` (no upload helper). **Add an `apiUpload(path, FormData, schema?)` helper** (copy `apps/web/src/shared/api/client.ts`'s multipart POST) so the image-upload control has a client. Prerequisite for `useComplexImages`.

## 12. Testing strategy

Project rule: **no new test files**. Verify via:

- `yarn lint` / `typecheck` / `build` across all workspaces; existing suite stays green (**api 37 + e2e 22, web 34, shared 18 = 111**; `@rieltor/crm` ships none).
- Compiled-JS scratch (nest build → node the compiled JS; never `tsx`) to prove: publish gate (409 when not verified / incomplete), slug generation + uniqueness, `PublicComplexDetail` strips booking PII, price-from computation, inquiry → scored `PropertyRequest` with `complexId`, moderator verify toggle, cross-org 404 on publish/image routes.
- Browser smoke: `/crm` publish flow, `/jk` browse + detail, verified badge render, `/moderation/developers` queue, inquiry CTA.

## 13. Open questions resolved → rulings map

| Map open question                                    | Resolution (§3 ruling)                                                           |
| ---------------------------------------------------- | -------------------------------------------------------------------------------- |
| Publish lifecycle: full moderation queue vs boolean? | Self-service `DRAFT↔PUBLISHED`, gated on org-verified + completeness (ruling 1). |
| Verified on Organization vs per-Complex?             | Organization-level (ruling 2).                                                   |
| Units into `/api/objects` search vs own surface?     | Own `/jk` surface; no projection (ruling 3).                                     |
| Anonymous inquiry vs authored lead?                  | Signed-in buyer → `PropertyRequest` (ruling 4).                                  |
| Images: extend `Image` vs new model?                 | New `ComplexImage`, reuse webp pipeline (ruling 5).                              |
| Slug: auto vs developer-chosen?                      | Auto at first publish (ruling 6).                                                |
| Region/viloyat taxonomy?                             | Deferred; free-text district (non-goal).                                         |
| Documents / construction timeline / installments?    | Deferred to later phases (non-goal).                                             |

## 14. Rollout

Single additive migration; no env changes. Ships behind no flag — a Complex is invisible to buyers until a verified developer publishes it, so the marketplace is unaffected until real inventory is published. Netlify/`CRM_DIST` parity for `/jk` is inherited from the existing web SPA (the ЖК pages are ordinary web routes).
