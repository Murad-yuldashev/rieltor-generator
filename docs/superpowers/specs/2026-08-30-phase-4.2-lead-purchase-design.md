# Phase 4.2 — Lead purchase + wallet design

_Date: 2026-08-30 · Branch: `claude/phase-4.2-lead-purchase` · Base: master `9ad5d16` · Part of: Phase 4 (Product C — Lead market) · Depends on: 4.1 (Lead / exclusive claim), 3.1 (RealtorGuard / Subscription test-payment stub)_

## 1. Goal

Monetize the exclusive lead claim from 4.1: a realtor now **pays** the lead's price (`priceSom`,
set at create in 4.1) out of a **prepaid wallet balance** to claim it. The realtor tops the balance
up in the cabinet (a test-payment stub, like the 3.1 subscription "test to'lov"); the claim debits
the balance atomically inside the same row-locked transaction that already enforces exclusivity, so
a lead can never be claimed without payment and a balance can never go negative or be double-spent.
This is the revenue mechanism of the lead market. **Conversion tracking** is 4.3; **real payment**
(Click/Payme) and **refunds** are later.

## 2. Scope

1. **`Wallet` + `WalletTransaction`** models — a cached `balanceSom` per realtor + an audit ledger.
2. **Top-up** — fixed preset packages, a test-payment stub: `POST /api/wallet/topup` credits the balance.
3. **Wallet view** — `GET /api/wallet` returns the balance + recent transactions (RealtorGuard).
4. **Paid claim** — extend 4.1's `LeadsService.claim` to debit `priceSom` from the wallet inside the
   claim transaction; insufficient balance → `402` and the lead stays OPEN.
5. **UI** — a wallet page in the cabinet (`apps/agent`): balance + top-up presets + history; the web
   lead board (`apps/web /requests`) shows the balance and, on an insufficient-balance claim, a
   top-up call-to-action linking to the cabinet wallet.

### Non-goals

- **Real payment gateway** (Click/Payme/Uzum) — the top-up is a stub that credits the balance
  directly, exactly like the 3.1 subscription "test to'lov". Real integration is later.
- **Refunds / lead-quality guarantee / disputes** — a claim is final in 4.2 (the exclusive claim +
  the 4.1 score are the quality signal). A refund path is a later concern.
- **Conversion tracking** (claimed lead → outcome) — Phase 4.3.
- **Custom top-up amounts** — presets only (chosen); a free-amount field is a later option.
- **Negative balance / credit** — the balance check forbids it; there is no overdraft.
- Marketplace, listings, and the 4.1 scoring/feed/exclusivity logic — unchanged except the claim's
  new debit step.

## 3. Data model (Prisma)

Two new models; no existing model changed. Migration is additive.

```prisma
model Wallet {
  id           String              @id @default(cuid())
  userId       String              @unique
  user         User                @relation(fields: [userId], references: [id], onDelete: Cascade)
  balanceSom   BigInt              @default(0)   // cached; == sum of transactions
  createdAt    DateTime            @default(now())
  updatedAt    DateTime            @updatedAt
  transactions WalletTransaction[]
}

enum WalletTxType {
  TOPUP        // balance credited (test-payment stub)
  LEAD_CLAIM   // balance debited to claim a lead
}

model WalletTransaction {
  id        String       @id @default(cuid())
  walletId  String
  wallet    Wallet       @relation(fields: [walletId], references: [id], onDelete: Cascade)
  type      WalletTxType
  amountSom BigInt                     // always positive; `type` gives the direction
  leadId    String?                    // the claimed PropertyRequest, for LEAD_CLAIM
  createdAt DateTime     @default(now())

  @@index([walletId, createdAt])
}
```

`User` gains `wallet Wallet?`. **`balanceSom` is the cached truth** (the ledger is the audit trail);
both are written in the same transaction — the same discipline 3.3b used for the rating aggregate.
`amountSom` is always positive; `TOPUP` adds, `LEAD_CLAIM` subtracts. A wallet is **created lazily**
(upsert, balance 0) on the realtor's first `GET /api/wallet` / top-up / claim — existing realtors
have no row yet, and a lazy upsert avoids a backfill.

## 4. Top-up (test-payment stub)

Fixed presets (round UZS figures ≈ a few leads' worth), defined once server-side:

```ts
// packages/shared — the canonical package list (id + amount), shared with the cabinet UI.
export const TOPUP_PACKAGES = [
  { id: 'p100', amountSom: '100000' },
  { id: 'p300', amountSom: '300000' },
  { id: 'p500', amountSom: '500000' },
] as const;
```

**`POST /api/wallet/topup`** (RealtorGuard) body `{ packageId }` (validated against `TOPUP_PACKAGES`;
unknown id → 400). In a transaction (wallet row-locked): upsert the wallet, `balanceSom += amount`,
create a `WalletTransaction` `{ type: TOPUP, amountSom }`. Returns the updated wallet view (§5). No
real gateway — the credit is immediate, exactly like `SubscriptionService.activate`.

## 5. Wallet view

**`GET /api/wallet`** (RealtorGuard) → `WalletView = { balanceSom: string, transactions:
WalletTxRow[] }` where `WalletTxRow = { id, type, amountSom: string, leadId: string | null,
createdAt: string }`, newest first, a bounded recent window (e.g. 50). `balanceSom`/`amountSom` are
BigInt-as-string (like `priceSom`). Lazily upserts the wallet (balance 0) so a first-time realtor
sees `balanceSom: '0'` + `[]`.

## 6. Paid claim (extend 4.1's `LeadsService.claim`)

4.1's `claim(id, realtorId)` already runs a transaction that (a) locks the lead row
(`SELECT ... FOR UPDATE`), (b) reads status/author, (c) rejects self-claim (400) and non-OPEN (409),
(d) sets `CLAIMED`/`claimedById`/`claimedAt`, (e) records a `ContactReveal`, (f) returns
`{ phone, name }`. Phase 4.2 inserts a **payment step** so the claim is atomic with the debit:

1. Also `select` the lead's **`priceSom`**.
2. Before mutating the lead, **ensure the realtor's wallet exists** (upsert balance 0) — so there is
   a row to lock — then **lock the wallet row** (`SELECT ... FOR UPDATE` on `Wallet WHERE userId =
realtorId`) **inside the same transaction**. Lock order is **lead row first, then wallet row**,
   consistently, so concurrent claims never deadlock; the wallet lock also serializes a realtor's
   simultaneous claims so the balance can't be over-spent.
3. Read the locked wallet's `balanceSom`; if `balanceSom < priceSom` → throw a
   `402`-mapped exception ("Balans yetarli emas — hisobingizni to'ldiring"); the transaction rolls
   back and the lead stays OPEN.
4. Else: `balanceSom -= priceSom`, create a `WalletTransaction` `{ type: LEAD_CLAIM, amountSom:
priceSom, leadId: id }`, then set the lead `CLAIMED` + record the `ContactReveal` (as 4.1).
5. Return `{ phone, name }` (unchanged) — optionally the new balance, but the feed/wallet refetch
   already reflects it.

The claim is now **all-or-nothing**: either the realtor pays and gets the exclusive contact, or
nothing changes. The self-claim (400) and already-claimed (409) checks stay and fire before any
debit. NestJS: map insufficient balance to a `402 Payment Required` (a `PaymentRequiredException`
via `HttpException(msg, 402)`), distinct from the 409/400.

## 7. UI

- **Cabinet (`apps/agent`) — the wallet home:** a wallet page (RealtorGuard) showing the current
  `balanceSom`, the **top-up preset buttons** (`TOPUP_PACKAGES` → `POST /api/wallet/topup` →
  invalidate the wallet query), and the **transaction history** (TOPUP "+X" / LEAD_CLAIM "−X" with
  the date). Reachable from the cabinet nav.
- **Web lead board (`apps/web /requests`):** show the realtor's current **balance** (a small widget
  fetched from `GET /api/wallet`) and the lead prices (already shown, realtor-only). On a claim that
  returns **402**, show "Balans yetarli emas" and a **top-up CTA** — a link to the cabinet wallet
  (`/agent/wallet`, a plain cross-app navigation; `apps/web` does not import `apps/agent`). The
  successful-claim contact panel (4.1) is unchanged.

## 8. Modules & wiring

- `apps/api`: a `WalletModule` (`WalletService` + `WalletController`, RealtorGuard) for `GET
/api/wallet` + `POST /api/wallet/topup`; the wallet upsert/debit helpers live in `WalletService`
  and are called from `LeadsService.claim` (so `LeadsModule` imports `WalletModule` or the debit is
  done inline in the claim tx via `tx` — the claim's debit MUST run on the same `tx`, so the logic
  is a helper that takes `tx`, not a separate service call that opens its own transaction).
- `apps/web`: the balance widget + the 402 top-up CTA on the lead board.
- `apps/agent`: the wallet page (balance + top-up + history).
- Shared Zod DTOs: `Wallet`/`WalletView`/`WalletTxRow`, `TopupSchema` (`{ packageId }`),
  `TOPUP_PACKAGES` constant.

## 9. Constraints

- Uzbek user-facing copy; **English** identifiers/comments.
- **No new test files**; the existing suite stays green.
- **Additive migration**; **no new env var** (the test-payment stub uses no gateway).
- Wallet + claim endpoints are **RealtorGuard** (role REALTOR + active subscription). The balance
  debit is **atomic with the claim** — the debit and the `CLAIMED` write are one transaction; the
  wallet row is `SELECT ... FOR UPDATE`-locked so simultaneous claims can't over-spend. Lock order
  lead→wallet, consistently, to avoid deadlock.
- **Do not break** 4.1: the claim still enforces exclusivity (lead row lock, 409/400) and masking;
  the only change is the added, in-transaction debit + the 402 path.
- BigInt money is serialized as a string end-to-end (like `priceSom`).

## 10. Verification

- Automated: `yarn lint`/`typecheck`/`build` (4 workspaces); the existing suite green; additive migration.
- API (compiled-JS scratch): a realtor with balance 0 claims a lead → **402**, the lead stays OPEN,
  no `WalletTransaction`; top-up 100k → balance 100000 + a `TOPUP` row; claim a 20k-fee lead →
  succeeds, balance 80000, a `LEAD_CLAIM` row (leadId), the lead CLAIMED; **concurrency**: two
  simultaneous claims by the SAME realtor with only enough balance for ONE → exactly one succeeds,
  one gets 402 (or 409 if same lead), balance never negative; a second realtor claiming an
  already-claimed lead → 409 (before any debit). `GET /api/wallet` returns the balance + ledger; a
  USER (non-realtor) → 403.
- Web/agent (browser smoke): a realtor with 0 balance tries to claim → "Balans yetarli emas" + the
  top-up CTA → cabinet wallet → top up a preset → balance rises + a TOPUP row → back to the board →
  claim → the fee is debited, the contact reveals (4.1 panel), the balance drops.

## 11. Risks

- **Atomicity of the debit + claim** — the debit MUST be in the SAME transaction as the `CLAIMED`
  write; a separate call that opens its own transaction could debit without claiming (or vice
  versa) on a partial failure. The debit logic is a `tx`-scoped helper called inside the claim
  transaction. Highest-risk item; the scratch must prove all-or-nothing.
- **Balance over-spend under concurrency** — a realtor firing two claims at once must not spend the
  same balance twice. The wallet row `SELECT ... FOR UPDATE` lock (held for the claim transaction)
  serializes them; the scratch must prove the second blocks and then sees the reduced balance.
- **Deadlock (lead + wallet locks)** — always acquire the lead row lock before the wallet row lock;
  top-up locks only the wallet. A consistent order removes the cross-lock cycle.
- **Cached balance drift** — `balanceSom` is the cached truth; every write (topup, claim-debit) is
  transactional with a `WalletTransaction`. A missed pairing desyncs the balance from the ledger;
  the scratch asserts `balanceSom == sum(TOPUP) - sum(LEAD_CLAIM)` after a sequence.
- **Cross-app top-up seam** — the board (`apps/web`) links to the cabinet wallet (`apps/agent`) for
  top-up; this is a plain URL navigation, not an import (FSD/app boundary preserved).
