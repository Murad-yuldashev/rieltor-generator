# Phase 7.2c — Realtor AI social content (post caption + hashtags) (design)

**Status:** approved design, ready for planning
**Branch:** `claude/phase-7.2c-listing-content` (off master `9a9ffc4`, the Phase 7.2b merge)
**Roadmap:** Phase 7 (Growth layer, last roadmap phase) — 7.1 mortgage → **7.2 AI assistant** → 7.3 map → 7.4 journal. Phase 7.2 slices: 7.2a buyer AI search (done) → 7.2b realtor lead assistant (done) → **7.2c realtor AI content** → 7.2d developer AI insights.

---

## 1. Goal

Give a realtor one-tap **ready-to-post social content** for a listing (C11): from the listing's fields
(type/deal/district/rooms/area/price) produce a catchy **post caption** + **hashtags** (Uzbek,
Instagram/Telegram-flavored, copyable). It reuses the existing `GeminiService`, and — like the
valuation and the 7.2b lead assistant — is a **hybrid**: a template caption+hashtags is always computed
from the fields, and Gemini enriches it when a key is available. The realtor copies and posts it
themselves (no posting integration).

This is the third slice of the Phase 7.2 AI-assistant subsystem; it follows the reuse pattern the prior
slices established (a `GeminiService` call with strict server-side validation of the model output) and
the 7.2b hybrid always-a-usable-result fallback.

## 2. Scope

**In scope (7.2c):**

- A guarded **`POST /api/ai/content`** (realtor-only): listing fields → `{ ai, caption, hashtags }` —
  Gemini-authored when available, a structured template otherwise.
- Shared DTOs for the request + the response.
- An **"AI post"** affordance on the realtor's listing surface in `apps/agent` (the browse page) that
  calls the endpoint and shows the caption + hashtags in a **copyable** panel.

**Deferred (named, not built):**

- Actually **posting** to Instagram/Telegram (integration) — 7.2c only drafts copyable text.
- Image / carousel / Stories-slide generation, video/reels, multiple variants / A-B, a saved post
  history, tone/language selection.
- Storing the generated content (7.2c is stateless — generated on demand, nothing persisted).
- The other Phase 7.2 slice (7.2d developer insights) and the rest of Phase 7.

## 3. Design decisions (resolved)

1. **Two outputs: caption + hashtags.** Gemini returns a JSON `{ caption, hashtags }`; the server
   validates it (strict) and falls back to the template if unusable.
2. **Hybrid, always-usable (like 7.2b / valuation).** A pure template `{ caption, hashtags }` is always
   computed from the listing fields; no API key / an unusable model response → the template (never a
   503). Gemini is an enrichment, not a dependency.
3. **Realtor-gated.** A new `@Controller('ai')` route guarded by `JwtGuard + RealtorGuard` (an active
   subscription — a premium realtor marketing tool, like 7.2b), distinct from the existing
   `JwtGuard`-only description writer. No ownership check: the content is generated from listing fields
   the client already holds (any published listing the realtor wants to promote); nothing private.
4. **Fields-in-body** (mirrors the existing `POST /api/ai/description`). The realtor's browse card
   already has the `ListingSummary`, so the client sends the fields — no extra DB read, no listing-id
   coupling.
5. **Draft-only, copyable, stateless.** No posting integration; nothing stored; no data-model change.

## 4. Data model

**No change.** 7.2c is a stateless transform over fields the client sends; nothing is written or added.

## 5. Backend

### 5.1 Shared DTOs (`packages/shared/src/schemas.ts`)

Mirror `AiDescriptionRequestSchema` (+ `priceSom`, which the caption needs).

```ts
/** The request body for the realtor AI social-content generator (fields the browse card already has). */
export const AiContentRequestSchema = z.object({
  type: ListingTypeSchema,
  deal: DealSchema,
  district: z.string().min(2),
  rooms: z.number().int().nullable().optional(),
  areaM2: z.number().positive(),
  priceSom: z.string().regex(/^\d+$/), // BigInt-as-string (RENT = per month)
});

/** The AI social-content result. ai=true → Gemini-authored; ai=false → structured template. */
export const AiContentResponseSchema = z.object({
  ai: z.boolean(),
  caption: z.string(), // the post text (Uzbek, with a call-to-action)
  hashtags: z.string(), // space-separated, e.g. "#toshkent #kvartira #yangiqurilish"
});
```

Plus the inferred types `AiContentRequest`, `AiContentResponse`.

### 5.2 AiContentController + helpers (`apps/api/src/ai/`)

- A new **`AiContentController`** added to `AiModule`: `@Controller('ai')`, **`@UseGuards(JwtGuard,
RealtorGuard)`**, `@Post('content')`. (A third `@Controller('ai')` class beside the guarded
  `AiController` `/description` and the public `AiSearchController` `/search-parse` — the established
  multi-controller pattern; distinct routes, no collision.)
- **Module wiring:** `AiModule` imports `AgentModule` (which exports `RealtorGuard`). No cycle —
  `AgentModule` imports only `[AuthModule, PresentationsModule]`, neither of which imports `AiModule`;
  and `leads.module.ts` already imports both `AiModule` + `AgentModule`, so the pattern is proven.
- **Handler:** Zod-parse the body (400 on bad input); compute the **template** (§5.3); build the prompt
  (§5.4); `gemini.generate(prompt, { maxTokens: 400 })`; return `parseContent(raw, template)` — Gemini
  when usable (`ai: true`), else the template (`ai: false`). Never throws for an AI/parse problem.

### 5.3 The template (`apps/api/src/ai/ai-content.template.ts`) — pure, always computable

- `buildContentTemplate(fields): { caption, hashtags }`:
  - `caption` — an Uzbek post from the fields, e.g. a rooms/type/district/area line + a price line
    (`formatPriceSom`-style grouping via an ICU-free helper — the 7.2a lesson, no `toLocaleString`) + a
    call-to-action ("Batafsil ma'lumot uchun yozing."), every interpolated field null-guarded
    (`rooms` optional; commercial has none).
  - `hashtags` — a space-separated set derived from the fields: a base (`#toshkent #korchmasmulk`) +
    deal (`#sotuv`/`#ijara`) + a type tag (`Record<ListingType, string>` — finite keys, no
    `noUncheckedIndexedAccess` gap, the 7.2a lesson) + a district tag (slugged: lowercased, spaces
    stripped). No user-free-text beyond the district string.

### 5.4 The prompt + output validation (`apps/api/src/ai/ai-content.parse.ts`) — untrusted output

- `buildContentPrompt(fields)`: an Uzbek instruction — role ("ko'chmas mulk e'loni uchun ijtimoiy tarmoq
  posti yozadigan yordamchi"), the listing fields, and "Return JSON only: `{ \"caption\": string,
\"hashtags\": string }`; the caption is a short, catchy Uzbek post (2-4 sentences, emojis ok) with a
  call-to-action; hashtags is a space-separated string of 4-8 relevant Uzbek/city tags."
- `parseContent(raw: string | null, template): AiContentResponse` — pure, **never trusts the model**:
  `raw == null` → `{ ai: false, ...template }`; strip code fences; `JSON.parse` in try/catch → on throw,
  the template; validate the object has non-empty string `caption` + `hashtags` (a small Zod schema) →
  success → `{ ai: true, caption, hashtags }` (trimmed, length-capped); failure → the template. Never
  throws. (The same discipline as 7.2a/7.2b, so it is Node-checkable in isolation.)

## 6. Frontend (`apps/agent`, FSD)

- **`features/listing-content/`** — a new feature:
  - `model/use-listing-content.ts` — `useListingContent()` (a mutation:
    `apiPost('/api/ai/content', AiContentResponseSchema, req)`; on network/HTTP error, resolve to a
    minimal client fallback so a failure never breaks the panel).
  - `ui/listing-content-button.tsx` — an "AI post" button (props: the listing's
    `{ type, deal, district, rooms, areaM2, priceSom }`); on click, call the endpoint, then show the

    (`navigator.clipboard.writeText`, guarded — the 7.2b / presentations pattern). A small "AI" /
    "namuna" (template) tag from `ai`. Uzbek copy.
- **Wire into the browse page** (`apps/agent/src/pages/browse/ui/browse-page.tsx`): render the "AI post"
  affordance per listing (the page maps `ListingCard`s; it passes the listing's summary fields to
  `<ListingContentButton … />`). The feature takes only plain fields — it does **not** import
  `@/entities/listing` internals or any `@/features/*` (FSD: a feature imports only entities/shared; the
  page composes). The exact card integration (a button in the card's action area vs a per-card panel) is
  a plan detail; do not restructure the card entity.
- **FSD:** `listing-content` imports only `@rieltor/shared` + the agent `shared/*` client/UI. `yarn lint`
  must pass (apps/agent `features → entities/shared` only).

UI copy Uzbek; identifiers/routes/comments English.

## 7. Rulings & invariants (load-bearing)

- **R1 — never trust the model's shape.** `parseContent` JSON-parses in try/catch and validates
  `{ caption, hashtags }` (non-empty strings) before use; any bad response → the template, never a 500
  and never an unvalidated object to the client.
- **R2 — hybrid, always usable.** The template `{ caption, hashtags }` is always computable from the
  fields; no key / outage / unusable parse → the template with `ai: false` (never a 503). Gemini only
  enriches.
- **R3 — realtor-gated.** `POST /api/ai/content` is guarded by `JwtGuard + RealtorGuard` (an active
  subscription). It reads only the fields in the request body (no private data, no ownership needed);
  the response returns only `caption` + `hashtags` derived from those fields.
- **R4 — draft-only, stateless, additive.** No posting integration, nothing stored, no data-model
  change, no migration; a new controller + helpers added to the existing `AiModule` (which gains an
  `AgentModule` import for `RealtorGuard`); the description writer + search parser untouched.
- **R5 — type/style discipline (7.2a/7.2b lessons).** Any type/deal→label map is
  `Record<ListingType, string>` / a small deal map (finite keys, no `noUncheckedIndexedAccess` gap);
  money uses the ICU-free grouping helper (no `toLocaleString`); every interpolated field null-guarded
  (`rooms` may be null for commercial).

## 8. Verification (no new test files — per project rule)

- `yarn typecheck` + `yarn lint` + `yarn build` green across api / shared / agent.
- Compiled-JS / pure-Node scratch (against a real `nest build`, never `tsx`, run from `apps/api` so
  `@rieltor/shared` resolves) of `parseContent` + `buildContentTemplate`: (a) `parseContent(null, tpl)`
  → `{ ai: false, ...tpl }`; (b) a non-JSON string → template; (c) a valid `{ caption, hashtags }` →
  `ai: true` with those fields (trimmed); (d) a JSON missing `hashtags` (or empty string) → template;
  (e) `buildContentTemplate` for a SALE and a RENT listing, a commercial listing with `rooms: null`, and
  a listing with `priceSom` "1500000000" → a coherent caption with NO literal "undefined"/"null", a
  grouped price, and a non-empty hashtag string.
- Booted-Nest HTTP check (never tsx): `POST /api/ai/content` — no auth → 401; a logged-in NON-realtor
  (no active subscription) → 403 (RealtorGuard); a realtor (key unset) → 200 with `ai: false` and a
  non-empty `caption` + `hashtags`; an invalid body (missing `areaM2`) → 400.
- Browser smoke: in `apps/agent` browse, a listing's "AI post" button shows a caption + hashtags; "Nusxa
  olish" copies it.
- Full suite green before merge (shared 18, web 34, api 37, e2e 22 → 111), zero new test files.
