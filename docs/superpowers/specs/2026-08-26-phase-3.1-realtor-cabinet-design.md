# Phase 3.1 — Realtor cabinet design

_Date: 2026-08-26 · Branch: `claude/phase-3.1-realtor-cabinet` · Base: master `e672a1c` · Part of: Phase 3 (Product C — Realtor platform)_

## 1. Goal

A new **`apps/agent`** realtor cabinet — a separate SPA where a realtor manages a
paid **subscription** (14-day trial → paywall, payment **stubbed**), a private
**realtor profile**, private per-listing **notes** (C9), and per-client
**collections / podborka** (C10), with a minimal in-app **listing browser** to add
listings to notes and collections. This is Phase 3's foundation and the platform's
**first paid subscription product**.

Later Phase 3 sub-phases (out of scope here): shareable **presentation** link +
analytics + Telegram sharing (C3/C4/C5) → 3.2; **site generator** subdomain microsite
(C1) and **public verified profile** + rating (C14) → 3.3.

## 2. Scope

1. New **`apps/agent`** SPA (React 19 · Vite 6 · Tailwind v4 · React Router 7 ·
   TanStack Query 5 · Feature-Sliced Design), served at the **`/agent` subpath** in
   production, with its **own auth** feature reusing the existing `/api/auth`.
2. **Subscription + trial + paywall** (payment stubbed): `become-realtor` → 14-day
   trial → guard → **stub `activate`** (30-day period).
3. **RealtorProfile** (internal only): agency, bio, regions, experience.
4. **Notes** (C9): one editable private note per `(realtor, listing)`.
5. **Collections** (C10): named per-client sets of listings, ordered, with a per-item note.
6. Minimal **listing browser** (reuses `GET /api/objects`) with "add note" /
   "add to collection" actions.
7. New **`agent`** API module with a **`RealtorGuard`** (auth + `REALTOR` role +
   active subscription).

### Non-goals (later Phase 3 or deferred)

- Public realtor profile + verification badge + rating (C14) — 3.3.
- Shareable presentation link + view analytics + Telegram-native sharing (C3/C4/C5) — 3.2.
- Site generator / subdomain microsite (C1) — 3.3.
- **Real payment** integration (Click / Payme / Uzum) — stubbed now, like the dev SMS/OTP stub.
- Managing the realtor's **own listings** inside the agent app — stays in `apps/web` for now.
- Sub-agent hierarchy (C12), commission visibility/payout (C7/C8), lead market (C16 — Phase 4),
  fixation (C6 — Phase 4), AI social content (C11), embeddable widget / XML feed (C2).
- **No change to the public marketplace** "who is selling" display (`DEFAULT_AGENT_ID` /
  the display-only `Agent` model stays exactly as-is; connecting real realtor profiles to
  public listings is 3.3).

## 3. App structure & serving

- New workspace **`apps/agent`** mirrors `apps/web`'s stack and FSD layout
  (`app/ · pages/ · widgets/ · features/ · entities/ · shared/`), with the same ESLint
  `boundaries` enforcement.
- **Dev:** its own Vite dev server on a dedicated port (e.g. 5174), added as a turbo `dev`
  task. `VITE_API_URL` reuses the same value `apps/web` uses (no new env).
- **Prod:** the API serves **`apps/agent/dist` at `/agent/*`** — Vite `base: '/agent/'`;
  the API registers a static handler + SPA fallback for `/agent/*` **ordered before** the
  existing `/` (web) SPA fallback so `/agent` is not swallowed. The `Dockerfile` builds
  `@rieltor/agent` and copies its `dist`.
- The agent app talks only to `/api/*`; it never imports from `apps/web` (separate app,
  clean boundary — the reason this app is separate).

## 4. Data model (Prisma)

New models (alongside today's `User` / `Listing` / `Agent`):

```prisma
enum SubscriptionStatus { TRIAL ACTIVE EXPIRED }

model RealtorProfile {
  id              String   @id @default(cuid())
  userId          String   @unique
  user            User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  agency          String                        // agency / brand name
  bio             String?
  regions         String[]                      // e.g. ["Toshkent", "Samarqand"]
  experienceYears Int?
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt
}

model Subscription {
  id               String             @id @default(cuid())
  userId           String             @unique
  user             User               @relation(fields: [userId], references: [id], onDelete: Cascade)
  status           SubscriptionStatus @default(TRIAL)
  tier             String             @default("PRO")   // single tier for MVP
  currentPeriodEnd DateTime                              // trial end OR paid period end
  createdAt        DateTime           @default(now())
  updatedAt        DateTime           @updatedAt
}

model Note {                                             // C9 — one private note per (realtor, listing)
  id        String   @id @default(cuid())
  realtorId String
  realtor   User     @relation(fields: [realtorId], references: [id], onDelete: Cascade)
  listingId String
  listing   Listing  @relation(fields: [listingId], references: [id], onDelete: Cascade)
  body      String
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  @@unique([realtorId, listingId])
}

model Collection {                                       // C10 — podborka per client
  id        String           @id @default(cuid())
  realtorId String
  realtor   User             @relation(fields: [realtorId], references: [id], onDelete: Cascade)
  name      String                                       // client label, e.g. "Aziz uchun 2-xona"
  createdAt DateTime         @default(now())
  updatedAt DateTime         @updatedAt
  items     CollectionItem[]
}

model CollectionItem {
  id           String     @id @default(cuid())
  collectionId String
  collection   Collection @relation(fields: [collectionId], references: [id], onDelete: Cascade)
  listingId    String
  listing      Listing    @relation(fields: [listingId], references: [id], onDelete: Cascade)
  position     Int
  note         String?
  addedAt      DateTime   @default(now())
  @@unique([collectionId, listingId])
}
```

Back-relations added: `User { realtorProfile RealtorProfile?  subscription Subscription?  notes Note[]  collections Collection[] }`;
`Listing { notes Note[]  collectionItems CollectionItem[] }`. `onDelete: Cascade` on the
`listing` relations keeps a removed listing from orphaning notes/items. `position` and the
item `note` exist now so 3.2's presentation (ordered showcase) builds on the same rows.

## 5. API — `agent` module (`/api/agent`)

New Nest module `apps/api/src/agent/`. Zod DTOs in `@rieltor/shared` (single source, as
existing modules do). Money is not involved here.

| Method + path                                                                                                            | Guard              | Purpose                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------ | -------------------------------------------------------------------------------------------------------------------- |
| `POST /become-realtor`                                                                                                   | Jwt                | Idempotent: set `User.role = REALTOR` + create `Subscription(TRIAL, now+14d)`. If already a realtor, return current. |
| `GET /subscription`                                                                                                      | Jwt + Realtor-role | Current subscription (status, `currentPeriodEnd`, computed `isActive`, `daysLeft`).                                  |
| `POST /subscription/activate`                                                                                            | Jwt + Realtor-role | **Stub payment** → `ACTIVE`, `currentPeriodEnd = now+30d`. Clearly labelled a test activation.                       |
| `GET /profile` / `PATCH /profile`                                                                                        | RealtorGuard       | Read / update `RealtorProfile` (agency, bio, regions, experienceYears).                                              |
| `GET /notes` · `GET /notes/:listingId` · `PUT /notes/:listingId` · `DELETE /notes/:listingId`                            | RealtorGuard       | List / read / **upsert** / delete the private note for a listing.                                                    |
| `GET /collections` · `POST /collections` · `GET /collections/:id` · `PATCH /collections/:id` · `DELETE /collections/:id` | RealtorGuard       | Collection CRUD (list includes item counts; detail includes ordered items joined to listing summaries).              |
| `POST /collections/:id/items` · `DELETE /collections/:id/items/:listingId` · `PATCH /collections/:id/items`              | RealtorGuard       | Add a listing (append at `max(position)+1`), remove, reorder (array of listingIds → positions).                      |

Listing browsing reuses the existing `GET /api/objects` — **no new listing endpoint**.

**Guards:**

- Existing `JwtGuard` authenticates every route.
- A small **role check** gates `subscription` endpoints + is implied by `become-realtor`'s
  upgrade. The subscription endpoints must stay reachable while a subscription is `EXPIRED`
  (so a lapsed realtor can re-activate) — so they are role-gated but **not** subscription-gated.
- **`RealtorGuard`** = `REALTOR` role **and** active subscription (`status != EXPIRED` **and**
  `currentPeriodEnd > now`). Applied to `profile`, `notes`, `collections`. On failure → `403`,
  which the agent app maps to a redirect to `/subscribe`.
- Ownership is always enforced in the service by `realtorId = req.user.id` (a realtor can only
  read/write their own notes/collections; `:id`/`:listingId` are scoped to the caller).

## 6. Subscription / trial / paywall flow

1. An authenticated `USER` entering `apps/agent` with no realtor role sees a **"Rieltor bo'lish"**
   screen. Click → `POST /become-realtor` → role `REALTOR` + `Subscription(TRIAL, now+14d)`.
2. Cabinet unlocks; a **trial banner** shows "Trial: N kun qoldi" (from `currentPeriodEnd`).
3. When `currentPeriodEnd` passes, `RealtorGuard` returns `403` on feature endpoints → the app
   routes to **`/subscribe`** (paywall): "Trial tugadi — obuna bo'ling".
4. `/subscribe` → **"Faollashtirish (test to'lov)"** → `POST /subscription/activate` →
   `ACTIVE, now+30d`. Clearly a stub; real Click/Payme replaces it later. Cabinet re-unlocks.

- **Expiry is evaluated live in the guard** (`currentPeriodEnd > now`) — the source of truth.
  A daily "flip to `EXPIRED`" cron is **optional / deferred** (the live check already gates
  correctly; the stored `status` is cosmetic between checks).

## 7. Notes & collections (the cabinet tools)

- **Notes (C9):** from the listing browser (or a collection item), open a listing → edit a
  private note (textarea) → `PUT /notes/:listingId` (upsert `body`). "Mening eslatmalarim"
  lists all notes (listing title + snippet + link). Private to the realtor.
- **Collections (C10):** "Kolleksiyalarim" lists collections (name + item count). Create with a
  name (client label). Open → ordered listing cards + optional per-item note; add (from the
  browser via "Kolleksiyaga qo'shish" → pick a collection), remove, reorder. **Private in 3.1**
  — the shareable link + analytics is 3.2, but the ordered-items model is already in place.
- **Listing browser:** a simple page hitting `GET /api/objects` with district/type/rooms filters;
  cards carry "Eslatma qo'shish" and "Kolleksiyaga qo'shish" actions.
- **Dashboard (home):** trial/subscription banner, quick counts (collections, notes), CTAs.

## 8. Auth in `apps/agent`

- Its **own auth feature** (login modal) calling the existing `/api/auth` (phone OTP + Telegram
  Login + the dev-OTP convenience). Token storage mirrors `apps/web`'s pattern (localStorage
  access/refresh + a reactive `useSession`). Extracting a shared `packages/auth-client` is
  **deferred** to avoid touching `apps/web` (low risk).
- After login, `useSession` exposes `role`; the app routes: `USER` → "Rieltor bo'lish";
  `REALTOR` + active → cabinet; `REALTOR` + expired → `/subscribe`.

## 9. Modules, wiring, CI

- `apps/agent` is a Yarn workspace `@rieltor/agent`; turbo picks up its `build`/`lint`/`typecheck`
  automatically. `Dockerfile` adds an `@rieltor/agent build` step and copies `apps/agent/dist`;
  the API serves it at `/agent`.
- New Prisma models → one migration. If the seed is extended to seed a demo realtor +
  trial subscription for dev, keep [[ci-gotchas]] in mind (the Docker seed reaches into `src`).
- **No new env var** (VITE_API_URL reused; the payment stub needs no external key) → the
  `check` / `e2e` CI jobs stay green without env changes. Verify the new app's `base: '/agent/'`
  and the API's `/agent` static ordering don't regress the existing web routes.

## 10. Constraints

- Uzbek user-facing copy; **English** identifiers/comments ([[english-code-only]]).
- **No new test files** ([[no-tests-unless-asked]]): verify with `yarn lint`, `yarn typecheck`,
  `yarn build` (all workspaces incl. `apps/agent`), the existing **111-test** suite staying
  green, plus a browser smoke of the trial→paywall→activate loop.
- The **payment stub** must be clearly labelled a test activation, never presented as a real
  charge (mirrors the dev-OTP / SMS stub precedent).
- FSD / Nest module boundaries respected; the agent module depends on services, and `apps/agent`
  never imports `apps/web`.
- The public marketplace agent display is untouched.

## 11. Verification

- Automated: `yarn lint` + `yarn typecheck` + `yarn build` clean across all four workspaces
  (`api`, `shared`, `web`, `agent`); existing 111 tests green; the API boots with the new module
  and every existing endpoint still responds.
- Manual (browser): sign in to `apps/agent` → "Rieltor bo'lish" → trial banner → create a
  collection, add a listing from the browser, add a note → force expiry (set `currentPeriodEnd`
  in the past) → confirm the paywall gate → "test to'lov" activate → cabinet re-unlocks.

## 12. Risks

- **New-app scaffolding** is the bulk of the work; keep `apps/agent` a thin mirror of `apps/web`'s
  config to avoid drift (Tailwind v4 tokens, Vite, RR7, TanStack setup).
- **`/agent` subpath serving** — the Vite `base` and the API static/fallback ordering must be
  correct or the web SPA fallback swallows `/agent/*`. Verify early.
- **Auth duplication** between web and agent is accepted debt; a shared package is the later fix.
- **Stub payment** means the "paid product" is not yet monetised for real — acceptable for the
  MVP foundation, explicit in copy.
