# Phase 8.1 — Cabinet Desktop Foundation (CRM + agent) — Design

**Status:** design (spec) — awaiting review
**Date:** 2026-09-20
**Branch:** `claude/phase-8.1-cabinet-desktop-foundation` (off master `b921385`)

## Goal

Make the two cabinet SPAs — `@rieltor/crm` (developer/застройщик) and
`@rieltor/agent` (realtor) — render as proper **desktop-responsive** apps
instead of a centred 480px "phone column", reusing the **web app's** existing
desktop layout language (the Uysot-style marketplace at `apps/web`), and give
each cabinet a **distinct accent colour** so they read as sibling products, not
copies of the public site.

This is **Phase A of three** (user-approved decomposition
"poydevor → CRM → agent"):

- **Phase 8.1 (this spec) — Foundation, both apps:** unlock the width, add a
  desktop header nav, recolour. After this phase both cabinets are full desktop
  width with a real header and their own colour, even though each page is still
  a single stretched column.
- **Phase 8.2 — CRM pages:** per-page responsive internal layout (card grids,
  detail main+sidebar, stat rows), richer widgets, more seed content.
- **Phase 8.3 — agent pages:** the same treatment for the 12 agent pages.

## Architecture

Both cabinets are client SPAs (`createBrowserRouter`, React 19 + Vite 6 +
React Router 7 + TanStack Query 5, FSD), served by the API at `/crm` and
`/agent` (Vite `base`). They already ship the responsive **tokens** the web app
uses (`--container-content/-tablet/-laptop/-desk`, `--breakpoint-md/-lg/-desk`
in each `app/index.css`) — but nothing consumes the wider tiers: every page
hard-caps itself at `max-w-content` (480px) and CRM re-renders a pill
`CabinetNav` at the top of each page, while agent has **no persistent nav at
all** (pages only link back to `/`).

The foundation, mirroring `apps/web/src/app/tab-layout.tsx` +
`widgets/site-header`:

1. A shared **`CabinetShell`** layout per app that wraps `<Outlet/>`, provides
   the responsive centred container (unlocking the 480px cap), and renders the
   header.
2. A **`CabinetHeader`** widget per app: sticky top header with brand + a
   horizontal section-nav (`NavLink`, icon+label, icon-only on tablet with the
   `aria-label` pattern from the web header) + a minimal account cluster. It
   replaces CRM's per-page `CabinetNav` and gives agent its first real nav.
3. A **recolour**: per-app accent tokens + replacing the hard-coded
   `from-violet-600` gradient (a Tailwind default, so token changes miss it)
   with a token-driven `from-accent`.

## Tech Stack

React 19, React Router 7 (`NavLink`, layout routes), Tailwind v4 (CSS-first
`@theme` tokens in `app/index.css`), TanStack Query 5, FSD. No new runtime
dependencies.

## Global Constraints

- **Code/identifiers/routes/comments in English**; only UI copy (and existing
  Uzbek strings) are Uzbek.
- **No new test files.** Verify with root turbo `yarn turbo run typecheck lint
  build --filter=@rieltor/crm --filter=@rieltor/agent` (never `yarn workspace
  <pkg> lint` — exit 127) plus a live browser smoke in docker/dev at desktop
  and phone widths. Editing existing fixtures is allowed.
- **No schema/migration and no seed changes in this phase** (foundation is
  frontend-only; seed enrichment lands in 8.2/8.3).
- **Additive, reversible** UI changes: the phone (<768) layout must remain
  visually intact; only the md/lg/desk tiers are added (the `app/index.css`
  comment "Phone (<768) and CIAN (>=1440) are frozen — new work is md:/lg:
  only" is respected, with the one exception that the 480px page cap is lifted
  so the wider tiers can take effect).
- **Reuse the web app's patterns** verbatim where they fit (container tiers,
  sticky header, `md:`/`lg:`/`desk:` grid idioms) — this phase adds no new
  design system, it extends the cabinets to the one the web app already uses.
- The web app (`apps/web`) is **not touched**.

## Non-Goals (this phase)

- Per-page internal responsive layout (grids, detail sidebars, stat rows) — that
  is Phase 8.2 (CRM) and 8.3 (agent). Phase 8.1 leaves page bodies as a single
  column; it only removes the width cap and adds the shell/header/colour.
- Seed/content enrichment — Phase 8.2/8.3.
- A mobile bottom tab bar (the web app has one; the cabinets keep a scrollable
  top nav on mobile — a bottom bar can be revisited later if wanted).
- Any change to auth, guards, data fetching, or API.

## Section 1 — Colour system

Each app's `src/app/index.css` currently declares the **same** violet as the
web app:

```
--color-accent: #6d28d9;
--color-accent-dark: #5b21b6;
--color-accent-soft: #f3eefe;
```

Replace per app (web keeps violet, untouched):

| App | `--color-accent` | `--color-accent-dark` | `--color-accent-soft` |
|-----|------------------|-----------------------|-----------------------|
| **crm** (blue) | `#2563eb` | `#1d4ed8` | `#eef4ff` |
| **agent** (teal) | `#0d9488` | `#0f766e` | `#e6f5f3` |

Components already consume `bg-accent` / `text-accent` / `bg-accent-soft` /
`shadow-accent`, so those recolour automatically. Two things do **not** and must
be fixed:

1. **Hard-coded `from-violet-600` gradient.** Every primary CTA and the two
   login modals use `bg-linear-to-br from-violet-600 to-accent-dark`. `violet-600`
   is a Tailwind default colour, not a token, so it stays violet after the token
   swap (a violet button on a blue/teal app). **Fix:** replace `from-violet-600`
   with **`from-accent`** in every occurrence in both apps (the gradient becomes
   accent → accent-dark, same-hue, and now recolours per app). Occurrences (from
   `git grep`): CRM — `app/root-layout.tsx`, `features/auth/ui/login-modal.tsx`
   (×2), `pages/{become-developer, building-detail, complex-detail, complexes,
   organization}` CTAs; agent — `app/root-layout.tsx`, `features/auth/ui/
   login-modal.tsx` (×2), `features/notes/ui/note-editor.tsx`, `pages/
   {become-realtor, collection-detail, profile, subscribe}` CTAs. The plan must
   `git grep -n "from-violet-600"` in each app and convert **all** hits (a
   single leftover is a Phase-A defect).

2. **Any other literal `violet-*` / `#6d28d9` / `#5b21b6`** in crm/agent `src`
   (outside `index.css`) is converted to the accent token equivalent. The plan
   greps to confirm none remain.

The web app's `--color-brand-green/-amber/-rose` semantic tokens stay as-is in
both cabinets (status colours, not brand accent).

## Section 2 — Responsive width foundation

The tier tokens already exist in each `app/index.css`
(`--container-content:30rem`, `--container-tablet:45rem`,
`--container-laptop:65rem`, `--container-desk:90rem`; `--breakpoint-md/-lg/-desk`).
Nothing changes in the token definitions.

The **480px lock** is lifted by moving width ownership into `CabinetShell`
(Section 3) and stripping each page's own outer `max-w-content` wrapper
(Section 5). The shell's container tiers mirror the web `tab-layout`:

- `<768` (phone): `max-w-content` (480px), centred — unchanged phone look.
- `md` (768): container grows to `max-w-tablet` (720px).
- `lg` (1024): `max-w-laptop` (1040px).
- `desk` (1440): `max-w-desk` (1440px), the CIAN width.

The `body` "phone frame" darker background (and its removal at ≥1440px) already
exists in `index.css` and is left as-is; it correctly stops framing once the
content fills the window.

## Section 3 — `CabinetShell` layout component (per app)

New: `apps/<app>/src/app/cabinet-shell.tsx` (FSD `app` layer, alongside
`root-layout.tsx`). Mirrors `apps/web/src/app/tab-layout.tsx`.

Responsibilities:
- Render `<CabinetHeader/>` (Section 4) as a sticky top bar.
- Wrap `<Outlet/>` in the responsive centred container:
  `mx-auto min-h-dvh max-w-content bg-surface md:max-w-tablet lg:max-w-laptop
  desk:max-w-desk` with padding tiers (`px-4 py-6 md:px-6 md:py-8 desk:px-8
  desk:py-10` — final values pinned in the plan to match the web rhythm).
- It does **not** re-gate auth — `RootLayout` (session gate) and the app's guard
  (`DeveloperGuard` / `CabinetGuard`) keep their jobs. `CabinetShell` nests
  **inside** the guard so the header only shows for a signed-in cabinet user.

Router wiring (Section 5) inserts `CabinetShell` as a layout route between the
guard and the page routes.

## Section 4 — `CabinetHeader` desktop nav (per app)

New: `apps/<app>/src/widgets/cabinet-header/ui/cabinet-header.tsx` (FSD
`widgets`). Models `apps/web/src/widgets/site-header`.

Layout:
- **Sticky bar:** `sticky top-0 z-50 border-b border-line bg-white/92
  backdrop-blur-xl` (same as web header).
- **Left:** brand — the app's name (CRM: "Rieltor**CRM**", agent:
  "Rieltor**Agent**") with the accent-coloured suffix, using the same
  logo-badge idiom as web `Logo` (accent gradient square + `Icon`). Links to `/`.
- **Centre/left-flow:** the section `NavLink`s (below), `flex items-center
  gap-1`, horizontally scrollable on phone (`overflow-x-auto` + `no-scrollbar`),
  inline from `md`.
- **Right:** minimal account cluster — the signed-in user's name/avatar (reuse
  the web header's avatar idiom) and, if the session store exposes a sign-out
  action, a "Chiqish" control. (The plan pins the exact `entities/session` API;
  if no sign-out exists, show identity only — adding auth actions is out of
  scope.)

Each `NavLink` uses the **web header idiom exactly**, including the a11y fix
just shipped there:

```
<Icon name={icon} className="h-[17px] w-[17px]" strokeWidth={2.1} />
<span className="hidden lg:inline">{label}</span>   // icon-only 768–1023
aria-label={label}                                  // accessible name in that range
end={to === '/'}                                    // home not always-active
active: bg-accent-soft text-accent / idle: text-ink-2 hover:bg-surface
```

**CRM sections** (exactly the current `CabinetNav` set — routes verified in
`crm/app/router.tsx`):

| Label | Route | `end` | Icon (existing `IconName`; plan pins) |
|-------|-------|-------|----------------------------------------|
| Tashkilot | `/` | yes | building/home |
| Majmualar | `/complexes` | no | building |
| Bandlar | `/bookings` | no | doc/calendar |
| Shartnomalar | `/contracts` | no | doc |
| Hisob | `/wallet` | no | wallet |
| Moliya | `/finance` | no | chart/money |

**Agent sections** (top-level routes from `agent/app/router.tsx`; agent has no
nav today, so this is the first one):

| Label | Route | `end` | Icon (plan pins) |
|-------|-------|-------|-------------------|
| Boshqaruv | `/` | yes | home/homeSolid |
| Mijozlar | `/leads` | no | phone/users |
| Qidiruv | `/browse` | no | search |
| Kolleksiyalar | `/collections` | no | heart/folder |
| Taqdimotlar | `/presentations` | no | doc |
| Eslatmalar | `/notes` | no | doc/note |
| Hisob | `/wallet` | no | wallet |
| Profil | `/profile` | no | user |

Icon names must be **existing** `IconName` values (`shared/ui/icon`); if a fitting
one is missing, add it to the icon set (additive SVG) rather than reuse a
misleading glyph — the plan enumerates the icon set and pins one per row.

Detail routes (`/complexes/:id`, `/buildings/:id`, `/contracts/:id`,
`/collections/:id`, `/presentations/:id`) are **not** nav entries; they keep
their parent section highlighted via the `NavLink` prefix match (no `end`).

The paywall `/subscribe` (agent) and the onboarding `become-*` pages are
**outside** `CabinetShell` (they render before a user has cabinet access), so
they get no header — matching how the router already isolates them.

## Section 5 — Router wiring + per-page cleanup

**Router (per app `app/router.tsx`):** insert `CabinetShell` as a layout route
wrapping the guarded page children:

```
{ element: <RootLayout/>, children: [
  { element: <DeveloperGuard/>, children: [        // agent: <CabinetGuard/>
    { element: <CabinetShell/>, children: [ ...existing page routes... ] },
  ]},
  ...isolated routes (agent /subscribe) stay as-is...
]}
```

For agent, the `become-realtor` view is rendered **by** `CabinetGuard` (not a
route), so confirm whether it should sit inside or outside the shell; per
Section 4 the onboarding shows **without** the header, so `CabinetGuard` must
render its onboarding branch outside `CabinetShell` (the plan pins the exact
nesting; the invariant is: no header until the user is a full cabinet member).

**Per-page cleanup (mechanical, both apps):**
- **CRM (10 pages):** remove the per-page `import { CabinetNav }` and its
  `<CabinetNav/>` render (now provided by the header), and strip the outer
  `mx-auto … max-w-content …` wrapper so the page inherits `CabinetShell`'s
  width. Pages: organization, complexes, complex-detail, building-detail,
  bookings, contracts, contract-detail, wallet, finance, become-developer
  (become-developer is outside the shell — see below).
- **agent (12 pages):** strip the outer `mx-auto … max-w-content …` wrapper.
  Pages: dashboard, profile, wallet, leads, browse, notes, collections,
  collection-detail, presentations, presentation-detail, subscribe,
  become-realtor.
- **Onboarding/paywall pages** (`become-developer`, `become-realtor`,
  `subscribe`) render outside `CabinetShell`, so they **keep** their own
  centred wrapper (they are standalone screens). The plan lists exactly which
  pages keep vs drop their wrapper.

The old `CabinetNav` widget (`crm/src/widgets/cabinet-nav`) becomes unused after
the header lands; delete it (and its barrel) to avoid dead code — a reviewer
would flag a leftover.

After this cleanup each page body is a single column that now stretches to the
shell width. Making that column into grids/sidebars is Phase 8.2/8.3.

## Section 6 — Mobile behaviour

- Phone (<768): the page column stays 480px-centred (via `CabinetShell`), the
  darker "phone frame" body background is unchanged. The header renders as a
  compact brand bar with the section nav as a **horizontally scrollable** pill
  row (replacing CRM's per-page pill nav; giving agent a nav it lacked). No
  bottom tab bar in this phase.
- The existing `AuthModalHost` / login modal and guards are untouched.
