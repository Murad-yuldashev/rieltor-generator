# Phase 7.2b — Realtor lead assistant (next-action + outreach draft) (design)

**Status:** approved design, ready for planning
**Branch:** `claude/phase-7.2b-lead-assistant` (off master `cb09c6a`, the Phase 7.2a merge)
**Roadmap:** Phase 7 (Growth layer, last roadmap phase) — 7.1 mortgage → **7.2 AI assistant** → 7.3 map → 7.4 journal. Phase 7.2 slices: 7.2a buyer AI search (done) → **7.2b realtor lead assistant** → 7.2c realtor AI content → 7.2d developer AI insights.

---

## 1. Goal

Give a realtor a one-tap AI helper for a **claimed lead**: from the buyer's request
(deal/type/district/rooms/budget/area/note) and the lead's current funnel stage, produce (1) a short
**next-action recommendation** and (2) a ready-to-send **first-outreach message** (Uzbek, copyable
into Telegram/SMS). It reuses the existing `GeminiService`, and — like the valuation feature — is a
**hybrid**: a template result is always computed from the lead's structured fields, and Gemini enriches
it when a key is available. The realtor edits and sends the draft themselves (no send integration).

This is the second slice of the Phase 7.2 AI-assistant subsystem; it follows the reuse pattern 7.2a
established (a `GeminiService` call with strict server-side validation of the model output) and adds the
hybrid always-a-usable-result fallback the valuation feature uses.

## 2. Scope

**In scope (7.2b):**

- A guarded, ownership-checked **`POST /api/leads/:id/assist`**: the claiming realtor gets
  `{ ai, nextAction, message }` for their claimed lead — Gemini-authored when available, a structured
  template otherwise.
- A shared DTO for the response.
- An **"AI yordam"** affordance on the claimed-lead surface in `apps/agent` (the leads page) that calls
  the endpoint and shows the next-action + a **copyable** outreach draft.

**Deferred (named, not built):**

- Actually **sending** the message (Telegram/SMS/call integration) — 7.2b only drafts a copyable text.
- AI **listing matching** (suggesting specific units for the lead), multi-turn conversation, a saved
  message/assist history, tone/length controls, voice.
- Storing the generated assist (7.2b is stateless — generated on demand, nothing persisted).
- The other Phase 7.2 slices (7.2c AI content, 7.2d developer insights) and the rest of Phase 7.

## 3. Design decisions (resolved)

1. **Two outputs: next-action + outreach draft.** Gemini returns a JSON `{ nextAction, message }`; the
   server validates it (strict) and falls back to the template if unusable.
2. **Hybrid, always-usable (like valuation).** A pure template `{ nextAction, message }` is always
   computed from the lead's structured fields + funnel stage; no API key / an unusable model response
   → the template (never a 503). Gemini is an enrichment, not a dependency.
3. **Ownership-gated (private buyer data).** The route lives on the existing
   `@Controller('leads')` (already `JwtGuard + RealtorGuard`) and verifies `lead.claimedById ===
caller` → else 403 ("Bu lead sizniki emas"), and the lead must be claimed (outcomeStage set) → else
   409 — mirroring the 4.3 `setOutcome` check. Because `RealtorGuard` requires an active subscription,
   the assistant is naturally a paid-realtor tool.
4. **Draft-only, copyable.** No send integration; the realtor copies the message and sends it via their
   own channel. This keeps 7.2b free of partner dependencies.
5. **Stateless.** The assist is generated per request and not stored — no data-model change.

## 4. Data model

**No change.** 7.2b reads existing `PropertyRequest` fields; nothing is written or added.

## 5. Backend

### 5.1 Shared DTO (`packages/shared/src/schemas.ts`)

```ts
/** The realtor lead-assistant result. ai=true → Gemini-authored; ai=false → structured template. */
export const LeadAssistResponseSchema = z.object({
  ai: z.boolean(),
  nextAction: z.string(), // short Uzbek next-step recommendation
  message: z.string(), // a copyable first-outreach draft (Uzbek)
});
```

Plus the inferred type `LeadAssistResponse`. (No request body — the lead id is a path param.)

### 5.2 LeadAssistService + route (`apps/api/src/leads/`)

- A new **`LeadAssistService`** (injects `PrismaService` + `GeminiService`), registered in
  `LeadsModule`'s providers and injected into `LeadsController` alongside the existing services (the
  established `FixationService` pattern). `GeminiService` is exported by `AiModule` — import `AiModule`
  into `LeadsModule` (or provide `GeminiService` per the module's existing wiring).
- **`assist(leadId, realtorId): Promise<LeadAssistResponse>`:**
  - Load the lead: `prisma.propertyRequest.findUnique({ where: { id: leadId }, select: { claimedById,
outcomeStage, deal, type, district, roomsMin, priceMaxSom, areaMinM2, note } })`. Not found → 404.
  - **Ownership + state:** `lead.claimedById !== realtorId` → `ForbiddenException('Bu lead sizniki
emas')`; `lead.outcomeStage == null` → `ConflictException('Bu lead hali olinmagan')`.
  - Compute the **template** `{ nextAction, message }` (always — §5.3).
  - Call Gemini: build the prompt (§5.4) → `gemini.generate(prompt, { maxTokens: 400 })`. If it returns
    a usable JSON, use it (`ai: true`); otherwise the template (`ai: false`).
- **Route:** `@Post(':id/assist') assist(@Param('id') id, @CurrentUser() u) { return
this.leadAssist.assist(id, u.id); }` on `LeadsController` (declared after the literal-path routes, per
  the existing convention). Guards inherited from the controller.

### 5.3 The template (`apps/api/src/leads/lead-assist.template.ts`) — pure, always computable

- `nextActionForStage(stage)`: a map from `LeadOutcomeStage` to a short Uzbek recommendation, e.g.
  `NEW` → "Xaridorga qo'ng'iroq qilib, byudjet va afzalliklarni aniqlang.", `CONTACTED` → "Mos
  variantlar tayyorlab, ko'rsatuvga taklif qiling.", `MEETING` → "Ko'rsatuvdan so'ng shartlarни
  kelishing va taklif yuboring.", `WON`/`LOST` → a closing note. (A `Record<LeadOutcomeStage, string>`
  — finite keys, so no `noUncheckedIndexedAccess` gap — the 7.2a lesson.)
- `templateMessage(lead)`: a filled Uzbek outreach draft from the structured fields, e.g.
  "Assalomu alaykum! Siz `<deal-word>` uchun `<district?>` `<roomsMin?>`-xonali uy qidirayotgan
  ekansiz`<, byudjet ... gacha>`. Men rieltorман, sizga mos variantlarни topishga yordam beraman.
  Qulay vaqtda gaplashsak bo'ladimi?" — every interpolated field guarded for null; money formatted with
  the ICU-free grouping helper (the 7.2a lesson). No buyer name in the template (privacy-safe; the
  realtor personalizes).
- `buildAssistTemplate(lead): { nextAction, message }` — combines the two.

### 5.4 The prompt + output validation (`apps/api/src/leads/lead-assist.parse.ts`) — untrusted output

- `buildAssistPrompt(lead)`: an Uzbek instruction — role ("rieltorga lead bilan ishlashda yordam
  beruvchi yordamchi"), the lead's fields + stage, and "Return JSON only: `{ \"nextAction\": string,
\"message\": string }`; the message is a short, polite Uzbek first-outreach to the buyer."
- `parseAssist(raw: string | null, template): LeadAssistResponse` — pure, **never trusts the model**:
  `raw == null` → `{ ai: false, ...template }`; strip code fences; `JSON.parse` in try/catch → on throw,
  the template; validate the object has non-empty string `nextAction` + `message` (a small Zod schema)
  → success → `{ ai: true, nextAction, message }` (trimmed, length-capped); failure → the template.
  Never throws. (The same discipline as 7.2a's `buildSearchResponse`, so it is Node-checkable in
  isolation.)

## 6. Frontend (`apps/agent`, FSD)

- **`features/lead-assist/`** — a new feature:
  - `model/use-lead-assist.ts` — `useLeadAssist(leadId)` (a mutation:
    `apiPost('/api/leads/${leadId}/assist', LeadAssistResponseSchema)`; on network/HTTP error, resolve
    to a minimal client fallback so a failure never breaks the panel).
  - `ui/lead-assist-panel.tsx` — an "AI yordam" button (props `{ leadId }`); on click, call the
    endpoint, then show the **next-action** line + the **message** in a read-only box with a **"Nusxa
    olish"** (copy) button (`navigator.clipboard.writeText`, guarded). A small "AI" / "namuna" (template)
    tag from `ai`. Uzbek copy.
- **Wire into the leads page** (`apps/agent/src/pages/leads/ui/leads-page.tsx`): render
  `<LeadAssistPanel leadId={lead.id} />` for a **claimed** lead (the row/detail already gated to the
  realtor's own claimed leads). The panel takes only the id — it does **not** import the `leads` feature
  (FSD: a feature imports only entities/shared; the page composes both).
- **FSD:** `lead-assist` imports only `@rieltor/shared` + the agent `shared/api` client (+ shared UI).
  `yarn lint` must pass (apps/agent has the same `boundaries` rules as apps/web).

UI copy Uzbek; identifiers/routes/comments English.

## 7. Rulings & invariants (load-bearing)

- **R1 — never trust the model's shape.** `parseAssist` JSON-parses in try/catch and validates
  `{ nextAction, message }` (non-empty strings) before use; any bad response → the template, never a 500
  and never an unvalidated object to the client.
- **R2 — hybrid, always usable.** The template `{ nextAction, message }` is always computable from the
  lead's structured fields + stage; no key / outage / unusable parse → the template with `ai: false`
  (never a 503). Gemini only enriches.
- **R3 — ownership + subscription gated.** `POST /api/leads/:id/assist` is on the guarded
  `@Controller('leads')` (`JwtGuard + RealtorGuard`, i.e. an active subscription); the service verifies
  `lead.claimedById === caller` (else 403) and `outcomeStage != null` (else 409). A realtor can never
  get another realtor's (or an unclaimed) lead's assist — the buyer's request stays private to the
  claimer.
- **R4 — draft-only, stateless, additive.** No send integration, nothing stored, no data-model change,
  no new migration; the route is added to the existing leads controller/module.
- **R5 — type/style discipline (7.2a lessons).** Any stage→label map is `Record<LeadOutcomeStage,
string>` (finite keys, no `noUncheckedIndexedAccess` gap); money in the template uses the ICU-free
  grouping helper (no `toLocaleString`); every interpolated lead field is null-guarded.

## 8. Verification (no new test files — per project rule)

- `yarn typecheck` + `yarn lint` + `yarn build` green across api / shared / agent.
- Compiled-JS / pure-Node scratch (against a real `nest build`, never `tsx`, run from `apps/api` so
  `@rieltor/shared` resolves) of `parseAssist` + `buildAssistTemplate`: (a) `parseAssist(null, tpl)` →
  `{ ai: false, ...tpl }`; (b) a non-JSON string → template; (c) a valid `{ nextAction, message }` →
  `ai: true` with those fields (trimmed); (d) a JSON missing `message` (or empty string) → template;
  (e) `buildAssistTemplate` for each stage + a lead with null district/rooms/budget → a coherent,
  no-`undefined` message and a stage-appropriate next action.
- Booted-Nest HTTP check (never tsx): `POST /api/leads/:id/assist` — no auth → 401; a realtor who is
  **not** the claimer → 403; an unclaimed lead → **403** (ownership is checked before state, mirroring
  `setOutcome`, so a null `claimedById` returns 403; the `outcomeStage == null` → 409 branch is
  defensive and not reachable over HTTP — `claim()` sets `claimedById` + `outcomeStage` atomically —
  exercisable only via a hand-seeded row in the compiled scratch); the claiming realtor (key unset) →
  200 with `ai: false` and a non-empty `nextAction` + `message`.
- Browser smoke: in `apps/agent`, a claimed lead's "AI yordam" button shows the next-action + a copyable
  message; "Nusxa olish" copies it.
- Full suite green before merge (shared 18, web 34, api 37, e2e 22 → 111), zero new test files.
