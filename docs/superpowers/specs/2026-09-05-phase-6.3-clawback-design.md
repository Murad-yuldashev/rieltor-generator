# Phase 6.3 — Commission clawback / sale unwind (design)

**Status:** approved design, ready for planning
**Branch:** `claude/phase-6.3-clawback` (off master `5e0b2fa`, the Phase 6.2 merge)
**Depends on:** 5.2 (Booking convert→SOLD), 5.4 (Fixation + commission), 6.1 (org wallet + funded commission), 6.2 (Contract)
**Roadmap:** Phase 6 — 6.1 org wallet → 6.2 Contracts → **6.3 clawback/reconciliation** → 6.4 payment schedules + debtors + finance/KPI.

---

## 1. Goal

Give a closed sale an **unwind path**. Today `Booking.convert`→SOLD is terminal: it flips the unit
to SOLD, converts the fixation (paying the realtor a commission and debiting the developer org's
wallet), and writes a Contract — with **no way to reverse any of it** if the deal later falls
through. 6.3 introduces the exact **inverse of convert**: a developer cancels the Contract, which
atomically claws back the realtor commission, refunds the org wallet, and returns the inventory
(unit / booking / fixation) to a re-sellable state.

The reversal is **net-zero** for the platform: the realtor's `COMMISSION` credit is undone by an
equal `COMMISSION_CLAWBACK` debit, and the org's `COMMISSION_DEBIT` is undone by an equal
`COMMISSION_REFUND` credit — both at the snapshot amount that was actually paid at convert.

## 2. Scope

**In scope (6.3):**

- A **cancel Contract** operation (`POST /api/crm/contracts/:id/cancel`) that performs the full,
  atomic, idempotent sale unwind (money + inventory state).
- Two reversal wallet primitives: realtor `debitForClawback` (unconditional, negative-capable) and
  org `creditRefund` (unconditional increment) — mirroring the 6.1 funded-commission idioms in reverse.
- Reversal **visibility**: the new ledger entries surface in the existing wallet ledgers (realtor
  cabinet + developer CRM); the contracts list/detail shows the `CANCELLED` status + reason.

**Deferred (named, not built):**

- Aggregate **reconciliation dashboard** (org/platform net commission after clawbacks, reversed-deal
  register) → **6.4** (finance/KPI).
- Two-party / realtor confirmation of the reversal (developer-initiated only in 6.3).
- Partial clawback, clawback dispute / appeal, refund windows / penalties.
- Automatic re-listing of the freed unit on the public marketplace.
- Re-fixate reset of a reversed `Fixation.commissionSom` (a 5.4 re-fixate concern).

## 3. Design decisions (the four forks, resolved)

1. **Full unwind (inventory + money).** The cancel is the complete inverse of convert: money
   clawback + `Contract → CANCELLED` + `Fixation → CANCELLED` + `Booking → CANCELLED` +
   `Unit → AVAILABLE` (re-sellable). Not a money-only reversal.
2. **Developer-initiated.** The org owns the deal and knows when it falls through, so the developer
   cancels the Contract (`POST /api/crm/contracts/:id/cancel {reason}`). Moderator-only and
   two-party confirmation are out of scope.
3. **Unconditional clawback (realtor wallet may go negative).** The commission is genuinely owed
   back, so the realtor is debited in full even if already spent — the wallet goes into debt. This
   mirrors 6.1's "org wallet may go negative" philosophy exactly; the realtor `Wallet.balanceSom`
   has no CHECK constraint and is negative-capable.
4. **Mechanism + ledger visibility only.** The `COMMISSION_CLAWBACK` / `COMMISSION_REFUND` rows
   appear in the existing wallet ledgers and the contract shows `CANCELLED`; the aggregate
   reconciliation dashboard is deferred to 6.4.

## 4. Data model (additive migration)

All changes are additive: two enum values and two nullable columns. No new tables.

```prisma
enum WalletTxType {
  TOPUP
  LEAD_CLAIM
  COMMISSION
  COMMISSION_CLAWBACK // 6.3: realtor commission reversed when a sale is unwound (debit)
}

enum OrgWalletTxType {
  TOPUP
  COMMISSION_DEBIT
  COMMISSION_REFUND // 6.3: org commission-debit reversed when a sale is unwound (credit)
}

model Contract {
  // ...existing fields (6.2)...
  // status ContractStatus already has ACTIVE|CANCELLED; 6.3 writes CANCELLED.
  cancelReason String?   // 6.3: why the sale was unwound (set with status=CANCELLED)
  cancelledAt  DateTime? // 6.3: when the contract was cancelled
}
```

`Booking.cancelReason` (5.2) and `Fixation.cancelledAt` (5.4) already exist and are reused.

Migration name: `phase_6_3_clawback`. Two `ALTER TYPE … ADD VALUE` (proven additive in this repo —
5.1 `UserRole`, 5.4 `WalletTxType += COMMISSION`) + two `ALTER TABLE "Contract" ADD COLUMN` nullable.
No `DROP`, no rewrite of existing rows.

## 5. Backend

### 5.1 Shared DTOs (`packages/shared/src/schemas.ts`)

- `WalletTxTypeSchema` gains `'COMMISSION_CLAWBACK'`; `OrgWalletTxTypeSchema` gains `'COMMISSION_REFUND'`.
- `ContractSchema` gains `cancelReason: z.string().nullable()` and `cancelledAt: z.string().nullable()`
  (ISO). `ContractRowSchema` inherits them via `.extend`.
- New `ContractCancelSchema = z.object({ reason: z.string().min(1).max(500) })` (+ `ContractCancel` type).
- **`contract.service.ts:toContract` must also map the two new fields** — `cancelReason: c.cancelReason`
  and `cancelledAt: c.cancelledAt ? c.cancelledAt.toISOString() : null` — otherwise every contract DTO
  (list/getOne/sign/cancel) fails the now-stricter `ContractSchema` parse. `getOne`/`list`/`sign` then
  return them as `null` for ACTIVE contracts (nullable), which is correct.

### 5.2 Reversal wallet primitives (caller-tx, unconditional)

`WalletService.debitForClawback` — the reverse of `credit` (`wallet.service.ts:121`); unconditional
(no `FOR UPDATE`, no 402), negative-capable, `upsert`-safe:

```ts
async debitForClawback(
  tx: Prisma.TransactionClient,
  userId: string,
  amountSom: bigint,
  ref: { fixationId?: string } = {},
): Promise<void> {
  const wallet = await tx.wallet.upsert({
    where: { userId },
    create: { userId, balanceSom: -amountSom }, // defensive: a credited realtor always has a wallet
    update: { balanceSom: { decrement: amountSom } },
    select: { id: true },
  });
  await tx.walletTransaction.create({
    data: { walletId: wallet.id, type: 'COMMISSION_CLAWBACK', amountSom, fixationId: ref.fixationId ?? null },
  });
}
```

`OrgWalletService.creditRefund` — the reverse of `debitForCommission` (`org-wallet.service.ts:99`);
unconditional increment:

```ts
async creditRefund(
  tx: Prisma.TransactionClient,
  orgId: string,
  amountSom: bigint,
  ref: { fixationId?: string },
): Promise<void> {
  const w = await tx.orgWallet.upsert({
    where: { orgId },
    create: { orgId, balanceSom: amountSom },
    update: { balanceSom: { increment: amountSom } },
    select: { id: true },
  });
  await tx.orgWalletTransaction.create({
    data: { orgWalletId: w.id, type: 'COMMISSION_REFUND', amountSom, fixationId: ref.fixationId ?? null },
  });
}
```

`amountSom` is stored POSITIVE in both ledgers; direction is carried by the type (mirrors 6.1).

### 5.3 The unwind — `ContractService.cancel(orgId, id, reason)`

`ContractService` gains two injected deps: `WalletService` and `OrgWalletService` (both already
provided in `DeveloperModule` — `BookingService` injects them the same way, so **no module change**).
`cancel` owns its `$transaction` (unlike `create`, which is caller-tx); it is the inverse of the
convert branch (`booking.service.ts:118-192`):

```ts
async cancel(orgId: string, id: string, reason: string): Promise<ContractRow> {
  return this.prisma.$transaction(async (tx) => {
    // Org-scoped existence check → 404 (foreign/missing).
    const found = await tx.contract.findFirst({
      where: { id, orgId },
      select: { id: true, unitId: true, bookingId: true, fixationId: true },
    });
    if (!found) throw new NotFoundException('Shartnoma topilmadi');

    // Atomic ACTIVE→CANCELLED gate — the single serialization point (inverse of convert's
    // booking updateMany). A re-fired/concurrent cancel gets count===0 → nothing reverses twice.
    const { count } = await tx.contract.updateMany({
      where: { id, orgId, status: 'ACTIVE' },
      data: { status: 'CANCELLED', cancelReason: reason, cancelledAt: new Date() },
    });
    if (count !== 1) throw new ConflictException('Shartnoma allaqachon bekor qilingan');

    // Full inventory reversal.
    await tx.unit.update({ where: { id: found.unitId }, data: { status: 'AVAILABLE' } });
    await tx.booking.update({
      where: { id: found.bookingId },
      data: { status: 'CANCELLED', cancelReason: reason },
    });

    // Money reversal — only on the fixation path, at the snapshot amount actually paid.
    if (found.fixationId) {
      const fixation = await tx.fixation.findUnique({
        where: { id: found.fixationId },
        select: { id: true, realtorId: true, commissionSom: true },
      });
      if (fixation) {
        await tx.fixation.update({
          where: { id: fixation.id },
          data: { status: 'CANCELLED', cancelledAt: new Date() },
        });
        const commissionSom = fixation.commissionSom ?? 0n;
        if (commissionSom > 0n) {
          await this.wallet.debitForClawback(tx, fixation.realtorId, commissionSom, { fixationId: fixation.id });
          await this.orgWallet.creditRefund(tx, orgId, commissionSom, { fixationId: fixation.id });
        }
      }
    }

    // Return the cancelled row with unit context (same shape as getOne).
    const row = await tx.contract.findFirst({
      where: { id, orgId },
      include: { unit: { select: { number: true, building: { select: { name: true } } } } },
    });
    return { ...toContract(row!), unitNumber: row!.unit.number, buildingName: row!.unit.building.name };
  });
}
```

### 5.4 Controller (`contract.controller.ts`)

Add to the existing `@Controller('crm/contracts')` (JwtGuard + DeveloperGuard):

```ts
@Post(':id/cancel')
async cancel(@CurrentUser() u: { id: string }, @Param('id') id: string, @Body() body: unknown) {
  const { reason } = ContractCancelSchema.parse(body);
  return this.contracts.cancel(await this.developer.orgIdOf(u.id), id, reason);
}
```

## 6. Frontend

- **`apps/crm` contract-detail** (`useCancelContract(id)` + a "Bekor qilish" control): shown only when
  `status === 'ACTIVE'`; collects a required `reason` (inline field), calls the cancel mutation,
  invalidates `['crm-contracts']` (+ the detail key). A `CANCELLED` contract renders a red status
  badge plus the `cancelReason` and `cancelledAt`. The sign control is hidden once cancelled.
- **`apps/crm` org-wallet ledger** (`pages/wallet`): render `COMMISSION_REFUND` as a green credit
  ("Komissiya qaytarildi").
- **`apps/agent` realtor wallet ledger**: render `COMMISSION_CLAWBACK` as a debit
  ("Komissiya qaytarib olindi"), sharing the app's existing debit style, and gate the LEAD_CLAIM
  "(lead)" amount suffix so it does not leak onto the clawback. The realtor's fixation view already
  reflects `Fixation → CANCELLED`.

UI copy Uzbek; identifiers/routes/comments English.

## 7. Rulings & invariants (load-bearing)

- **R1 — exactly-once reversal.** The `Contract` `ACTIVE→CANCELLED` `updateMany` `count===1` gate is
  the single serialization point (inverse of convert's booking gate). A concurrent/re-fired cancel
  gets `count===0` → 409, so the clawback, refund, and state reversal run **at most once**.
- **R2 — net-zero at the snapshot amount.** The reversal uses `Fixation.commissionSom` (the exact
  amount credited/debited at convert), so realtor `−commissionSom` + org `+commissionSom` returns the
  platform to neutral. The live unit price is NOT re-read (it could have changed).
- **R3 — unconditional, negative-capable clawback.** The realtor debit never blocks and may push the
  wallet negative (debt); the org refund is an unconditional increment. Amounts stored POSITIVE,
  direction by type.
- **R4 — full inventory reversal.** `Unit → AVAILABLE`, `Booking → CANCELLED` (+reason),
  `Fixation → CANCELLED` (+cancelledAt). The freed unit is re-sellable; the cancelled fixation is
  re-fixatable via the 5.4 path.
- **R5 — walk-in (no fixation) contract.** No money to reverse; only `Contract/Booking → CANCELLED`
  and `Unit → AVAILABLE`.
- **R6 — org-scoping.** `cancel` is gated by `orgId = orgIdOf(caller)`; a foreign/missing id → 404.
  Only `ACTIVE` contracts cancel (already-CANCELLED → 409).
- **R7 — additive-only + money-as-string.** Two enum values + two nullable columns; ledger amounts
  `String(bigint)`.
- **R8 — `FixationStatus.CANCELLED` reused** (not a new `REVERSED` value) so the 5.4 re-fixate path
  is unchanged; the reversal audit trail is the `COMMISSION_CLAWBACK` ledger row + `contract.cancelReason`.
