# Phase 4.3 — Conversion tracking + analytics + scoring refinement design

_Date: 2026-09-01 · Branch: `claude/phase-4.3-conversion-tracking` · Base: master `401bd07` · Part of: Phase 4 (Product C — Lead market) · Depends on: 4.1 (Lead / exclusive claim), 4.2 (wallet / paid claim)_

## 1. Goal

Close the last gap in the lead market's feedback loop. Today a lead's life ends at
**CLAIMED**: a realtor pays, gets the buyer's contact, and nothing records what happened
next. Phase 4.3 lets the claiming realtor record the **outcome** of a claimed lead
(a small funnel: contacted → meeting → won/lost, with a reason on a loss), surfaces
that as **analytics** (the realtor's own funnel + a platform funnel for moderators), and
feeds it back into **lead scoring** so future leads in segments that historically convert
score higher. The scoring feedback is confidence-weighted: with little data it falls back
to the current deterministic score, exactly like the valuation model stayed formula-based
until comparables exist. **Refunds/disputes remain deferred** — the outcome data is the
foundation a future refund system would build on, but 4.3 records, it does not settle money.

## 2. Scope

1. **Outcome model** — three additive fields on `PropertyRequest` (the outcome is 1:1 with
   an exclusively-claimed lead, so no new table) + two enums; the claim sets the initial
   stage.
2. **Outcome recording** — `PATCH /api/leads/:id/outcome` (the claimer only) advances the
   stage / sets the lost reason.
3. **Conversion-weighted scoring** — a pure `conversionAdjustment` blended onto the existing
   pure `computeLeadScore` at lead-create time, driven by the segment's historical win rate
   with Bayesian shrinkage toward the global rate.
4. **Analytics** — `GET /api/leads/stats` (the realtor's own funnel) and
   `GET /api/moderation/conversion` (platform funnel + per-segment win rates, moderators).
5. **UI** — a cabinet "Mening leadlarim" page (`apps/agent`: claimed leads + an outcome
   stepper + a personal funnel summary) and a web moderator page (`apps/web`:
   `/moderation/conversion`, read-only platform funnel + segment table).

### Non-goals

- **Refunds / disputes / lead-quality guarantees** — a `WRONG_NUMBER`/`NOT_SERIOUS` loss
  records the fact; it does not refund the claim or open a dispute. Deferred (later phase).
- **Retroactive rescoring** — the conversion adjustment applies to **newly created** leads;
  existing OPEN leads keep the score they were created with (no churny rescore job).
- **Author/buyer reliability scoring** — the chosen signal is segment win-rate, not
  per-author history (a later option if repeat authors prove common).
- **A strict outcome state machine** — the realtor may set any stage (to fix a mis-tap);
  the only guards are ownership + the lead being CLAIMED.
- **Real-time analytics / charts library** — counts and rates rendered as plain lists/tables
  (the presentations analytics precedent), no new charting dependency.
- Marketplace, wallet, and the 4.1/4.2 claim/exclusivity/debit logic — unchanged except the
  claim's new "set initial outcome stage" line and the create path's new score adjustment.

## 3. Data model (Prisma)

Additive: three fields on `PropertyRequest`, two new enums, one index. No existing model changed.

```prisma
enum LeadOutcomeStage {
  NEW         // just claimed, not yet contacted
  CONTACTED
  MEETING
  WON         // terminal — deal done
  LOST        // terminal — see lostReason
}

enum LeadLostReason {
  NO_RESPONSE
  WRONG_NUMBER
  NOT_SERIOUS
  BOUGHT_ELSEWHERE
  OTHER
}

model PropertyRequest {
  // ... existing fields ...
  outcomeStage     LeadOutcomeStage?   // null until claimed; set to NEW on claim
  lostReason       LeadLostReason?     // set iff outcomeStage == LOST
  outcomeUpdatedAt DateTime?

  // ... existing @@index([status, createdAt]) ...
  @@index([deal, type, outcomeStage])  // supports the segment win-rate counts
}
```

- The **claim** (4.2's `LeadsService.claim`, inside the existing transaction) sets
  `outcomeStage: 'NEW'` alongside the `CLAIMED`/`claimedById`/`claimedAt` write. One added
  field on the same update — no new lock, no new round-trip.
- `WON`/`LOST` are the **resolved** (terminal) states; `NEW`/`CONTACTED`/`MEETING` are
  in-progress. The scoring win-rate is `WON / (WON + LOST)` over a segment.

## 4. Outcome recording

**`PATCH /api/leads/:id/outcome`** (RealtorGuard + ownership) body `{ stage: LeadOutcomeStage,
lostReason?: LeadLostReason }`:

- 404 if the lead does not exist; **403** if `claimedById !== callerId` (only the claimer
  owns the outcome); **409** (or 400) if the lead is not `CLAIMED` (`outcomeStage` is null).
- `stage === 'LOST'` ⇒ `lostReason` **required** (400 if missing); any other stage ⇒
  `lostReason` is cleared to `null`.
- Writes `outcomeStage`, `lostReason`, `outcomeUpdatedAt = now()`. Returns the updated lead
  (the `Lead` DTO, extended with the outcome fields).
- No strict transition order — the realtor can move backward to correct a mistake. The
  ownership + CLAIMED checks are the only invariants.

The lead's `status` stays `CLAIMED` throughout (the outcome funnel is orthogonal to the
OPEN/CLAIMED lifecycle; a `WON`/`LOST` outcome does **not** reopen or close the lead).

## 5. Conversion-weighted scoring

The current pure function stays the base; a second pure function computes the adjustment; the
service composes them at create time.

```ts
// lead-scoring.ts — both pure, unit-testable.
export function computeLeadScore(input): number {
  /* unchanged: 0..100 base */
}

const PRIOR_STRENGTH = 10; // alpha — how many "prior" observations the global rate is worth
const ADJ_MAX = 15; // the adjustment is bounded to +/- this
const ADJ_GAIN = 40; // K — maps a (rate - global) gap to score points

/**
 * Confidence-weighted score adjustment from a segment's resolved outcomes.
 * With few/no resolved leads, rHat -> globalRate, so the adjustment -> 0 (pure base).
 */
export function conversionAdjustment(won: number, lost: number, globalRate: number): number {
  const resolved = won + lost;
  if (resolved === 0) return 0;
  const rHat = (won + PRIOR_STRENGTH * globalRate) / (resolved + PRIOR_STRENGTH);
  const raw = Math.round(ADJ_GAIN * (rHat - globalRate));
  return Math.max(-ADJ_MAX, Math.min(ADJ_MAX, raw));
}
```

- **Segment** = `deal + type + budgetTier`, where `budgetTier` buckets `priceMaxSom` into a
  few coarse ranges (a small constant table; `null` budget is its own bucket). Concrete
  buckets: `NONE` (priceMaxSom null), `LOW` (≤ 300 mln), `MID` (300 mln – 800 mln),
  `HIGH` (> 800 mln) — a pure `budgetTier(priceMaxSom)` helper maps to a bucket and to its
  `priceMaxSom` range for the count `WHERE`. District is **excluded** so segments do not
  fragment into single-sample cells.
- **globalRate** = `WON / (WON + LOST)` over **all** resolved leads; when there are no
  resolved leads at all, `globalRate` is undefined ⇒ treated as making every adjustment `0`
  (pure base). (Implementation: if total resolved is 0, skip the adjustment entirely.)
- At **create** time in **`RequestsService.create`** (`apps/api/src/requests` — the buyer's
  `POST /api/requests` post that becomes a lead; it already computes `computeLeadScore` +
  `priceForScore`):
  1. `base = computeLeadScore(input)`.
  2. Count the segment's `won`/`lost` and the global `won`/`lost` (four cheap `count`
     queries via the service's existing Prisma client, scoped by
     `outcomeStage IN (WON, LOST)`; the segment adds `deal`/`type`/the `budgetTier` range;
     lead creation is a cold path).
  3. `final = clamp(base + conversionAdjustment(segWon, segLost, globalRate), 0, 100)`.
  4. Persist `score = final`; `priceForScore(final)` sets `priceSom` (unchanged mapping).
- Existing leads are **not** rescored. The loop improves newly created leads as data grows.
  With zero history the behaviour is byte-identical to 4.1's scoring.

## 6. Analytics

- **Realtor funnel** — `GET /api/leads/stats` (RealtorGuard): over the caller's claimed leads,
  a count per `outcomeStage` (NEW/CONTACTED/MEETING/WON/LOST), the **win rate**
  `WON / (WON + LOST)` (or null when no resolved), and a breakdown of `lostReason`. Shown at
  the top of the cabinet "Mening leadlarim" page.
- **Platform funnel** — `GET /api/moderation/conversion` (RolesGuard MODERATOR/ADMIN,
  read-only): the same stage counts across **all** claimed leads, plus a **per-segment**
  table (`deal + type + budgetTier` → won, lost, win rate) — the very aggregates the scoring
  consumes, surfaced so a moderator can see which segments convert. No mutation.

Both are plain `groupBy`/`count` reads (no new dependency); rates computed in a small pure
helper so they are testable and consistent between the two endpoints.

## 7. UI

- **Cabinet (`apps/agent`) — "Mening leadlarim" (`/agent/leads`, under CabinetGuard,
  reachable from the nav):**
  - The **personal funnel summary** at the top (from `GET /api/leads/stats`): stage counts +
    win rate + lost-reason breakdown.
  - The **claimed leads list** (`GET /api/leads/mine`, its `Lead` DTO extended with the
    outcome fields): each lead shows its details + the buyer contact (already revealed on
    claim) + an **outcome stepper** — buttons/controls to set the stage
    (NEW→CONTACTED→MEETING→WON/LOST) and, on LOST, pick a reason — calling
    `PATCH /api/leads/:id/outcome` and invalidating the leads + stats queries.
  - Uzbek copy for the stage/reason labels; English identifiers.
- **Web (`apps/web`) — `/moderation/conversion` (moderator, alongside the existing
  `/moderation/realtors` + `/moderation/reviews`):** the platform funnel counts + the
  per-segment win-rate table, read-only.

## 8. Modules & wiring

- `apps/api`: the outcome (`PATCH /api/leads/:id/outcome`) + realtor stats
  (`GET /api/leads/stats`) endpoints extend the existing **`LeadsModule`**
  (`LeadsController` + `LeadsService`); the scoring change is in **`RequestsService.create`**
  (`RequestsModule`, which already imports `lead-scoring.ts`) + the two pure functions in
  `lead-scoring.ts` — `RequestsService` runs the segment/global counts on its existing Prisma

  `Lead` schema, `LeadOutcomeUpdate` (`{ stage, lostReason? }`), `LeadStats`

- `apps/web`: the `/moderation/conversion` page.

## 10. Verification

- Automated: `yarn lint`/`typecheck`/`build` (4 workspaces); the existing suite green;
  additive migration.
- Scoring (pure-function reasoning + compiled-JS scratch): with **zero** resolved leads the
  final score equals the 4.1 base (byte-identical); a segment with a high win rate raises new
  leads' scores by ≤ `ADJ_MAX`, a low win rate lowers them by ≤ `ADJ_MAX`, and a thin segment
  (1–2 resolved) barely moves (shrinkage). `conversionAdjustment` is bounded and monotonic in
  the win rate.
- API (compiled-JS scratch): claim a lead → `outcomeStage` becomes `NEW`; the claimer
  `PATCH .../outcome` NEW→CONTACTED→WON succeeds and updates timestamps; a non-claimer → 403;
  an outcome on an unclaimed lead → 409/400; `stage=LOST` without `lostReason` → 400, with a
  reason → LOST + reason stored; `GET /api/leads/stats` returns the caller's funnel; a
  non-realtor → 403; `GET /api/moderation/conversion` as MODERATOR → the platform funnel +
  segments, as a plain user → 403.
- Web/agent (browser smoke): a realtor opens "Mening leadlarim", sees their claimed leads +
  the funnel summary, advances a lead through the stepper (stage persists, win rate updates),
  marks one LOST with a reason; a moderator opens `/moderation/conversion` and sees the
  platform funnel + the segment table.

## 11. Risks

- **Scoring determinism / testability** — folding data into the score risks making it
  non-deterministic and hard to test. Mitigated by keeping `computeLeadScore` and
  `conversionAdjustment` **pure**; the DB counts live in the service, and with no data the
  composed score is identical to 4.1's. The scratch asserts the zero-data identity.
- **Thin-data over-fitting** — a segment with one lucky WON must not massively boost every
  new lead there. Bayesian shrinkage toward the global rate + the `ADJ_MAX` clamp bound the
  swing; a single sample barely moves `rHat`.
- **Segment sparsity** — too fine a segment (with district) yields single-sample cells.
  Segment is deliberately coarse (`deal + type + budgetTier`, no district).
- **Outcome ownership** — only the claimer may write an outcome; the endpoint checks
  `claimedById === callerId` and the CLAIMED state, so a realtor cannot alter another's lead
  outcome or an unclaimed lead. The scratch asserts the 403/409 paths.
- **Claim-path regression** — the `outcomeStage = NEW` write is one field on the existing
  CLAIMED update inside the claim transaction; it must not perturb the wallet debit or the
  exclusivity lock. Reviewed as part of the claim change; the scratch re-runs the 4.2 claim
  invariants (402/409/one-winner) plus the new stage set.
- **Cross-app boundary** — the cabinet "my leads" page and the web moderator page are in
  their own apps; neither imports the other (FSD/app boundary preserved).
