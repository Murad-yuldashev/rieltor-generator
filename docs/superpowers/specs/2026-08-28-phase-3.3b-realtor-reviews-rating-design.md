# Phase 3.3b — Realtor reviews + rating design

_Date: 2026-08-28 · Branch: `claude/phase-3.3b-realtor-reviews` · Base: master `ce0369c` · Part of: Phase 3 (Product C) · Depends on: 3.3a (RealtorProfile, `/r/:slug`, marketplace seller resolution)_

## 1. Goal

The second half of **C14**: a public **rating + reviews** system for realtors. Any
phone-verified user can leave **one moderated review** (1–5 stars + optional comment) per
realtor. The aggregate (average + count) renders on the public `/r/:slug` microsite (the spot
3.3a reserved) **and** on the marketplace seller display, closing the trust loop 3.3a opened with
the verified badge. With this, **Phase 3 (Realtor toolkit) is complete**.

## 2. Scope

1. **`Review` model** + a cached aggregate (`ratingSum`, `ratingCount`) on `RealtorProfile`.
2. **Write:** `POST /api/r/:slug/reviews` (authenticated) — upsert one review per user per realtor,
   created `PENDING`; a realtor cannot review themselves.
3. **Public read:** `GET /api/r/:slug` gains `ratingAvg`, `ratingCount`, and the list of **APPROVED**
   reviews (author name + photo). The caller's own review (to pre-fill/edit the form) comes from a
   separate authenticated `GET /api/r/:slug/my-review`.
4. **Moderation:** a MODERATOR/ADMIN endpoint to list PENDING reviews and approve/reject; only
   APPROVED reviews are public and counted. Extends the existing moderator area (3.3a).
5. **Marketplace connection:** `AgentSchema` + `ListingSummary` gain `ratingAvg` + `ratingCount`
   (always-populated), rendered as a compact stars+count on the seller panel / result-row / card.
6. **UI:** the `/r/:slug` rating block (aggregate + review list + a "leave a review" form); a
   read-only rating view in the cabinet (`apps/agent`); the marketplace stars.

### Non-goals

- **Realtor replies** to reviews — later.
- **Report / flag** an already-published review — unnecessary under pre-publish moderation; later.
- **Sorting/filtering the marketplace by rating** — later (the aggregate is displayed, not yet a filter).
- **Interaction gating** (only past clients may review) — the answer chosen is open reviews for any
  phone-verified user, moderated. Most `ContactReveal`s are anonymous, so an interaction gate is not
  enforceable with today's data.
- Real payment, subdomain — unchanged from 3.3a.

## 3. Data model (Prisma)

A new `Review` model + two cached columns on the existing `RealtorProfile` (3.3a). Migration is
additive.

```prisma
enum ReviewStatus {
  PENDING
  APPROVED
  REJECTED
}

model Review {
  id         String       @id @default(cuid())
  /// The realtor being reviewed (User.id; the user owns a RealtorProfile).
  realtorId  String
  realtor    User         @relation("ReceivedReviews", fields: [realtorId], references: [id], onDelete: Cascade)
  /// The author of the review (User.id).
  authorId   String
  author     User         @relation("WrittenReviews", fields: [authorId], references: [id], onDelete: Cascade)
  rating     Int          // 1..5, validated in the DTO
  comment    String?      // optional, capped in the DTO (~1000 chars)
  status     ReviewStatus @default(PENDING)
  createdAt  DateTime     @default(now())
  updatedAt  DateTime     @updatedAt

  @@unique([realtorId, authorId])       // one review per user per realtor (re-submit = upsert)
  @@index([realtorId, status])          // public list (APPROVED) + aggregate recompute
  @@index([status, createdAt])          // moderator PENDING queue
}
```

Additions to `RealtorProfile`:

```prisma
model RealtorProfile {
  // ... existing (3.1 + 3.3a)
  ratingSum   Int @default(0)   // sum of APPROVED ratings
  ratingCount Int @default(0)   // number of APPROVED reviews
}
```

`User` gains the two back-relations (`ReceivedReviews`, `WrittenReviews`). The average is derived:
`ratingCount > 0 ? ratingSum / ratingCount : null`. **Self-review is rejected in the service**
(`authorId === realtorId` → 400); the `@@unique` guarantees one row per (realtor, author).

**Why cache the aggregate:** the marketplace serializes the seller for every listing on every
request (Section 5). Computing `AVG`/`COUNT` per listing would be an N+1. `ratingSum`/`ratingCount`
are updated transactionally whenever a review's APPROVED-membership changes (Section 6), so the
mapper reads two integers.

## 4. Write flow + public read

**Write — `POST /api/r/:slug/reviews`** (`JwtGuard`, authenticated; NOT subscription-gated — the
reviewer is a marketplace user, not a subscriber):

- Resolve the realtor by `slug` (the public identity); `NotFoundException` on unknown slug.
- Body `ReviewCreateSchema` = `{ rating: 1..5 (int), comment?: string ≤ 1000 }`.
- `authorId = req.user.id`. If `authorId === realtorId` → `BadRequestException('O'zingizga sharh qoldira olmaysiz')`.
- **Upsert** on `[realtorId, authorId]`, in a transaction: create or overwrite the caller's review;
  **status resets to `PENDING`** on every write (an edit re-enters moderation). If the row being
  overwritten was `APPROVED`, it leaves the APPROVED set, so the same transaction decrements the
  aggregate (`ratingSum -= oldRating`, `ratingCount -= 1`); a create, or an edit of a non-APPROVED
  review, leaves the aggregate untouched. Returns the caller's review (`{ rating, comment, status }`).

**Public read — `GET /api/r/:slug`** (existing endpoint, extended, still public/unauthenticated):
`PublicRealtor` gains `ratingAvg: number | null`, `ratingCount: number`, and
`reviews: PublicReview[]` where `PublicReview = { id, rating, comment, authorName, authorPhotoUrl,
createdAt }` — **APPROVED only**, newest first. `authorName` = `User.name ?? 'Foydalanuvchi'`;
`ratingAvg` is the raw `ratingSum / ratingCount` quotient (the UI rounds to one decimal). No
`authorId`/internal fields leak.

**Caller's own review — `GET /api/r/:slug/my-review`** (`JwtGuard`, authenticated): returns
`{ rating, comment, status } | null` for `req.user.id` on that realtor. The web calls it only when
logged in, to pre-fill the form and show a "moderatsiyada" state; keeping it off the public GET
avoids optional-auth on an otherwise-anonymous route.

## 5. Marketplace connection

Mirrors the 3.3a additive pattern exactly. In `apps/api/src/listings/mapper.ts` (`resolveSeller`):

- **Published realtor** (owner is REALTOR with a slug) → `ratingAvg = ratingCount > 0 ? ratingSum /
ratingCount : null`, `ratingCount` from the owner's `realtorProfile`. The `FULL_INCLUDE` owner
  select gains `ratingSum` + `ratingCount`.
- **Else** (default Agent / seed) → `ratingAvg: null`, `ratingCount: 0`.

`AgentSchema` gains **`ratingAvg: z.number().nullable()`** + **`ratingCount: z.number()`** (always
populated). `ListingSummarySchema` gains **`agentRatingAvg`** + **`agentRatingCount`** (like the
3.3a `agentVerified`/`agentProfileSlug` pair), populated in `toListingSummary`. The listing-detail
seller panel + the result-row/card render a compact **stars + `(N)`** when `ratingCount > 0`;
otherwise nothing (seed listings show no rating, unchanged).

## 6. Moderation

- **`GET /api/moderation/reviews`** (MODERATOR/ADMIN) → PENDING reviews for the queue:
  `{ id, realtorName, realtorSlug, authorName, rating, comment, createdAt }`, oldest first.
- **`PATCH /api/moderation/reviews/:id`** (MODERATOR/ADMIN) body `{ status: 'APPROVED' | 'REJECTED' }`.
  In a **transaction**: read the review's current status, set the new status, and adjust the
  realtor's `RealtorProfile.ratingSum`/`ratingCount` by the delta so the cache always reflects the
  set of APPROVED reviews:
  - PENDING/REJECTED → APPROVED: `ratingSum += rating`, `ratingCount += 1`.
  - APPROVED → REJECTED: `ratingSum -= rating`, `ratingCount -= 1`.
  - No change when the membership is unchanged.
    Re-submitting an already-APPROVED review flips it back to PENDING (Section 4), which must also
    decrement the aggregate at that moment — so the **upsert path**, when it moves a row out of
    APPROVED, applies the same `-rating`/`-1` delta in its transaction. (Only an APPROVED→not
    transition touches the cache; a PENDING edit that stays PENDING does not.)
- Reuse the existing `RolesGuard` + `@Roles('MODERATOR','ADMIN')` (same as the 3.3a realtor
  verification). The moderator web page (3.3a "Rieltorlar") gains a "Sharhlar" queue.

## 7. UI

- **`apps/web` `/r/:slug`** (the reserved 3.3b block): a header stat (average stars + `N ta sharh`),
  the APPROVED review list (author name/photo, stars, comment, date), and a **"Sharh qoldirish"**
  form for an authenticated user (star picker + optional comment). Logged-out → a login prompt
  (reuse `LoginModal`). The user's own review shows its status ("Moderatsiyada" when PENDING) and is
  editable. A realtor viewing their own `/r/:slug` sees no form (self-review blocked).
- **`apps/web` marketplace**: compact stars + count on the listing-detail seller panel (`AgentCard`)
  and the result-row/card, gated on `agentRatingCount > 0`.
- **`apps/web` moderator**: the "Sharhlar" PENDING queue with approve/reject.
- **`apps/agent` cabinet**: a read-only "Baholarim" view — the realtor's average, count, and their
  APPROVED reviews (reuses `GET /api/r/:slug` for their own slug, or a small cabinet endpoint).

- `apps/api`: a `ReviewsService` + a review controller on `@Controller('r')` (`POST /api/r/:slug/reviews`
  with `JwtGuard`, and `GET /api/r/:slug/my-review` with `JwtGuard`); the `RealtorPublicService.getBySlug`
  extended to include `ratingAvg`/`ratingCount`/`reviews` (APPROVED); the moderation area gains the
  reviews endpoints; the listings `mapper` + `FULL_INCLUDE` extended (Section 5). The aggregate
  updates live in `ReviewsService`/the moderation service (transactional deltas).
- `apps/web`: the `/r/:slug` rating block + review form; the marketplace stars; the moderator queue.
- `apps/agent`: the read-only ratings view.
- Shared Zod DTOs: `Review`/`PublicReview`, `ReviewCreateSchema`, `PublicRealtor` additions,
  `AgentSchema`/`ListingSummary` additions, the moderator review row + verify schemas.

## 11. Risks

- **Aggregate drift** — the cached `ratingSum`/`ratingCount` must be updated in the SAME transaction
  as every APPROVED-membership change (approve, reject, and an edit that moves an APPROVED row back
  to PENDING). A missed delta desynchronizes the average. Highest-risk item; the scratch must prove
  every transition. (A recompute-from-rows fallback is trivial if ever needed but not on the hot path.)
- **Marketplace serialization** — the `AgentSchema`/`ListingSummary` additions must be
  always-populated (default `null`/`0`) or existing listing tests/consumers break; verify the listing
  suites early (same as 3.3a's `agentVerified`).
- **Review spam / abuse** — mitigated by phone-verified auth + one-per-user (`@@unique`) +
  pre-publish moderation + self-review block. No rate-limit in this phase (fast-follow, alongside the
  3.3a public/upload rate-limit item).
- **Author privacy** — only `authorName` (nullable → "Foydalanuvchi") + `authorPhotoUrl` are public;
  `authorId`/phone never leak.
